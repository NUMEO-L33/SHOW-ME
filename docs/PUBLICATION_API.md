# 게시·공유 중지 HTTP 계약 — 2026-09-21

2026-09-22 후속 화면 연결과 합성 브라우저 검증은 `PUBLICATION_UI.md`를 따른다. 아래 API 구현 시점의 미연결 기록과 구분하며 기본 운영 활성화는 여전히 OFF다.

기존 E3의 저장 원장·처리본·확정·철회 위에 HTTP 경계와 화면용 요청 함수를 연결했다. 원래 개발 MD의 목표/완료 조건은 변경하지 않았다. **기본 제품은 새 게시를 접수하지 않는다.** 기본 bootstrap이 게시 실행기를 주입하지 않으므로 `canRequest=false`, 새 게시 요청은 503이다. 후속 `PUBLICATION_RUNTIME.md`에서 실제 처리·확정과 선택적인 서버 lifecycle 연결을 구현했지만 기본 활성화/공개 버튼/뷰어는 아직 연결하지 않았다. API 등록과 제품 공개 활성화를 구분한다.

## 소유자 API

모든 경로는 `/api/guides/:guideId` 아래이며 기존 `Authorization: Bearer <editToken>` 인증을 사용한다. 키를 URL/query로 받지 않는다. 잘못된 키/없는 작업은 404, 삭제 대기는 차단하고, 비공개 자료가 만료된 뒤에도 게시 상태 조회와 공유 중지는 허용한다. 인증은 JSON 파싱 전과 비동기 처리 후에도 검사한다.

| 메서드·경로 | 용도 |
| --- | --- |
| GET `/publications` | 진행 중 작업 또는 가장 최근 작업과 현재 공개 상태 |
| GET `/publications/:publicationId` | 응답을 잃어버린 특정 요청의 결과와 현재 공개 상태 |
| POST `/publish` | 사용자가 명시적으로 확인한 새 게시 요청 / 같은 요청 ID의 결과 복구 |
| POST `/unpublish` | 화면에서 관측한 상태와 일치할 때 공유 중지·진행 중 게시 취소 |

게시 본문은 `publicationId`, `baseDraftRevision`, `inputFingerprint`, `reviewFingerprint`, `originalSharingEnabled:false`, `publicSharing:true`만 허용한다. JSON 4 KiB, UUID/지문/정수 검사를 적용한다. 원본 공유 true는 409이며 숨은 원본 경로/worker 명령/임의 설정은 받지 않는다. 새 접수는 신뢰된 실행기의 `PublicationAdmission`으로만 전달하고 저장 계층에서 현재 초안·개인정보 확인을 재검사한다. 실행기를 환경 변수 하나로 우회 활성화하지 않는다.

같은 요청 ID·내용은 기존 작업만 조회/복구하고 완료·취소된 게시를 되살리지 않는다. 내용이 바뀐 재전송은 409다. 응답 유실/timeout 때 새 ID로 자동 재요청하면 안 된다. 이미 저장된 요청은 실행기가 중지됐어도 같은 ID로 확인할 수 있다.

공유 중지는 `{expectedHeadVersion, expectedJobId}`를 비교한다. 첫 게시 전 버전은 0이며 진행 중 작업이 없으면 ID는 null이다. 관측 뒤 새 게시가 생기면 409로 충돌을 알리고 최신 상태를 다시 확인해야 한다. 서버/클라이언트가 몰래 최신 값으로 바꿔 재시도하지 않는다. 공개 참조와 작업 취소가 먼저 확정되고 물리 파일 정리는 내구 원장을 통해 나중에 수행한다.

응답은 `{publication}` 허용 목록이다. 상태·head version·pending/active publication ID·활성 상태일 때만 공개 상대 경로·최초 게시/만료 시각·요청/철회 가능 여부와 축약 job 상태만 포함한다. 원문 job, lease, 자산 키, 초안 내용, 파일명, AI 공급자, 입력/확인 지문은 응답하지 않는다. `canRequest`는 실행기·편집 가능·만료·진행 중 작업에 대한 안내값이며 개인정보 확인 완료의 증거가 아니다. UI는 저장 완료와 현재 개인정보 확인까지 함께 판단해야 한다.

상태 조회는 JSON 원자 읽기 / PostgreSQL 부모 공유 잠금 안에서 현재 head·job·자산과 마지막에 얻은 DB 시각을 사용한다. 조회가 보존 시각을 늘리지 않는다. 정확한 최초 게시+15일 이후 공개 경로를 응답하지 않는다.

## 공개 응답과 이미지

공개 경로는 `/api/public/guides/:slug`다. 32자 난수 slug가 일치해도 현재 활성·미만료·삭제 대기 아님·완료 처리본 조건을 매번 만족해야 한다. 오래된 원본 guide slug나 비공개 조회 API로 대체하지 않는다.

공개 JSON은 제목, 게시/만료 시각, publication ID, 단계별 문구·탭 좌표·크기·처리 이미지 URL만 반환한다. 단계 ID는 게시본 내 `step-1` 등의 순번으로 변환하여 내부 초안 ID를 노출하지 않는다. 파일명·원본/미가림 이미지 키·편집 키·내부 가이드 ID·가림 후보 원문은 포함하지 않는다. 확인된 사용자 작성 문구 자체는 의도한 공개 내용이다.

이미지는 `/api/public/guides/:slug/assets/:publicationId/:stepId/:variant`로 읽는다. variant는 frame/thumbnail만 받으며 다음 순서를 따른다.

1. 현재 공개 권한과 해당 게시본의 처리본 receipt를 읽는다.
2. 저장소의 처리본 하나만 읽고 크기·SHA-256·PNG 식별자를 전체 검증한다. 검증 전에 이미지 바이트를 보내지 않는다.
3. 저장소 읽기 이후 현재 공개 권한과 동일 receipt를 다시 확인한 뒤 응답한다.

기존 이미지 ID/없는 순번/query/Range 요청은 404다. 손상·누락·읽기 실패 때 원본으로 대체하지 않는다. 읽는 동안 철회됐다면 새 이미지 응답은 404가 된다. GET과 HEAD 모두 현재 권한을 확인하며 조건부 요청으로 304를 재사용하지 않는다.

모든 관련 응답은 `Cache-Control:no-store`, `Referrer-Policy:no-referrer`, `X-Content-Type-Options:nosniff`, `Cross-Origin-Resource-Policy:same-origin`, `X-Robots-Tag:noindex,nofollow,noarchive`를 사용한다. 이미 전송한 응답/사용자가 저장한 이미지/제3자 복사본을 회수한다는 보장은 아니다. 공개 링크를 받은 사람이 내용을 볼 수 있다는 점은 게시 UI에서 설명해야 한다.

## 자원 제한·화면 요청 함수

- 소유자 조회/변경: 각각 IP당 분당 60/20회, I/O pool 16개, 단계별 기본 timeout 5초.
- 공개 JSON/이미지: 각각 IP당 분당 120/240회. JSON pool 16개, 이미지 pool 4개, 기본 timeout 25초.
- 이미지당 최대 기존 receipt 상한 13 MiB와 4,096 chunk. 전체 검증을 위한 메모리 버퍼를 사용한다. 뷰어는 이미지 동시 요청을 4개 이하로 제한하고 일시적 503을 처리해야 한다. 아직 그 UI는 연결하지 않았다.
- timeout/접속 종료 뒤 실제 I/O가 끝나지 않으면 슬롯을 계속 점유하여 미완료 요청이 무한히 쌓이지 않게 한다. 분당 제한은 프로세스 로컬이며 다중 서버 전체 한도/운영 부하 검증을 대신하지 않는다.
- `artifacts/showme/src/lib/publication-client.ts`는 같은 출처·no-store·redirect 거절을 사용하는 상태 조회/게시/공유 중지 요청 함수다. 응답 허용 목록·상태·고정 15일·상대 공개 경로·요청 ID를 검증한다. 숨은 자동 재시도는 없다. 아직 편집기나 공개 뷰어에서는 호출하지 않는다.

## 검증과 다음 단계

일반 API 집중 16개와 클라이언트 5개를 추가했다. 잘못된 인증·명시적 동의·원본 공유 금지·응답 유실·재전송 충돌·삭제/철회/재게시·기한 만료·실제 합성 PNG·손상된 저장소·미종료 I/O 한도·빈도 제한을 검사한다. 실제 PostgreSQL에는 HTTP→기존 요청 복구→실제 처리본 준비/확정→공개 조회→철회→재접속 검사를 추가했고, 잠금 대기 중 15일 경계 통과를 소유자 상태 조회에도 검사한다.

첫 DB 검사는 테스트의 내부 단계 ID에 포함된 가이드 ID가 공개 응답에 나타나 실패했다. 검사 조건을 낮추지 않고 공개용 순번으로 분리했으며 같은 회귀 조건을 일반 검사에도 넣었다. 최종 전체 수치와 임시 컨테이너 정리는 `SESSION_CHECKPOINT.md`를 따른다.

후속 실행기/선택적 lifecycle 연결은 `PUBLICATION_RUNTIME.md`를 따른다. 남은 순서는 편집기 게시·철회/공개 뷰어 UI와 합성 브라우저 검증 → Replit migration·기존 역할·Storage 및 합성 실환경 검증이다. 기본 활성화와 불확실 원격 쓰기의 운영 해소도 남아 있다. API 단계에서는 새 migration/운영 DB 변경, .env·키 수정, 개인 영상, 외부 AI 호출, 커밋·푸시·배포·서버 재시작을 하지 않았다.
