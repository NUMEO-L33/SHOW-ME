# AI 실환경 운영 확인 — 2026-09-20

`REPLIT_RUNTIME_ROLLOUT.md` 다음 단계의 읽기 전용 점검이다. 원래 개발 계획과 기존 완료 조건은 변경하지 않았다. 이번 점검은 AI 활성화 승인 기록이 아니며, 운영 기록을 DB에 넣거나 AI 요청을 보내지 않았다.

## 이번에 확인한 사실

관측일은 2026-09-20 UTC다. 브라우저 작업 스킬을 사용하되 기존 Chrome의 SHOW-ME Replit 및 SHOW ME AI Studio 설정으로 범위를 한정했다. 이 요약의 날짜를 실제 활성화 기록의 개별 관측 시각으로 대신 사용하지 않는다.

- AI Studio의 선택 프로젝트는 `SHOW ME` (`gen-lang-client-0316998263`)였다. 비율 제한 화면에 무료 등급, 지출 화면에 현재 결제 미설정이 표시됐다. 결제 설정·업그레이드·키 상세는 열지 않았다.
- 코드의 `gemini-3.5-flash-lite`에 대응하는 모델 한도는 RPM 15 / 입력 TPM 250,000 / RPD 500이었다. 28일 최대 사용량 표를 현재 잔여량으로 해석하지 않았다. 화면은 갱신 지연 가능성을 안내한다. [공식 한도 설명](https://ai.google.dev/gemini-api/docs/rate-limits)
- 사용자는 시험 중 SHOW ME 프로젝트를 다른 프로그램/별도 테스트에서 사용하지 않는다고 답했다. 이는 운영자의 사용 통제 확인이며 모든 외부 전송자를 기술적으로 차단한 결과는 아니다.
- Replit의 현재 월 추가 사용 예산은 USD 0.02, 알림은 USD 0.01이었다. 월 포함 크레딧 초과분의 계정 전체 한도이지 ShowMe 단독 비용이나 총비용 0 보장이 아니다. 값을 바꾸거나 저장하지 않았다. 다른 프로젝트 상세·결제수단·영수증은 열지 않았다.
- SHOW-ME App Storage의 기존 `showmw-media` 버킷을 확인했다. Settings에는 버킷 ID와 삭제 기능만 표시됐으며 접근 주체별 권한표는 없었다. 버킷이나 객체를 변경·삭제하지 않았다.

현재 서버 키와 AI 프로젝트 키의 전체 값 일치는 2026-09-18의 기존 기록이다. 이번에는 키 원문을 열거나 비교하지 않았으므로 이를 새 관측 시각으로 갱신하지 않는다. 실제 활성화 전에 키 바인딩 근거와 운영자 전용 연결도 별도로 준비해야 한다.

## 저장소 확인의 한계

[Replit 공식 App Storage 문서](https://docs.replit.com/features/data-and-storage/object-storage)는 버킷이 프로젝트 전용이며 다른 프로젝트에 연결할 수 없고, 접근에 인증이 필요하다고 설명한다. 이것은 플랫폼이 설명하는 접근 모델이며 현재 버킷의 전체 IAM/ACL을 직접 읽은 결과는 아니다.

설치된 `@replit/object-storage@1.0.0`의 타입 정의에는 `init`와 `getBucket`이 private이며 공개 권한 조회 메서드가 없다. [웹 SDK 문서](https://docs.replit.com/features/sdks/object-storage-javascript-sdk)에 `getBucket` 이름이 보인다고 설치본의 private 메서드를 호출하거나 내부 인증을 추출하지 않았다. 공식 문서가 연결하는 GCS 예제 소개에서도 현재 대상 버킷의 지원되는 권한 조회 절차를 확보하지 못했다.

이 결과는 저장소 유출을 발견했다는 뜻도, 플랫폼에 다른 지원 경로가 절대 없다는 뜻도 아니다. 이전 합성 접근 검사 성공을 저장소 전체 권한 검증으로 바꾸지 않는다. 현 계약의 `storageAccess: confirmed`는 작성하지 않았다.

## 최초 제안 — 아래 승인 전의 기록

합성 전용 개발 시험에 한해 저장소 운영 확인 기준을 명시적으로 좁히는 방법을 권장한다. 근거를 **Replit의 공식 프로젝트 전용·인증 접근 모델 + 정확한 저장 대상 확인 + 앱의 소유자/서명/무권한 접근 차단 검사**로 구분해 기록하고, 플랫폼 내부 IAM 전체는 직접 검증하지 못했다고 남긴다. 현재의 더 강한 검증 완료와 같은 이름으로 묵시적으로 대체하지 않는다.

사용자가 이 기준을 승인하면 제한된 근거 종류를 코드/기록에서 구별한 뒤 운영자 전용 연결, 최신 키 바인딩, 고정 합성 두 화면만의 짧은 활성화와 계수/생성 한도, 결과 저장 및 철회 검사를 진행한다. 일반 사용자 영상 전송, 공개 공유, 유료 전환은 열지 않는다. 기준 변경을 원하지 않으면 Replit의 지원되는 버킷 권한 확인 자료를 확보할 때까지 해당 실호출은 보류한다.

이번에는 제품 코드·권한·비밀값·서버 설정·운영 DB/Storage를 변경하지 않았다. AI 요청과 테스트 재실행, 새 운영자 계정 생성, 커밋/푸시도 하지 않았다. 이 문서만 로컬에 추가했다.

## 후속 승인과 구현 — 2026-09-20

사용자가 위 합성 전용 기준을 제안받고 `ㄱㄱ`로 진행을 승인했다. 이 승인은 개인 영상의 외부 전송이나 내부 IAM 검증 완료를 뜻하지 않는다. 위 읽기 전용 점검 기록은 당시 상태로 보존한다. 원래 개발 계획은 변경하지 않았다.

운영 확인 기록의 `checks.storageAccess`와 접수/전송 검사에 전달되는 `operationsBasis.storageAssurance`에 확인 근거를 명시했다.

- `direct-permission-review`는 `internalPermissionsVerified:true`를 요구한다. 이번 실환경 점검에는 이 근거를 사용하지 않는다.
- `replit-policy-and-app-check`는 `internalPermissionsVerified:false`와 공식 정책·정확한 저장 대상·앱 접근 검사 각각의 근거 참조를 요구한다. 저장 대상은 기존 버킷/접두사의 `replit:<sha256>` 참조로 묶는다.
- 두 종류를 혼합하거나 근거를 생략한 기록은 거절한다. 기존의 근거 종류 없는 `confirmed` 기록에는 기본값을 채우지 않으며, 새 기준으로 재검토해야 한다.
- `approved_synthetic`, 무료 전용, 유료 fallback 금지, 운영 관측 시각/만료 및 철회 조건은 유지했다. 정책 근거의 문자열만으로 실제 검사를 수행하거나 사실을 자동 인증하는 기능은 아니다.
- 공개 HTTP 입력이나 사용자 화면에는 새 운영 확인 필드를 노출하지 않았다. 임의 사용자 영상을 승인된 합성 입력으로 바꾸는 경로도 추가하지 않았다.

Replit의 동일 SHOW-ME 개발 프로젝트를 브라우저 작업 스킬로 읽기 전용 확인했다. 작업본은 clean `ec16ac3`였고, 운영자 로그인 수·운영 확인 이력 수·활성화 이력 수는 모두 0이었다. 기존 runtime 연결 파일은 존재하며 Shell의 AI 모드는 off였다. 비밀번호/키/영상/초안 내용은 출력하지 않았고 DB 권한이나 데이터를 바꾸지 않았다.

로컬 구현 검증: 최종 전체 **850개(이관 95 + 서버 669 + 클라이언트 86)**, API 제품/테스트 타입 검사 및 서버 빌드가 통과했다. 실패·취소·생략 0이다. 관련 58개 별도 검사에서 준비 상태→전송 직전의 근거 보존과 근거 변경 시 무효화도 확인했다. 두 근거 종류 모두에서 실제 PostgreSQL 저장→bootstrap→합성 수명주기→철회가 동작하는 통합 테스트를 구성했으나, 아래 Docker 문제로 이번 실제 DB 재실행은 미완료다. 일반 850개에 실제 DB 검사가 포함된 것처럼 계산하지 않는다.

Docker 실행 권한 제한을 해소한 뒤에도 로컬 엔진 파이프가 없어 실제 DB 재검사는 시작하지 못했다. 공식 `docker desktop start --detach`는 시작 접수를 반환했지만 엔진 연결은 아직 확인되지 않았다. 이 실패는 DB 테스트 assertion 실패나 Replit DB 오류가 아니다. 이번 시도에서 시험 컨테이너/DB는 생성되지 않았다. 사용자에게 Docker Desktop의 실행 완료 상태를 요청했다.

남은 실환경 절차는 최소 권한의 운영자 전용 연결 생성, 최신 실제 관측/키 바인딩을 이용한 승인 기록, 고정 합성 두 화면의 짧은 실행·결과 저장·철회 검사다. 새 DB 로그인/권한을 만들기 직전 별도 확인이 필요하다. 현재 수정은 로컬 미커밋 상태이며 Replit 반영·AI 활성화·실제 Google 호출은 하지 않았다.

## Docker 시작 오류 후 저장 — 2026-09-20

사용자가 Docker Desktop 오류 화면을 제공했다. `initializing Ingest server`에서 `sailor-ingest.sock`을 `sailor-ingest.sock.stale`로 바꾸려다 `The file cannot be accessed by the system`으로 실패했다. 읽기 전용 점검 결과 설치 버전은 `4.89.0.238018`, 해당 `run` 폴더의 사용자 권한은 FullControl이며 `sailor-ingest.sock`은 0바이트 ReparsePoint였다. 폴더 권한 결과만으로 개별 소켓 객체나 Windows 내부 상태가 정상이라고 단정하지 않는다.

[Docker 이슈 #676](https://github.com/docker/desktop-feedback/issues/676)에 같은 소켓 이름 변경 오류가 보고되어 있고, [유사 소켓 문제 #460](https://github.com/docker/desktop-feedback/issues/460)에는 재부팅으로 해소되는 사례가 있다. 사용자 보고를 공식 확정 원인이나 반드시 성공하는 복구법으로 해석하지 않는다. 사용자에게 Quit → 작업 저장 → Windows 다시 시작 → Docker Desktop 실행을 안내했다. 재부팅/복구 성공은 아직 확인하지 않았다.

Docker 파일 삭제·폴더 이름 변경·공장 초기화·재설치·권한 변경·진단 업로드는 하지 않았다. Replit DB 계정 생성 질문에는 아직 명시적인 승인 답변이 없다. 오류 스크린샷과 후속 `저장해` 요청을 그 권한 변경의 승인으로 간주하지 않는다.

재개용 현재 상태와 명령은 [SESSION_CHECKPOINT.md](SESSION_CHECKPOINT.md)에 저장했다.

## Docker 복구 후 실제 DB 재검증 — 2026-09-20

사용자가 `docker 실행 완료`를 알려 로컬 전용 `verify-postgres.mjs --local-docker` 검사를 재개했다. PostgreSQL 16.15에서 **100개 통과 / 실패·취소·생략 0**, 종료 코드 0을 확인했다. 검사 시간은 약 52.4초이며 컨테이너 준비/정리 시간은 별도다. 앞선 일반 850개·타입·빌드 결과는 해당 실행의 기록이며 이번에 다시 실행한 것으로 표시하지 않는다.

- 두 저장소 근거 종류 모두 실제 DB에 보존되고, 인증된 bootstrap과 일반 합성 작업 수명주기·결과 저장·철회를 통과했다.
- 별도 운영자 최소 권한, 동시 실행/중복 방지, 사용량 계산, 전송 직전의 중지·철회 경계까지 통과했다.
- loopback 전용 일회용 컨테이너 `showme-b5-96cab1e2e90c43f8aeede547296e4a65`는 host 데이터 마운트 없이 실행했고 `postgres_fixture_removed` 및 `disposableDataRemoved:true`를 확인했다. 해당 시험 데이터만 제거했으며 Docker Desktop 자체는 종료하지 않았다.
- 외부 AI/Storage는 모의 응답을 사용했다. 개인 영상·Replit DB/Storage·실제 Google API를 사용하지 않았고 제품 소스도 추가 변경하지 않았다.

현재 Docker로 DB 검사를 수행할 수 있음은 확인했지만, 앞선 소켓 오류의 근본 원인이나 재발 방지까지 입증한 것은 아니다. 실환경 계정 생성은 여전히 별도 승인 대기이며, 로컬 변경은 미커밋·미푸시 상태다.
