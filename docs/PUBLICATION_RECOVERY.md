# 게시 준비 작업의 재시작 정리 — 2026-09-21

E3 내부 유지보수 루프 `PublicationRecoveryWorker`를 추가했다. 기존 MD 목표/완료 조건은 변경하지 않았다. **복구는 실패한 비공개 준비 작업 정리이며 게시 성공이나 공개 링크 복원이 아니다.** 클래스 생성/import만으로 실행되지 않으며 제품 시작·HTTP·UI에 등록하지 않았다.

후속 `PUBLICATION_COMMIT.md`에서 원자적 게시 확정을 구현했다. 이 루프의 정리 대상도 `succeeded` 작업 중 자산이 이미 cleanup인 이전 게시 묶음까지 확장했다. 활성 ready 처리본은 대상이 아니며 repository도 삭제 대기가 아닌 활성 묶음의 정리를 거절한다. 아래 952/118개와 JSON v7은 복구 단계 당시 검증 기록이며 최신 결과/저장 형식은 후속 문서를 따른다.

다음 후속 `PUBLICATION_LIFECYCLE.md`에서는 한 회차 시작에 최대 20개 게시 만료 발견/철회를 추가했다. 공개 참조를 차단한 뒤 기존 cleanup 경로로 처리본을 정리한다. 원본/초안 정리와 제품 자동 시작은 여전히 미연결이다. 아래 실패 준비 작업만 다룬다는 설명은 최초 복구 단계의 범위다.

## 처리 범위

- `listPublicationRecovery`는 만료된 running 작업과, 자산 기록이 남은 failed/cancelled 작업을 별도로 찾는다. queued, 만료 전 running, 자산 기록이 이미 제거된 과거 작업은 정리 대상에서 제외한다.
- 각 조회는 최대 20개를 반환한다. 고유한 batch UUID의 keyset cursor를 두 종류별로 돌리며, 끝에 도달하면 다음 회차에 처음부터 조회한다. 미확인 writer나 반복 실패 선두 때문에 뒤쪽 작업이 계속 가려지지 않는다. JSON과 실제 PostgreSQL이 같은 순서/필터를 사용한다.
- 만료 취소는 기존 부모 가이드 잠금 안에서 version/현재 DB 시각을 재검사한다. 작업을 재claim하거나 가림 변환/원격 put을 다시 실행하지 않는다. 늦은 원래 writer의 준비 확정도 허용하지 않는다.
- 정리는 해당 terminal 작업의 정확한 자산 묶음만 대상으로 한다. 출력 키를 지운 뒤 실제 writer 종료와 원장 version이 확인될 때만 자산 기록을 제거한다. 초안/원본/다른 묶음/부모 가이드는 이 루프가 삭제하지 않는다. 부모 전체 삭제는 기존 lifecycle의 책임이다.
- PostgreSQL 자산 INSERT/UPDATE/DELETE도 RETURNING 결과를 확인하도록 보완했다. 조용히 무시된 DB 쓰기는 완료로 반환하지 않는다. 정리 실패 후 원장을 남겨 재접속한 worker가 다시 시도한다.

## 실행·중단과 자원 상한

- 명시적 `start()`만 주기 실행한다. 기본 간격 5초, 실패 시 최대 60초까지 재시도 간격이 늘고, 정리 미완료가 있으면 최소 30초 간격이다. 원격 오류 원문/키/파일명은 상태 보고에 포함하지 않는다.
- 로컬 동시 tick은 하나로 합쳐진다. 한 회차 제한은 기본/최대 30초이며, 개별 자산 묶음 삭제의 기본 제한은 5초다. 후보별 오류는 다음 후보를 막지 않는다.
- DB 조회가 제한시간 뒤에도 끝나지 않으면 그 worker의 실행 자리를 유지해 추가 조회가 쌓이지 않게 한다. 종료/시간 초과 뒤 늦게 도착한 조회 결과로 다음 저장소 요청을 시작하지 않는다.
- 삭제 SDK가 제한시간 후 계속 실행 중이면 같은 Storage 인스턴스의 기존 요청을 추적하고, 실제 완료 전 새 정리 묶음을 시작하지 않는다. 종료 전 이미 요청한 작업을 취소했다고 가정하지 않는다. 재접속 시 삭제 자체는 같은 terminal 키에만 안전하게 재시도한다.
- `stop()`은 새 회차를 막고 호출자에게 신속히 돌아오되 이미 진행 중인 I/O가 있으면 `pendingIO: true`를 보고한다. 이미 발행한 DB/저장소 작업의 취소나 물리 삭제 완료를 뜻하지 않는다. 멈춘 인스턴스는 재시작하지 않으며 새 인스턴스를 만들어 사용한다.
- 공통 삭제 함수에도 중단 검사를 추가했다. 이미 취소된 요청이나 늦게 도착한 원장 조회가 새로운 저장소 삭제를 시작하지 않으며, 중단 뒤 다음 20-key 묶음을 시작하지 않는다.

## 불확실 원격 쓰기의 한계

프로세스가 원격 put 중 죽어 `writerSettled=false`로 남은 경우, 반복 삭제가 성공해도 ‘writer 종료/삭제 완료’로 승격하지 않는다. 일시적인 파일 부재나 lease 만료는 늦은 put이 불가능하다는 증거가 아니다. 해당 job/자산 기록과 부모 삭제 차단은 유지한다. 자동 루프는 나머지 정리를 계속할 수 있지만 **이 불확실성 자체를 자동 해소한 것은 아니다.**

실제 Replit Storage의 요청 종료/늦은 commit 검증과 불확실 기록의 운영 해소 절차는 R1 실환경 검증에 남긴다. 타이머만으로 종료를 조작하거나, 삭제를 강제로 완료 처리하는 운영 명령은 추가하지 않았다. 단독 E2 자산 함수의 job 없는 기록을 이 루프가 임의로 가져가 정리하지도 않는다.

다음 제품 구현은 불변 게시본·원자적 활성 참조 교체, 철회, 첫 게시 후 15일 만료다. 이후 준비 실행기/이 정리 루프/인증 API의 제품 lifecycle 연결과 Replit 실환경 검증을 함께 진행해야 한다. 현재 미공개 원본 보존 정책은 바꾸지 않았다.

## 검증·배포 경계

- 새 일반 검사 12개: 재접속·정확한 lease 경계, queued/유효 lease 보존, 실제 가림 이미지 정리, 20개 미확인 선두 뒤 작업 처리, 실패 후 재시도, 동시 tick, 멈춘 DB 조회·늦은 삭제, 중단 시 추가 삭제 차단, 명시적 주기 실행/중단, 잘못된 입력 거절/제품 미등록을 검사했다. 처음 실행의 4개 실패는 새 다중 가이드 fixture가 extracting 상태를 생략한 문제였고, fixture 수정 후 12개 모두 통과했다. 제품 상태 검증을 완화하지 않았다.
