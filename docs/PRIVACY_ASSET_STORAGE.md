# 가림 처리본 내구 저장 — 2026-09-21

원래 개발 계획의 E2 저장 엔진 체크포인트다. 기존 MD의 목표·완료 조건은 변경하지 않았다. **내부 저장 함수와 삭제 연결을 구현했으며 게시 접수/자동 worker/공개 HTTP/화면 버튼은 활성화하지 않았다. E2/E3 전체 또는 실환경 완료가 아니다.** 원본 보기, 개인 영상 AI 전송, Replit/Google 설정도 변경하지 않았다.

## 구현 범위

- `writePrivateRedactions`는 서버 내부 함수다. 소유자 인증을 대신하지 않으며 이후 E3의 인증된 게시 접수기가 호출해야 한다. 현재 HTTP 경로/제품 시작 경로에서 호출하지 않는다.
- 현재 저장 revision·미디어 지문·개인정보 확인 지문이 모두 일치하고, 제목/모든 단계의 문구/화면 확인이 완료돼야 작업을 예약한다. 처리 계획은 서버의 초안/정규 원본 프레임 키에서만 만든다. 켜진 가림은 visible/zIndex와 무관하게 적용한다.
- 새 `guide_assets` 행에 모든 출력 키의 정리 소유권을 먼저 기록한다. 가이드당 최대 4개 묶음, 각 24단계/48개 PNG다. 묶음 UUID별 독립된 `guides/<id>/private-redactions/<batch>/<index>-<variant>.png` 키를 쓰고 원본 키를 덮어쓰지 않는다.
- 작업 상태는 reserved → writing → ready 또는 cleanup이다. claim은 revision과 단일 writer를 비교해 한 번만 성공한다. 모호한 응답을 받았다고 같은 쓰기를 재전송하지 않는다. ready는 내부 자산 준비 상태일 뿐 게시 허가가 아니다.
- 기존 제한된 JPEG 디코딩/불투명 타일 PNG 변환을 재사용한다. 이미지와 썸네일을 각각 비공개 Storage에 저장하고, 전부 다시 읽어 길이/SHA-256이 일치하는지 확인한 뒤 DB에 receipt를 저장한다. 실패 시 원본/기존 미가림 썸네일을 대신 복사하지 않는다.
- 완료 직전 부모 가이드 잠금 안에서 현재 revision·확인 상태·처리 계획을 재검사한다. 수정/삭제가 먼저 반영되면 ready로 확정하지 않고 cleanup으로 보낸다. 초안·원본·보존 시각은 저장 엔진이 변경하지 않는다.
- 프로세스당 엔진 1개, 전체 제한 120초, 원본 읽기 2 MiB, 출력/재읽기 최대 13 MiB, 스트림 조각 수 제한을 적용한다. 임시 파일은 신뢰한 `config.dataDir/work`를 전달받아 그 아래 고유 디렉터리에 만들고 finally에서 지운다. 이 위치는 기존 시작 시 일회용 work 정리 대상이다. 임의 HTTP 경로를 workDir로 받으면 안 된다.

## 삭제·늦은 쓰기

- 기존 전체 삭제 API와 lifecycle의 최종 삭제에 처리본 정리를 연결했다. 먼저 작업을 취소하고 정규 출력 키를 지운 뒤, 실제 writer가 종료됐을 때만 기록을 제거한다.
- JSON repository와 PostgreSQL repository 모두 자산 기록이 남으면 가이드 삭제를 거절한다. SQL FK도 `ON DELETE RESTRICT`다. 미정리 자산을 cascade로 잊지 않는다.
- 저장소 SDK가 취소를 무시하면 호출자는 timeout/취소 오류를 받지만 작업 슬롯·정리 기록은 유지한다. 늦은 저장이 실제로 끝난 뒤 다시 삭제한다. 실패한 삭제는 기록을 보존하여 재시도할 수 있다. 오류 응답에 원본 키/비밀값을 넣지 않는다.
- **프로세스가 원격 저장 도중 완전히 죽어 종료 여부가 불명확해진 기록은 자동으로 완료/삭제됐다고 추정하지 않는다.** 재시작 후에도 writing/cleanup 기록과 삭제 차단이 유지된다. 이를 안전하게 해소하는 게시 job 복구/운영 절차는 E3에서 연결해야 한다. 현재 엔진을 일반 사용자에게 활성화하지 않은 이유이며, 무조건 시간이 지나면 안전하다고 처리하지 않는다.
- reserved/ready 등 종료가 확인된 자료의 정리 함수와 기존 전체 삭제의 반복 정리는 구현했다. 별도 게시 작업 큐, 전역 고아 작업 발견/재시작 복구, 영구 저장소의 늦은 commit에 대한 실제 검증까지 완료한 것은 아니다.

## 저장 형식·배포 주의

- 신규 migration `0013_private_redaction_assets.sql`만 추가했다. 기존 migration SQL은 바꾸지 않았다. 기존 운영 DB에는 실행하지 않았다.
- Replit의 verify-only 서버 반영 전 별도 migration 권한으로 0013 적용, 기존 실행 역할의 `guide_assets` SELECT/INSERT/UPDATE/DELETE 권한 확인/추가가 필요하다. 역할 새 생성 함수에는 해당 테이블을 추가했지만 **기존 역할을 자동 재생성/승격하지 않는다.** 운영 변경은 별도 단계다.
- JSON 파일은 v6으로 올라간다. v1–v5는 읽기 시 디스크를 다시 쓰지 않고, 다음 쓰기 때 빈 자산 원장을 추가한다. 구형 버전에 자산 필드가 섞인 파일은 거절하여 삭제 목록을 무시하지 않는다. v6을 쓴 뒤 구형 바이너리로 단순 롤백하지 않는다.
- 자산 원장을 이미지 접근 권한으로 사용하면 안 된다. 원본/임시/처리본 모두 현재 공개 경로가 없고, 기존 소유자 DTO에도 새 object key를 추가하지 않았다. 이후 공개 자산 응답은 별도 확정 게시본과 현재 공개 권한·만료를 검사해야 한다.

## 검증

- 일반 새 검사 14개: 실제 합성 JPEG → 처리 PNG/썸네일 → LocalStorage 저장/재읽기·재접속, 원본/초안 불변, 예약 상한, 단일 writer, 수정/삭제 경합, 부분 저장·원본 읽기·손상 재읽기·변환 오류, 늦은 쓰기, 삭제 실패 재시도, JSON 업그레이드, 잘못된 처리 계획, 직접 object key/미등록 HTTP 비노출, 실제 전체 삭제 경로를 검사했다.
- 전체 일반 **911개 통과**(이관 99 / 서버 713 / 클라이언트 99), 실패·취소·생략 0. 이후 임시 파일 위치를 기존 work 정리 경로로 옮긴 최종 변경은 관련 14개 재검사·서버 제품/테스트 타입 검사·서버 빌드 통과로 확인했다. 화면 코드는 바꾸지 않았으며 이번 단계의 새 브라우저 UI 검증은 없다.
- 실제 PostgreSQL 16.15 **106개 통과**, 실패·취소·생략 0, 종료 코드 0. 새 3개는 예약 상한/동시 claim/재접속/삭제 제한, 편집 후 확정 거절/실제 trigger 실패 롤백, ready receipt와 초안·보존 시각 불변을 검사했다. 기존 14개 migration 적용/재실행도 포함한다.
- 첫 전체 실행의 모듈 초기화 순환을 버전 상수 분리로 해결했다. JSON v6 및 새 자산 조회에 맞게 이전 형식 시험 fixture와 mock을 갱신했다. 첫 DB 실행에서는 예전 migration 개수 기대값 13 때문에 1개 실패했고, 실제 14에 맞춰 수정한 전체 재실행이 통과했다. 실패 실행도 성공으로 소급하지 않는다.
- Docker 엔진 부재로 처음에는 시작 전 실패했다. 사용자가 실행한 뒤 일회용 로컬 DB로 재개했다. 최종 컨테이너 `showme-b5-957a6e3081dc4a819e8efc6bd1f74eb7` 및 이전 실행 컨테이너의 `postgres_fixture_removed`를 확인했다. 개인 영상, .env, 운영 DB, 실제 외부 AI/Storage는 사용하지 않았다.
