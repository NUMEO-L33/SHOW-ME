# 게시 확정의 원자적 저장 — 2026-09-21

기존 계획 E3의 내부 게시 확정 단계를 구현했다. 모든 처리본 준비가 끝난 뒤 불변 게시본, 활성 게시 참조, 작업 성공, 이전 처리본의 정리 소유권을 함께 저장한다. **HTTP·공개 조회·화면 버튼·자동 실행은 아직 연결하지 않았고, 실제 공개 기능을 켜지 않았다.** 원래 개발 MD의 목표와 완료 조건은 변경하지 않았다.

후속 `PUBLICATION_LIFECYCLE.md`에서 내부 철회·현재 접근 검사·15일 만료/처리본 정리를 추가했다. 아래 철회/만료 미구현과 검증 개수는 확정 단계 당시 기록이다. 제품 HTTP/뷰어 연결과 7일 비공개/15일 게시 보존 분리는 여전히 남아 있으므로 실제 공개는 활성화하지 않는다.

## 확정 계약

- `commitPublication`은 부모 가이드 잠금 안에서 정확한 작업 ID/version/writer lease, lease 유효기간, 현재 저장 초안·개인정보 확인·이미지 계획을 다시 검사한다. ready이고 writer 종료가 확인된 자산 묶음만 사용할 수 있다. 선택적 `now`는 신뢰된 테스트용이며 HTTP 입력으로 노출하면 안 된다.
- `guide_publications`는 허용된 제목·단계 문구·순서·클릭 표시와 검증된 처리본 PNG/썸네일 receipt만 보관한다. 원본 키·파일명·편집 자격 증명·제작 의도·개인정보 후보는 복사하지 않는다. 원본 공유는 계속 `false`만 허용한다. 이 저장 구조 자체는 공개 응답 DTO가 아니다.
- `publication_heads`는 별도로 무작위 생성한 192비트 공개 slug와 활성 게시본 ID를 가진다. 기존 내부/편집 식별자를 공개 slug로 재사용하지 않는다.
- 새 snapshot INSERT, job `succeeded / committed`, 활성 head 전환, 이전 active 자산의 cleanup 전환은 PostgreSQL의 한 트랜잭션 또는 JSON의 한 번의 원자적 파일 교체로 확정한다. DB 예외·조용히 무시된 쓰기·파일 저장 실패에서 기존 게시본을 유지한다.
- PostgreSQL은 각 변경의 RETURNING을 확인하며, 게시본 UPDATE를 막는 trigger와 활성 참조의 복합 FK를 둔다. 기존 게시본을 수정해서 새 초안과 섞지 않는다. 이후 초안 편집도 이미 확정한 snapshot에는 영향을 주지 않는다.
- 같은 성공 요청을 다시 보내면 동일 소유권과 직전 version을 확인해 저장된 결과를 반환할 뿐 다시 쓰지 않는다. 이후 게시본으로 전환한 뒤 과거 요청을 재전송해도 과거 게시본을 다시 활성화하지 않는다. 이미지 변환/원격 put도 이 메서드에서는 실행하지 않는다.
- 일반 준비 취소/실패/abandon으로 성공한 게시를 되돌리지 않는다. 활성 게시본의 처리 자산은 일반 자산 정리 명령이 가져가지 못한다. 새 게시 확정에 성공한 뒤 이전 묶음만 cleanup으로 넘기고, 기존 복구 루프가 `succeeded`이면서 실제 자산 상태가 cleanup인 묶음도 정리한다. active ready 묶음은 제외한다.
- 전체 삭제 표시가 먼저 저장되면 새 확정과 성공 재전송을 거절한다. 이 표시 뒤에는 활성 자산 보호를 해제해 기존 전체 삭제 순서로 처리본을 정리한다. 모든 자산 원장이 제거된 뒤 부모 삭제가 게시본/참조/작업 이력을 함께 지운다.

## 보존 기간: 저장 규칙만 완료

첫 확정 때 서버 시각으로 `expiresAt = firstPublishedAt + 15 × 24시간`을 저장한다. 같은 링크의 재게시로 slug·최초 게시 시각·만료를 바꾸지 않으며 SQL trigger도 이를 차단한다. 만료 경계부터 새 확정을 거절하고 성공 재전송 결과의 `active`는 false다.

**15일 보존·공개 접근 차단·자동 만료 정리를 모두 구현한 것은 아니다.** `getPublicationState`는 인증/만료 판단이 없는 내부 저장 조회이며 공개 API로 그대로 내보내면 안 된다. 제품 공개 조회에는 삭제 대기 여부·현재 활성 참조·만료 시각 검사가 별도로 필요하다.

기존 제품의 7일 미공개 정리는 현재 부모 가이드를 전체 삭제한다. 그대로 게시 기능을 켜면 15일 게시본도 일찍 삭제할 수 있으므로, 다음 단계에서 원본/초안 정리와 공개 처리본 보존을 분리해야 한다. 게시 가이드를 통째로 7일 정리에서 제외하여 원본 보관을 무단 연장하는 방식은 적용하지 않았다. 공유 철회, 만료 후 참조 차단·자산 정리, 위 보존 분리를 마치기 전 제품 lifecycle에 연결하지 않는다.

## 저장 형식과 배포 경계

- 새 migration `0015_publication_commit.sql`을 추가했다. 앞선 SQL 파일은 수정하지 않았고 0014 job 상태 제약은 새 migration에서 확장한다. 운영 DB에서는 실행하지 않았다.
- JSON v8이다. v1–v7을 읽을 때 파일을 쓰지 않고 다음 변경에서 승격한다. 구버전에 새 게시 필드가 숨어 있거나, 성공 작업과 게시본/참조가 불일치하면 거절한다. 구형 바이너리로 단순 롤백하면 안 된다.
- 새 runtime 역할 생성 코드에 snapshots SELECT/INSERT/DELETE와 heads CRUD를 추가했다. snapshot UPDATE는 허용하지 않는다. 기존 역할·Replit DB 권한은 변경하지 않았다. 실제 반영 시 migration과 실행 역할 권한 검사가 별도 필요하다.
- 로컬 미커밋·미푸시 변경이다. Replit pull·재시작·배포, .env·키·개인 영상·외부 AI·일반 공개 설정을 건드리지 않았다.
- 원격 put 도중 프로세스가 죽어 writer 종료가 불확실한 경우는 이전 단계와 동일하게 원장/삭제 차단을 보존한다. 실제 Replit Storage의 늦은 commit 및 운영 해소 검증은 남아 있다.

다음 순서: 공유 철회와 7일 비공개/15일 게시 보존 분리·만료 → 인증 API/작업 실행/화면 연결 → 합성 실환경 출시 검사. E3 전체나 운영 준비 완료로 표시하지 않는다.
