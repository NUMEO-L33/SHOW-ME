# B5 실행 조건 근거 연결 — 내부 구현

2026-09-18. **근거를 묶는 코드만 구현했다. 실제 근거 발급기와 서버 시작 연결은 없으며, 외부 AI는 계속 꺼져 있다.** 현재 사용자 허용 범위인 Replit 처리·저장만 유지한다.

## 이번에 구현한 것

`artifacts/api-server/src/processor/analysis-readiness.ts`의 `EvidenceAnalysisReadiness`는 서버가 제공한 세 검증기의 결과를 받아 기존 접수/전송 검증 계약으로 연결한다. 기본 생성자는 검증기가 없으므로 요청을 거절한다. HTTP 본문, 환경 플래그, 예전 시험 결과를 가져와 준비 완료로 바꾸는 경로는 없다.

| 근거 | 함께 확인하는 범위 |
|---|---|
| 실행 환경 | 동일 배포, PostgreSQL 원장·내구 실행기·계수 원장, Replit 비공개 저장소, 프로젝트 전체 원자적 한도 차감, 호스팅 허용 범위, 프로젝트/키 버전 참조 |
| 승인 입력 | 가이드·전체 manifest 지문·장면 수·모델·프롬프트 버전, 합성 자료 승인, 모든 묶음의 전체 요청 상한 검토 참조 |
| 무료 프로젝트/정책 | 동일 배포·프로젝트·키 버전, 현재 모델, 무료 전용·유료 전환 금지, RPM/입력 TPM/RPD, 앱 예산 정책 |

이 값들의 **문자열 형식이 맞는다는 사실은 실제 검증 증거가 아니다**. 각 검증기는 현재 사실을 확인하고 전체 근거 레코드에 대한 동기식 `isCurrent`를 제공해야 한다. HTTP/환경 JSON을 그대로 돌려주거나 항상 `true`를 반환하는 구현은 허용하지 않는다. 검증기 계약 자체는 네트워크 방화벽이 아니다.

- 세 근거가 전부 유효해야 한다. 서로 다른 배포·프로젝트·키 버전·입력의 근거를 섞지 않는다.
- 근거는 최대 30초이며 새 스냅샷은 가장 이른 확인 시각/만료 시각을 사용한다. 조회할 때 유효기간을 새로 늘리지 않는다.
- 만료, UTC 앱 날짜/태평양 공급자 날짜 변경, 시간 역행, 철회, 실패 시 거절한다. `isCurrent`의 Promise/문자열/숫자는 참으로 취급하지 않는다.
- 조회는 기본 5초 이내에 실패하며, 취소를 무시한 늦은 결과는 근거로 등록하지 않는다. 진행 중 조회는 최대 8개, 근거 보관은 최대 64개다. 멈춘 검증기는 실제 완료 전까지 슬롯을 점유한다.
- `clear()`는 발급한 근거와 진행 중 조회를 함께 무효화한다. 입력/키/정책/환경 변경 시 실제 근거 발급기도 변경을 감지해 기존 레코드를 철회해야 한다.
- 반환값과 검증기 입력을 복제하며 원문 오류·경로·키 값은 노출하지 않는다. 키 버전 참조는 비밀 키 자체가 아니다.
- 기존 예산 검증과 저장 직전 검증을 재사용한다. 조회가 성공해도 저장 전에 철회되면 분석 예약은 남지 않는다.

## 그대로 유지한 경계

사용자 동의/소유권은 기존 분석 API와 내구 상태 검증의 책임이다. 이 연결부가 동의를 만들거나 생략하지 않는다. 준비 스냅샷도 단독 전송 허가가 아니다. 기존 실제 이미지 해시/디코딩 검증, 정확한 요청 지문의 검토 상한, 별도 원장을 거치는 계수, 최신 실측 검증, 최종 잠금/전송 검사 모두 필요하다.

`inputTokenBound`는 승인 자료의 **모든 묶음에 대한 검토된 상한**을 참조하는 필드다. 이 연결부는 토큰 수를 계산하지 않으며 이미지 개수·바이트 수·과거 성공 요청으로 상한을 추정하지 않는다. 정확한 요청의 상한 검증기와 일치하는 근거를 실제 발급기가 제공해야 한다.

현재 `server.ts`/시작 코드에는 이 연결부나 실제 근거 발급기를 넣지 않았다. 기본 새 분석은 기존처럼 503이며, `countTokens`·`generateContent`·AI dispatcher를 실행하지 않는다. 스키마·의존성·클라이언트 UI도 변경하지 않았다.

## 검증과 남은 일

후속으로 [DB 읽기 전용 검사](ANALYSIS_DATABASE_PROBE.md)를 추가했다. 실제 저장소의 DB 객체를 검사하는 부분이지만, 결과는 준비 스냅샷이 아니며 실행 권한을 발급하지 않는다. 후속 로컬 PostgreSQL 16.15 검사 66개(신규 19개 포함)는 모두 통과했다. 운영 DB/저장소 검증이나 실환경 readiness 연결을 뜻하지 않는다.

그 다음 명시적 `check:analysis-db` 명령을 추가해 현재 환경의 DB 설정으로 **별도 프로세스에서** 검사할 수 있게 했다. 실제 CLI 4개를 포함한 로컬 PostgreSQL 70개를 통과했다. 사용자 승인 후 코드 `555b504`를 커밋·푸시·Replit 작업본에 반영하고, Replit B5 단위 55개와 API 제품/테스트 타입 검사를 통과했다. 실제 Replit 대상 명령은 **`target-invalid`, 종료 코드 1로 DB 인증·SQL 전에 거절**됐다. Helium 내부 개발 DB의 SSL 미사용 방식과 점검기의 원격 TLS 필수 조건이 맞지 않기 때문이다. 비밀번호 없는 SSL 지원 진단만 수행했고 조건 완화·Secrets 변경·서버 재시작은 하지 않았다. 세부 결과와 후속 승인 범위는 [DB 검사 문서](ANALYSIS_DATABASE_PROBE.md)를 따른다. 실제 DB 검증은 미완료이며, 이 명령도 실행 중인 API 서버와 동일한 설정/배포임을 증명하거나 실제 근거 발급기를 대신하지 않는다.

- 신규 28개: 정상 결합, 누락/형식/범위/만료/철회, 무료 조건/단위 구분, 비동기 검증 거절, 복제/재진입, 날짜/시계, 시간 초과/늦은 결과/동시 한도, 실제 로컬 예약 경로의 저장 직전 철회와 정상 접수를 확인했다.
- 최종 일반 회귀 **692개(이관 91 + 서버 544 + 클라이언트 57), 실패·생략 0, 종료 코드 0**. API 제품/테스트 타입 검사와 API 빌드 통과. 빌드는 최초 Windows 상위 경로 접근 제한으로 실패한 뒤 같은 명령을 필요한 권한으로 실행해 성공했다. 신규 검사의 최초 실패는 모의 근거 비교가 JSON 속성 순서에 의존한 문제였으며, 전체 값의 깊은 비교로 수정한 뒤 검증했다.
- 이 연결부 최초 검증 자료는 **모의 근거와 로컬 시험 저장소**다. 이것을 현재 Google 계정, 운영 DB/Storage, 호스팅 예산 또는 실제 전체 입력 상한 검증으로 표시하지 않는다. 최초 구현 시 실제 PostgreSQL 47개는 재실행하지 않았지만 위 후속 66개 검사에는 포함돼 재통과했다. 프런트엔드 제품 빌드는 이번 범위에서 재실행하지 않았다.
- 남은 B5: 선택한 환경의 실제 근거 발급/갱신/철회 구현, 정확한 입력 상한의 신뢰 가능한 근거, 운영 대상 연결 검증. 이후 별도 승인된 합성 자료 실호출과 시작 코드 연결이 필요하다. 이번 작업은 B5 전체 완료가 아니다.
- 연결부의 최초 구현에서는 사용자 영상·환경 비밀값·브라우저/CDP·Replit 재시작·운영 DB 변경·공개 공유를 다루지 않았다. 후속 Replit 점검에서는 승인된 SHOW-ME Chrome 탭만 사용했고 비밀값 비출력·영상 비접근·DB 무변경·외부 AI 비활성을 유지했다.
