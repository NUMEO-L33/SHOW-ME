# 분석 HTTP API — Gate 3B-2A / B3 접수기 / B4-A 저장 연계

작성일: 2026-09-14 · 범위: 독립 Node 프로세서의 요청·조회·취소 경계

세 경로와 `DurableAnalysisAdmission`을 실제 서버에 등록했다. **기본 접수기에는 실제 준비 조건 검증기(`AnalysisAdmissionReadiness`)가 없으므로 새 분석 요청은 계속 `503 ANALYSIS_UNAVAILABLE`이며 초안·대기 작업도 만들지 않는다.** B3의 202 흐름은 가상의 준비 조건 보고서와 실제 로컬 JSON 저장소를 연결한 HTTP 통합 테스트다. 실제 DB/작업 실행기/무료 상태를 검증했거나 Google 자동 분석이 동작한다는 뜻이 아니다.

키나 `.env` 확인값만으로 분석을 켤 수 없다. 작업·운영 예산의 저장 기반과 접수 연결은 구현했지만 실제 영상 전송·제품 내 동의 화면·작업 실행기 가동·운영 한도 확정·공개 배포는 포함하지 않았다. 기존 가상 화면 시험 명령은 [Gemini 설정](GEMINI_SETUP.md)을 따른다.

## 경로와 인증

| 경로 | 역할 | 정상 응답 |
|---|---|---|
| `POST /api/guides/:guideId/analysis` | 분석 요청 또는 같은 요청 재조회 | 준비된 접수기에서 저장된 활성 실행은 202, 끝난 실행 재조회는 200 |
| `GET /api/guides/:guideId/analysis/:runId` | 저장된 실행 상태와 검증된 결과 조회 | 200 |
| `POST /api/guides/:guideId/analysis/:runId/cancel` | 분석 실행만 취소 | 200 |

- 모두 가이드 소유자의 `Authorization: Bearer <edit token>`이 필요하다. 다른 키·누락·잘못된 키·존재하지 않는 가이드는 동일한 404다. URL query나 프레임용 `asset_token`으로 대신할 수 없다.
- 조회와 취소는 접수기가 없어도 기존 저장 실행에 대해 동작한다. 미디어가 삭제 중이거나 ready가 아니거나 입력 화면이 교체되었으면 오래된 분석을 현재 결과로 반환하지 않는다.
- 분석 라우터의 응답은 오류를 포함해 `Cache-Control: no-store`다. 서버 전체의 시작 전 readiness 503은 기존 공통 응답을 사용한다.

## 요청 본문

`Content-Type: application/json`, 최대 4 KiB, 압축하지 않은 JSON 객체만 받는다.

```json
{
  "runId": "e49a79eb-cbc6-45db-a681-f9ea395b171a",
  "baseDraftRevision": 0,
  "consentVersion": "screen-analysis-v1",
  "externalProcessing": true
}
```

- `runId`: 브라우저가 새 작업마다 만드는 소문자 UUID v4. 위 값은 예시다. 응답 유실 후에는 새 ID를 만들지 말고 기존 ID를 사용한다.
- `baseDraftRevision`: 요청자가 확인한 초안 버전. 첫 요청은 0이며, 정수 0–2,147,483,646만 허용한다.
- 현재 동의 버전과 `externalProcessing: true`를 모두 확인한다. 이 값은 요청자의 동의 표시이며, 개인정보 처리 조건의 적합성이나 Google 무료 등급을 검증한 것이 아니다. 제품 내 설명·동의 UI는 아직 없다.
- 서버가 `provider: gemini`, `model: gemini-3.5-flash-lite`, `promptVersion: showme-gemini-ko-v1`과 현재 입력 화면의 지문을 결정한다. 모델은 앞선 가상 화면 시험에서 성공한 3.5로 명시했다. 일반 Gemini 어댑터의 기본 3.8 모델은 변경하지 않았다.
- 모델·공급자·프롬프트·파일 경로·이미지·API 키를 본문에 넣으면 거절한다. 이번 API는 파일 업로드 경로가 아니다.
- 취소는 본문 없이 보내거나 빈 JSON 객체 `{}`를 보낸다. 임의의 추가 필드는 거절한다.

## 중복·상태·시간 초과

1. 최초 초안과 실행을 동일한 저장소 작업에서 생성한다. 인증 때 읽은 미디어 지문이 저장 시점에도 같아야 한다. 오래된 버전·동시 실행 충돌·교체된 화면이면 일부 초안만 남기지 않는다.
2. 같은 실행 ID와 같은 버전·입력·동의·모델·프롬프트의 재요청은 저장된 실행을 반환한다. 이미 끝난 실행도 새 분석으로 바꾸지 않는다. 같은 ID에 다른 조건을 보내거나 다른 실행이 활성 상태이면 409다.
3. 동시 요청은 HTTP 사전 조회만으로 중복을 막을 수 없다. B3 접수기는 B2 저장소를 사용해 **최초 초안·실행·묶음·예산 예약을 같은 중복 방지 범위**에서 처리한다. PostgreSQL은 전체 중단 제어→전체/가이드 날짜 구간→가이드 잠금 순서다. 잠금을 얻은 뒤 쓰기 직전에 동기식 준비 조건 검사를 다시 통과해야 새 작업을 저장한다.
4. 접수기 응답 대기는 5초다. 시간이 지나면 중단 신호와 `503 ANALYSIS_ADMISSION_TIMEOUT`을 반환한다. 이 시간은 인증·저장소 조회를 포함한 전체 HTTP 제한이 아니다.
5. 시간 초과는 접수 실패가 확정됐다는 뜻이 아니다. 저장 후 응답만 유실됐을 수 있다. 같은 `runId`로 조회하고, 필요하면 동일한 요청을 재전송한다. 조회가 404여도 접수기가 늦게 완료될 수 있으므로 임의로 새 ID를 만들지 않는다. 서버가 자동 재시도·예산 반환을 하지 않는다.

응답은 `{ "run": { ... } }` 형태다. 실행 ID·상태·모델·기준/적용 초안 버전·`cancellable`·`reviewRequired`·검증된 `result`·제한된 `errorCode`·토큰 수·생성/갱신 시각만 반환한다. 원본 파일 위치·프레임 저장 키·편집 키/해시·입력 지문·처리 시도 ID·lease·공급자 원문·추론 내용은 포함하지 않는다.

상태는 `queued`, `running`, `succeeded`, `failed`, `cancelled`다. queued/running에서만 `cancellable`이 참이다. 성공하면 `reviewRequired`가 참이며, **검토 완료·개인정보 없음·게시 가능**을 뜻하지 않는다. 최초 미수정 초안에만 기존 revision 규칙으로 결과를 채택하고, 사람이 수정한 초안은 덮어쓰지 않는다. 재시도 가능 여부를 판단하는 필드는 아직 제공하지 않는다.

취소는 원본·프레임·초안을 삭제하지 않는다. 이미 취소된 실행에 다시 취소해도 성공하고, 성공/실패로 끝난 실행의 취소는 409다. 취소 후 늦은 완료 결과는 저장하지 않는다. **이미 전송된 Google 계산이나 과금의 즉시 중단을 보장하지 않으며**, 실제 worker의 중단 신호 연결은 다음 단계다.

## 실패 응답과 요청 제한

오류 본문은 `{ "error": "고정된 한국어 안내", "code": "제한된 코드" }`다.

| HTTP | 대표 코드 | 의미 |
|---|---|---|
| 400 | `ANALYSIS_INVALID_REQUEST`, `ANALYSIS_CONSENT_REQUIRED` | 형식 또는 동의 확인 필요 |
| 404 | `GUIDE_NOT_FOUND`, `ANALYSIS_NOT_FOUND` | 접근할 가이드/실행 없음 |
| 409 | `ANALYSIS_MEDIA_NOT_READY`, `ANALYSIS_STATE_CHANGED` | 미디어·초안·분석 상태 충돌 |
| 413 / 415 | `ANALYSIS_BODY_TOO_LARGE`, `ANALYSIS_JSON_REQUIRED` | 본문 크기·형식·압축 거절 |
| 429 | `ANALYSIS_RATE_LIMIT` | 해당 경로 요청 속도 제한, `Retry-After` 확인 |
| 429 | `ANALYSIS_BUDGET_LIMIT` | 전체 또는 가이드의 요청/토큰/계산용 금액 한도 부족, 예약/가격표 상세 비노출 |
| 503 | `ANALYSIS_UNAVAILABLE`, `ANALYSIS_ADMISSION_TIMEOUT` | 실행 미준비 또는 접수 확인 지연 |
| 500 | `ANALYSIS_INTERNAL_ERROR` | 내부 처리 실패; 원문 오류 비노출 |

프로세스별·IP별로 요청은 15분당 10회, 조회는 분당 60회, 취소는 분당 30회다. 경로별 제한을 분리해 요청 제한이 조회·취소까지 막지 않게 했다. **분산 한도나 토큰/금액 예산은 아니다.** DB/공급자 오류·인증 헤더·잘못된 JSON 원문을 로그에 남기지 않으며, 5xx는 고정된 이벤트와 코드만 기록한다.

## 다음 단계의 필수 조건

- 운영 DB에서 전체·가이드별 사용 상한, 모델별 최대 사용분 예약과 정산, 동시 재전송의 단일 예약을 검증한다. 현재 계정 없는 구조에서 사람별 한도를 보장하지 않는다. 불확실한 완료·시간 초과 예약은 보수적으로 유지한다.
- 예산 예약·실행 저장·내구성 있는 작업 전달이 함께 성공하거나 함께 거절되도록 만든다. HTTP 응답 뒤 프로세스가 종료되어도 대기 실행을 다시 찾을 수 있어야 한다.
- 별도 AI dispatcher, 제한된 동시 실행, 재시작/lease 복구, 실패 묶음 보존, 취소/삭제 중단을 검증한다. 기존 미디어 큐에 무조건 추가하지 않는다.
- 실제 화면을 외부에 보낼 조건과 제품 내 동의를 정하고, 실행 시에도 권한·현재 입력·동의·예산을 확인한다. 로컬 가상 화면 시험의 무료 등급 확인값이나 하루 10회 파일 한도를 운영 허가로 재사용하지 않는다.
- 실제 PostgreSQL·다중 프로세스 경합·운영 저장소·작업 실행기·무료/유료 조건 검증을 거친 뒤에만 **실제 준비 조건 검증기**를 연결한다. 기본 접수기는 그 전까지 닫혀 있다. 테스트용 준비 보고서를 운영 허가로 사용하지 않는다.

## 검증 범위

초기 Gate 3B-2A HTTP 테스트는 실제 Express 경로와 로컬 JSON 저장소를 사용하되 접수기와 AI 공급자는 시험용이었다. 인증·동의·JSON 제한·동시 중복·조회·완료 결과·취소·삭제 경합·안전한 오류·접수 시간 초과·경로별 요청 제한을 검사했다. MP4/MOV/WebM의 실제 FFmpeg 업로드 회귀 검사에서도 API 미준비 시 초안이 변하지 않는지 확인한다. 아래 초기 수치는 당시 기록이며 최신 검증은 B3 기록을 따른다.

JSON과 PostgreSQL이 공유하는 상태 전이에 원자적 `request` 명령을 추가했다. DB 스키마 변경은 없지만 실제 PostgreSQL 통합·복제본 간 예산 검증을 실행한 것은 아니다. Google 실호출·사용자 영상 전송·브라우저 조작·공개 배포 없이 수행하는 로컬 검증이다.

2026-09-14 `npm run check` 통과: 새 API 테스트 17개를 포함한 processor 171개 + client 4개, **총 175개 테스트**, 타입 검사·processor 빌드·lint·frontend production build 성공. 기존 Vite 설정 로더와 라우트 분류 안내는 남아 있지만 빌드는 성공했다. 업로드 테스트의 이전 “API 미존재 404” 조건은 “유효한 요청도 실행 미준비 503, 초안 변화 없음”으로 갱신했다.

## B3 준비 조건과 당시 검증 — 2026-09-14

- 준비 보고서는 신뢰하는 서버 구성에서만 받는다. 가이드/입력 지문/프레임 수/모델/프롬프트, 승인된 가상 자료, DB·실행기 계약, 프롬프트·schema·대상/문맥을 포함한 입력 토큰 상한, 가격표·한도, 무료 프로젝트/할당량을 대조한다. 실제 확인은 미래의 검증기 책임이며 정해진 문자열을 넣는 것만으로 확인됐다고 간주하지 않는다.
- 보고서는 최대 30초로 제한한다. 저장 직전에도 같은 보고서가 유효한지 동기적으로 확인하고 만료·철회·중단·UTC 날짜 변경·시계 역행 시 쓰지 않는다. 확인 함수가 Promise나 문자열을 반환해도 준비 완료로 처리하지 않는다. 마지막 검사 뒤의 DB/파일 확정 지연까지 외부 조건을 동결하는 것은 아니므로 실행기가 실제 전송 직전에 다시 검증해야 한다.
- 기본은 `free_only`: 유료 fallback을 거절하고 전체 요청/토큰 한도가 확인 보고서의 무료 할당량을 넘지 못한다. 계산용 양수 단가는 결제 승인과 다르다. `paid_capped`는 별도 서버 설정의 승인 ID·프로젝트·양수 금액 상한이 모두 일치해야 한다. 이 유료 경로는 가상 계약 시험만 했으며 실제 지출 정책은 무료만 유지한다.
- 준비 조건/정책 변경·중단 제어·검증기/DB 오류는 제한된 503으로 응답한다. 순수 예산 부족은 429다. 이미 저장된 요청의 재전송·조회·취소는 준비 조건이 꺼져도 유지하며 새 예약/worker 실행을 만들지 않는다. 프로젝트·승인 근거·검증 보고서는 응답/로그/예약에 복사하지 않는다.
- 신규 접수 테스트 **24개**: 기본 차단, 실제 HTTP→원자 예산 저장, 중복 20건, 실행/가이드 한도 경합, 무료/유료 계약, 만료/철회/날짜/중단, 늦은 보고서·응답 유실, 오류 비노출, 동기 검사 강제, PostgreSQL 사전 검사/롤백 경계 모의 시험. 전체 `npm run check`: processor 247 + client 4 = **251개**, 타입·빌드·lint 통과.
- 실제 PostgreSQL·worker·프로젝트 무료 여부·정확한 토큰 상한을 이번에 검증하지 않았다. 추가 migration·환경변수 변경·Google 호출·사용자 자료 전송·UI 변경·푸시·배포는 없다. 다음 B4는 DB에 저장된 대기 작업을 찾아 안전하게 처리·복구하는 실행기다.

## B4-A 저장 연계와 최신 검증 — 2026-09-14

HTTP 경로·본문·응답 DTO는 바꾸지 않았다. 내부 저장소에 대기 작업 조회·단일 소유권 인수·만료 인계를 추가했지만 자동 실행 루프는 없고, 소유권은 외부 전송 허가가 아니다. owner ID/횟수는 서버 내부 원장 호출에만 쓰며 HTTP 본문에 추가할 수 없다.

PostgreSQL 저장소에 migration `0005`와 조회 열 일치 검사가 필요해 접수기 보고서의 미래 DB 계약을 `postgres-0005`로 올렸다. 이전 `postgres-0004` 보고서도 거절한다. 실제 검증기는 여전히 없으므로 기본 POST는 503, 기존 조회/취소 계약은 유지한다. 신규 작업 테스트 24개를 포함해 **총 275개**(processor 271 + client 4), 타입·lint·빌드 통과다. 실제 DB migration/연결·공급자 전송·UI·푸시/배포는 하지 않았다. 다음은 B4-B의 자동 처리·부분 결과 복구이며 [상세 경계](ANALYSIS_EXECUTION_DESIGN.md)를 따른다.
