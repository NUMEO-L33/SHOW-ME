# 게시 작업 원장 — 2026-09-21

기존 계획 E3의 첫 내부 구현이다. **게시 요청 기록·작업 소유권·비공개 준비 상태까지만 구현했으며, 실제 게시 확정/공개 API/버튼/자동 worker는 연결하지 않았다.** 원래 개발 계획의 목표·완료 조건을 변경하지 않았다.

위 범위와 아래 성공 명령 미구현·JSON v7 설명은 원장 단계 당시의 기록이다. 후속 `PUBLICATION_COMMIT.md`에서 별도 원자적 확정 메서드, `succeeded / committed`, 불변 게시본/활성 참조, migration 0015·JSON v8을 추가했다. 준비 완료 자체는 여전히 게시 성공이 아니며 제품 API/공개 기능은 미연결이다. 최신 검증은 후속 문서를 따른다.

## 구현 계약

- `publication_jobs`에 요청 UUID, 저장 revision, 미디어·개인정보 확인 지문, 원본 공유 옵션, 불변 문구/정렬/보이는 클릭 표시 snapshot을 저장한다. 제작 의도, 원본 파일명·키, 개인정보 후보/확인 기록, 편집 자격 증명은 content에 복사하지 않는다. 이 내부 원장 자체는 공개 DTO가 아니다.
- 요청 행과 `guide_assets`의 출력 키 정리 소유권을 **같은 부모 가이드 잠금·같은 트랜잭션**으로 저장한다. JSON도 한 번의 원자적 파일 교체다. 한쪽만 저장되면 롤백한다. PostgreSQL의 조용히 무시된 쓰기도 성공으로 응답하지 않는다.
- 같은 요청 UUID/지문은 기존 작업 조회로 처리하고 쓰거나 다시 실행하지 않는다. 취소/실패 후 재전송도 작업을 되살리지 않는다. revision·입력·확인 지문·원본 옵션 중 하나라도 다르면 충돌이다. UUID는 가이드별로 격리된다.
- 원본 공유는 현재 `false`만 접수한다. 초안 저장과 개인정보 확인이 완료되고 현재 처리 계획과 일치해야 예약한다. 내부 상한은 가이드당 미종료 작업 1개, 전체 요청 이력 32개, 기존 자산 묶음 4개다. 이력을 몰래 버려 idempotency를 잃지 않으며, 제품 개방 전 사용자 안내/상한 정책을 점검해야 한다.
- claim은 job version을 비교하고, 독립된 120초 lease와 자산 writer 소유권을 한 번에 설정한다. 같은 claim을 재사용하거나 기존 키로 새 writer가 작업을 이어받지 않는다. PostgreSQL은 부모 잠금을 얻은 **후** DB 시각을 읽는다. 메서드의 선택적 `now`는 신뢰된 테스트용이며 HTTP 입력으로 받으면 안 된다.
- 모든 처리본 receipt가 준비된 뒤에도 현재 초안/확인/이미지 계획과 원래 snapshot을 다시 검사한다. 통과 상태는 `running / assets-ready`일 뿐 `succeeded` 또는 게시 완료가 아니다. 아직 성공 명령/공개 slug/공개 참조는 없다.
- 후속 `preparePublicationAssets`가 실제 E2 엔진에 연결됐다. `check-writer`로 처리 중 현재 소유권을 확인하고, `complete-assets`로 이미지 receipt와 job 준비 상태를 함께 저장한다. 정확한 자기 lease만 허용하는 `abandon`은 취소·응답 유실 후 정리에 쓰며 원격 쓰기 종료를 추정하지 않는다. 자세한 계약과 후속 검증은 `PUBLICATION_PREPARATION.md`에 별도로 기록한다.
- 수정 또는 삭제가 먼저 반영되면 준비 확정을 거부하고 자산을 cleanup으로 보낸다. 취소는 미종료 작업을 멈추고 늦은 writer의 준비 확정을 막는다. 초안과 기존 미디어 보존 시각은 게시 작업 명령이 갱신하지 않는다.
- 대기/만료 작업을 인덱스로 제한 조회하는 `listPublicationWork`를 제공한다. 재접속 후에도 조회·만료 취소할 수 있지만 **자동 복구 루프를 시작한 것은 아니다.**
- 후속 `PUBLICATION_RECOVERY.md`에는 만료/정리 후보의 batch UUID 순환 조회와 명시적 내부 유지보수 루프를 구현했다. 이전 `listPublicationWork`는 그대로이며 새 `listPublicationRecovery`가 종류별 최대 20개를 반환한다. 제품 시작 경로에서는 여전히 실행하지 않는다.

## 중단·삭제의 한계

lease 만료는 원격 저장이 끝났다는 증거가 아니다. 복구 명령은 작업을 실패 처리하고 자산 원장을 cleanup으로 전환하되 `writerSettled=false`를 그대로 보존한다. 새 writer/키 재사용/임의 성공 판정은 없다. 실제 writer가 종료됐음을 확인할 수 없는 원격 쓰기는 여전히 삭제 완료를 막는다. 이 불확실 상태를 해소하는 운영 절차와 늦은 원격 commit 검증은 남아 있다.

기존 전체 삭제 경로가 자산 정리를 완료해야 가이드가 지워진다. `guide_assets`의 RESTRICT가 그 순서를 보호하고, 정리 완료 후 게시 요청의 비공개 문구/이력은 부모와 함께 지운다. 이 단계의 취소는 **게시 작업 취소**이며 아직 공개 링크 철회 기능은 아니다.

## 저장 형식 / 배포

- migration `0014_publication_jobs.sql` 추가. 기존 SQL은 수정하지 않았다. 상태·소유 가이드/배치·작업 조회 시각의 projection CHECK와 큐 인덱스가 있다.
- JSON v7. v1–v6을 읽을 때 디스크를 다시 쓰지 않고 다음 저장 때 올린다. v6의 기존 자산 원장을 보존하며, 구버전에 새 게시 필드가 섞여 있으면 거절한다. 구형 바이너리로 단순 롤백하면 안 된다.
- 새 runtime 역할 생성 코드에는 `publication_jobs` CRUD를 포함한다. **기존 역할/운영 DB는 변경하지 않았다.** Replit 반영 전 0013/0014 migration 및 기존 실행 역할의 두 새 테이블 권한 검증이 별도로 필요하다.
- 현재 제품 HTTP에 게시 접수/조회 경로가 없고 일반 서버가 작업을 자동 생성·claim하지 않는다. 내부 Repository 메서드는 소유자 인증을 대신하지 않는다.

## 검증 기록

- 새 일반 검사 12개: 요청/자산 동시 저장, allowlist snapshot, 재접속/재전송, 변경된 요청 충돌, 12개 동시 claim, 수정/취소/삭제 경합, 비공개 준비 상태, 정확한 lease 경계, 불확실 writer 보존, v6 업그레이드, 이력 상한, 제품 HTTP 비노출.
- 실제 PostgreSQL 16.15 **111개 통과**, 실패·취소·생략 0, 종료 코드 0. 새 5개는 독립 연결의 동시 요청/claim, 저장 실패/조용히 무시된 쓰기 롤백, 편집 후 준비 거절/삭제 순서, 재접속·만료 발견·projection 거절, 실제 부모 잠금 대기 뒤 DB 시각을 검사한다. 0000–0014 migration 적용/재실행도 통과했다.
- 일회용 컨테이너 `showme-b5-f2b0877d1fd44e23b02154842b678281`은 `postgres_fixture_removed`로 정리를 확인했다. .env/운영 DB/개인 영상/실제 외부 AI를 쓰지 않았다. 이 새 DB 검사의 이미지 receipt는 합성 값으로 저장 경계만 검사하며 실제 E2 렌더링 연결 완료를 주장하지 않는다.
- 첫 일반 전체 실행에서 기존 DB probe의 30ms 타이밍 테스트가 파일 읽기 중 제한시간에 도달하여 실패했다(서버 724/725). 제품 제한은 바꾸지 않고 테스트의 시간·시작 시점을 명시적으로 제어했으며, DB 시작 전 만료 검사도 추가했다. 관련 31개와 최종 테스트 타입 검사는 통과했다. 최초 새 HTTP 검사의 잘못된 비 UUID fixture도 실제 인증 형식에 맞춰 수정했다.
- 서버 제품/테스트 타입 검사와 빌드 통과. 초기 빌드는 샌드박스의 상위 디렉터리 접근 제한으로 실패했고, 같은 빌드를 권한 환경에서 재검사해 통과했다. 새 UI/브라우저 검증은 없다.
- 최종 일반 전체 재실행은 **924개 통과**(이관 99 / 서버 726 / 클라이언트 99), 실패·취소·생략 0, 종료 코드 0이다. 이전 실패 실행과 구분한다. DB 검사 이후 제품 코드는 바뀌지 않았고 테스트 시간 제어/문서만 보완했다. 이번 변경은 로컬 작업본에 저장했으며 커밋/푸시와 Replit 반영은 아직 하지 않았다.
