# B5 후속: DB 운영 기록을 실행 전 근거에 연결

2026-09-19. [저장·철회 단계](ANALYSIS_OPERATIONS_STORE.md)의 다음 내부 구현이다. 원본 요구 MD는 바꾸지 않았다. **실행 전 근거 연결부 구현이지 실제 운영 승인 발급이나 제품 AI 활성화가 아니다.**

## 이번 구현

`PostgresAnalysisOperationsStore.observe`는 한 번의 읽기 전용 repeatable-read 트랜잭션에서 DB 시각·전역 중지 상태·해당 배포의 최신 운영 기록을 함께 읽는다. 동시에 다른 연결이 철회해도 서로 다른 시점의 제어 상태와 기록을 섞지 않는다. 상태가 없거나 손상되면 자동 수리하지 않으며 중지를 해제하지 않는다. 결과는 `authorizesAnalysis:false`다.

`OperationsReviewEvidenceSource`는 이 관측을 기존 `EvidenceAnalysisReadiness.operations` 계약으로 변환한다.

- 매 `inspect`마다 DB를 새로 조회한다. HTTP/환경변수의 임의 승인 JSON이나 과거 영수증을 준비 완료로 바꾸지 않는다.
- `approved` 상태·다섯 확인 항목·미만료·DB 중지 해제 상태가 모두 필요하다. 배포·프로젝트·키 버전·저장소를 서버의 명시된 바인딩과 대조한다.
- 운영자의 원래 관측·작성·만료 시각을 유지한다. 조회 증거는 최대 30초이고, DB 조회 시작 전 시각보다 늦게 시작한 것으로 꾸미지 않는다. 운영 기록 만료를 넘지 않으며 DB 시각 차이·날짜 경계·시간 역행을 거절한다.
- 한 인스턴스의 DB 조회는 한 번에 하나, 로컬 영수증은 최대 64개다. 기본 기한은 4초다. 취소/실패/명시적 `clear()` 뒤 늦은 결과는 발급하지 않으며, 취소를 무시한 작업은 실제 종료 전까지 슬롯을 점유한다.
- 영수증 전체를 비교하고 반환값을 복제한다. 최신 버전이나 내용의 변경, DB 조회 실패를 관측하면 이전 로컬 영수증을 무효화한다. 원문 오류는 노출하지 않는다.

## 반드시 구분할 것: 로컬 검사와 프로세스 간 차단

동기식 `isCurrent`는 **이 프로세스가 발급·관측한 기록의 로컬 검사**다. 다른 프로세스의 DB 변경을 네트워크 조회 없이 즉시 감지한다고 주장하지 않는다. 다음 조회 전에는 30초 미만의 기존 영수증이 로컬 검사에 통과할 수 있다.

따라서 이 소스는 반드시 기존 DB 접수·계수·생성의 **공통 중지 상태 및 최종 전송 잠금**과 함께 사용해야 한다. 운영 기록 변경/철회는 같은 제어 행을 잠그고 `halted:true`를 원자적으로 저장한다. 변경이 커밋된 뒤 시작하려는 요청은 캐시가 남아 있어도 DB 검사에서 막힌다. 이미 먼저 시작한 외부 요청을 회수하는 것은 아니다.

실제 PostgreSQL 검사에서 독립 연결로 철회한 후 로컬 `isCurrent`가 아직 참인 상황을 의도적으로 만들었다. 그 상태에서도 실제 저장소의 생성 시작 콜백은 **0회**였고 새 근거 조회는 실패하며 로컬 영수증도 무효화됐다. 알림 수신이나 항상 참인 검증기로 이 검사를 대체하지 않았다.

공통 중지를 수동 SQL로 해제하는 것은 제품 경로에 없다. 검사에서만 기존 실행 중인 환경을 재현하기 위해 일회용 DB 상태를 만들었다. 자동 재개·관리자 HTTP·서버 시작 등록은 추가하지 않았다.

## 입력량 상한 조사 — 해결 완료 아님

2026-09-19 공식 문서를 다시 읽었으며 계정 접속·키 사용·영상 전송·AI 호출은 없었다.

- [미디어 해상도 문서](https://ai.google.dev/gemini-api/docs/media-resolution)는 해상도에 따른 미디어 토큰 배분과 이미지 권장 최대값을 설명하지만, 모델군별 표는 근삿값이라고 명시한다. 이것만으로 시스템 지시·응답 스키마·메타데이터·모든 이미지·요청 부가 구조를 합친 정확한 요청의 상한을 증명하지 않았다.
- [계수 API](https://ai.google.dev/api/tokens)는 입력을 토크나이저로 계산하며 `generateContentRequest`로 시스템 지시 등을 포함한 전체 요청을 받을 수 있다. 즉, 현재 코드의 계수도 자료를 외부로 보내는 요청이다. 그 응답을 이미 보낸 **같은 계수 요청의 사전 승인**으로 사용할 수 없다.
- [현재 모델 문서](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite)의 입력 컨텍스트 한도 1,048,576은 특정 ShowMe 요청이 그보다 작은 운영 예산/분당 한도 안에 들어간다는 증명이 아니다. 이를 임의의 안전 상한이나 과거 합성 실측 7,199의 재승인으로 사용하지 않았다.

현재 `auditGeminiInput().verifiedInputTokenUpperBound`는 계속 `null`이다. 계수 호출 전에도 별도 검토된 전체 상한을 요구하는 기존 보호를 완화하지 않았다.

**제안(승인 전 미구현):** 승인된 비개인 합성 자료의 계수 단계를 별도 허가로 분리하고 요청 횟수·동시성·자료 크기·시간·목적지·중복/철회를 제한한다. 계수 성공 후 한도 안의 정확한 요청만 생성 단계로 넘긴다. 이 방식은 계수 자체의 사전 토큰량 보증을 대체하므로 단순 리팩터링이 아닌 설계 변경이다. 일반 ‘진행’ 요청으로 이 차이를 묵시 승인한 것으로 처리하지 않는다. 실제 외부 호출과 개인 영상 전송/활성화 권한은 별개다.

## 검증과 상태

- 관련 단독 검사 54개 및 API 제품/테스트 TypeScript 검사, 서버 빌드 통과.
- 최초 단독 검사에서 테스트용 비교 함수가 객체의 키 순서까지 문자열 비교하여 통합 검사를 거절했다. 실제 구조 동등성 비교로 고친 뒤 54개를 통과했다. 제품 안전 조건은 완화하지 않았다.
- 실제 PostgreSQL 16.15 검사 **83개 통과, 실패·취소·생략 0**. 새 3개는 독립 연결 철회 후 전송 차단, 동시 철회의 일관된 읽기 스냅샷, 읽기 전용 역할·손상/누락 상태의 무수정 거절을 검증한다.
- 일반 전체 회귀 **803개(이관 91 + 서버 626 + 클라이언트 86)** 통과, 실패·취소·생략 0, 종료 코드 0. 기존 격리 실행기로 앱 환경/비밀값을 제외하고 기존 테스트용 FFmpeg/ffprobe만 사용했다. 실제 PostgreSQL 83개는 별도 검사다.
- 사용자의 기존 Docker 실행 승인 범위에서 루프백·임시 메모리 DB만 사용했다. 검사 컨테이너와 DB의 자동 정리를 확인했다. Replit DB/Storage, 개인 영상, 실제 AI 전송은 사용하지 않았다.

새 소스는 서버 시작/HTTP 경로에 등록하지 않았다. 운영자 인증 진입점·최소 DB 권한 구성, 실제 운영 확인 내용, 런타임/승인 입력 소스, 입력 상한과 계수 허가 설계가 남아 있다. 로컬 작업본만 수정했고 커밋/푸시·Replit 반영·AI 활성화는 하지 않았다.
