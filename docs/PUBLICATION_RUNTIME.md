# 게시 실행기와 서버 시작·종료 연결 — 2026-09-21

2026-09-22 후속 편집기/공개 뷰어 연결은 `PUBLICATION_UI.md`를 따른다. 기본 bootstrap 활성화 및 Replit 실환경 검증은 여전히 별도다.

기존 E3의 요청 원장 → 실제 가림 처리본 준비 → 원자적 게시 확정 → 철회/만료 정리를 `DurablePublicationRuntime`으로 연결했다. 원래 개발 MD의 목표·완료 조건은 변경하지 않았다. 실행기는 새로운 게시 요청을 스스로 만들지 않으며, 이미 명시적으로 접수·저장된 요청만 처리한다.

## 실행과 재시작

- 생성/import만으로 시작하지 않는다. 명시적인 `start()`가 예약 실행을 시작하고, 내부 `tick()`은 한 회차를 직접 검사하는 진입점이다. HTTP에는 tick/claim/lease/commit 경로를 노출하지 않는다.
- 매 회차에 기존 만료/철회 자산 정리를 수행하고 queued 작업 하나를 찾아 처리한다. 단계는 `preparePublicationAssets` → 이번 호출이 받은 writer lease로 `commitPublication`이다. 이미지 검증·현재 편집/확인·철회/삭제·만료 검사는 기존 저장 계층에서 다시 적용한다.
- queued 발견은 batch UUID 순서의 keyset cursor다. 실패한 첫 작업 때문에 이후 가이드가 영구적으로 가려지지 않으며 끝에 도달하면 다시 처음으로 순환한다. JSON/실제 PostgreSQL에서 동일한 투영 필드와 순서를 사용한다. 추가 migration은 없다.
- 이미 running/assets-ready인 과거 작업의 lease를 읽어서 준비/확정을 재개하지 않는다. 유효 lease는 건드리지 않고, 만료 뒤 기존 복구 루프가 실패·정리로 전환한다. 새 실행기는 알려지지 않은 원격 쓰기가 종료됐다고 추정하지 않는다.
- 재시작 때 아직 queued인 명시적 요청은 발견해 처리할 수 있다. 이미지 저장이 이미 시작된 작업을 재업로드하는 것과 구분한다. 실행기 중지는 공유 철회가 아니다. 기존 게시 링크를 철회하려면 별도 소유자 API를 사용한다.
- 최종 commit 응답만 유실된 경우 같은 요청/lease의 성공 여부를 읽어 확인한다. 재렌더·재업로드·추가 commit은 하지 않는다. 상태 확인도 실패하면 과거 running 기록을 남겨 만료 복구로 넘긴다.
- 확정 실패는 이전 공개 snapshot을 유지한다. 이번 호출이 실제로 준비한 lease에 한해서 abandon하고 해당 실패 처리본만 정리한다. 성공한 현재 처리본은 cleanup 보호 규칙을 따른다.

## 한도와 종료

- 변환은 기존 공통 private asset session의 프로세스당 1개 한도를 공유한다. 서로 다른 서버에서는 저장소의 job version/lease 비교로 같은 작업의 중복 claim을 막는다. 프로세스 전체/다중 서버의 부하 검증을 대신하는 것은 아니다.
- 기본 회차 제한 120초, 이미지 준비 제한 100초, 정리 회차 최대 30초다. 평상시 5초 간격으로 찾고 성공 후에는 다음 작업을 바로 찾는다. 실패 시 간격을 늘려 최대 60초까지 기다린다.
- 제한시간 뒤에도 실제 DB/저장소 작업이 끝나지 않으면 해당 실행 슬롯을 계속 점유한다. 반복 tick이 추가 조회/변환을 무한히 쌓지 않으며 `pendingIO`로 불확실성을 표시한다. 정상 진행 중인 정리 회차만으로 새 접수를 막지는 않는다.
- 접수는 입력을 먼저 복사·검증하고 한 번만 DB에 전달한다. 최대 16개 접수 I/O와 기본 5초 제한을 둔다. HTTP 응답을 잃거나 취소되더라도 이미 DB에 저장된 요청은 같은 ID로 복구한다. timeout만으로 실제 DB 쓰기가 취소됐다고 가정하지 않는다.
- `stop()`은 즉시 신규 접수·다음 회차를 차단하고 변환/정리에 취소 신호를 보낸다. 정상적인 정리 완료를 기본 1초, 최대 5초의 한도 안에서 기다린다. 끝나지 않은 I/O는 `pendingIO:true`로 남기며 임의로 writer 종료/삭제 완료를 기록하지 않는다.
- DB commit이 이미 발행된 뒤 종료됐다면 그 트랜잭션 결과가 나중에 확정될 수 있다. HTTP/서버 종료를 이미 발행한 트랜잭션의 롤백 보장으로 설명하지 않는다. 공유 철회가 먼저 확정된 경우에는 저장 계층의 잠금/버전 비교가 늦은 게시를 차단한다.

## 제품 lifecycle 경계

`startProcessor(config, {createPublication})`의 선택적인 신뢰된 factory를 연결했다. API와 실행기는 정확히 같은 repository/storage 인스턴스를 사용해야 하며 다르면 중단한다. DB/저장소/미디어 시작 검증을 통과한 뒤에만 시작하고, 서버 종료/시작 실패 때 stop을 호출한다. AI와 게시 접수 게이트는 어느 한 실행기의 종료 대기가 길어도 둘 다 즉시 닫는다.

종료 시 미완료 I/O가 남으면 lifecycle은 `PUBLICATION_STOP_PENDING`을 보고하며 정상 완료로 숨기지 않는다. 다른 서버 자원은 계속 정리한다. DB 종료/프로세스 강제 종료 뒤 남은 불확실 writer 기록은 자동으로 지우지 않는다.

**기본 `startConfiguredProcessor`는 이 factory를 주입하지 않는다.** 운영 환경 변수나 UI 버튼만으로 켜는 우회 경로를 추가하지 않았다. 선택적 연결 코드와 합성 시험은 완료하되 실제 공개 기능 활성화, 화면 연결, Replit 반영은 별개다. `.env`·키·개인 영상·실제 AI를 사용하지 않는다.

## 검증과 남은 작업

일반 검사는 저장 후 재접속, 실제 합성 PNG 준비/확정, 두 실행기의 중복 방지, HTTP 접수→예약 실행→공개 처리본→철회/정리, 중간 편집/삭제/철회, commit 응답 유실, 실패한 재게시, 과거 assets-ready lease 미재사용, 중단 중 늦은 put, 미종료 DB 조회/접수 한도, 입력 복사, 시작/종료 게이트와 시작 실패를 확인한다. 실제 DB에는 독립 repository의 발견/처리/확정과 commit 트리거 실패 시 이전 링크 보존·실패 자산 정리를 추가했다. 최종 전체 수치는 `SESSION_CHECKPOINT.md`에 기록한다.

처음 집중 검사에서 정상 정리 중 접수를 막던 게이트와 종료 직후 아직 정리 중인 임시 폴더 문제가 드러났다. 정상 처리와 timeout 뒤 미완료 I/O를 구분하고 제한된 종료 대기를 추가했다. 새 재게시 fixture의 잘못된 요청 필드도 바로잡았다. 마지막 점검에서는 저장 실패와 동시에 진행 중인 DB monitor가 있을 때에도 실제 monitor 종료 전에는 공통 writer 슬롯을 반환하지 않도록 보완하고, 미응답 monitor와 늦은 정리의 회귀 검사를 추가했다. 후속 일반 검사에서 기존 API 시간 제한 검사 하나의 실패를 관측했으며, 상세 출력이 남지 않아 원인을 단정하지 않는다. 해당 테스트의 저장 완료 시각 가정은 완료 신호+모의 시각으로 바꾸었고 API/실행기 34개를 다시 통과했다. 최종 일반 전체 1,031개 통과 후 Docker를 재연결하고 직전 미확인 컨테이너가 없음을 확인했다. 새 로컬 일회용 PostgreSQL 16.15에서 최종 코드의 135개 검사(migration 0000–0017)를 모두 통과했고 시험 DB 정리도 확인했다. Replit 운영 DB 검증을 의미하지 않는다.

다음은 편집기의 게시·진행 상태·공유 중지와 공개 뷰어 연결, 합성 브라우저 검사다. 이어 Replit의 migration·기존 실행 역할·Storage 및 제한된 합성 실환경 검증, 불확실 원격 쓰기 해소 절차가 필요하다. Windows 화면 빌드 의존성 문제는 앞선 기록의 미완료 상태이며 이번 서버 작업에서 설정을 바꾸지 않았다. E3 전체/운영 배포 완료로 표시하지 않는다.
