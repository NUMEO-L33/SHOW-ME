# B5 후속: 승인된 합성 자료의 계수와 생성 허가 분리

2026-09-19. [운영 기록 연결 단계의 제안](ANALYSIS_OPERATIONS_SOURCE.md)에 대한 사용자 승인 후 구현했다. 원본 요구 MD와 앞 단계의 당시 기록은 그대로 두며, 이 문서에 설계 변경과 검증 결과를 추가한다.

## 결정과 범위

기존 방식은 `countTokens`를 보내기 전에도 전체 요청의 검토된 토큰 상한을 요구했다. 새 방식은 **명시적으로 승인된 비개인 합성 자료만** 요청 횟수·크기·시간 제한 아래 먼저 계산하고, 그 정확한 요청의 측정값이 승인 한도 이내일 때만 생성을 허용한다.

이는 계수 요청 자체의 **사전 토큰 상한 보증을 포기하는 설계 변경**이다. 크기를 토큰량으로 환산하거나 과거 실측을 현재 요청의 증명으로 쓰지 않는다. `auditGeminiInput().verifiedInputTokenUpperBound`는 여전히 `null`이다. 계산 요청도 이미지가 포함되는 외부 요청이므로 실제 실행 승인은 별개다.

이번 승인은 내부 구현·합성 검사에만 적용했다. 개인 영상의 외부 전송, 실제 AI 호출, 제품 활성화, 유료 전환, 키/계정 변경, Replit 배포는 하지 않았다.

## 구현

- `approved-countable-input`이라는 별도 승인 종류가 `inputTokenLimit`과 `countPolicy`를 명시해야 한다. 기존 `reviewed-analysis-input` 승인은 여전히 검토된 상한을 요구한다. 둘을 섞거나 기존 검사가 실패했을 때 새 방식으로 자동 전환하지 않는다.
- 승인 범위는 `approved_synthetic`, 지출 모드는 `free_only`로 제한한다. 이 문자열만으로 합성 자료나 무료 운영이 증명되는 것은 아니다. 신뢰할 수 있는 입력 승인 발급부와 현재 운영 기록이 필요하며, 파일명으로 합성 여부를 판단하지 않는다.
- 실행기는 새 방식에서 실제 계수 단계를 필수로 요구한다. 단순 오프라인 측정값 조회만으로 건너뛸 수 없다. 정확한 이미지 바이트·순서·메타데이터·시스템 지시·스키마가 포함된 요청을 계산하고, 생성 직전에도 같은 요청인지 검사한다.
- 계수는 기존 DB의 예약 → 공통 요청 한도 → 전송 잠금 → 단일 호출 → 정산 경로를 사용한다. 동의/철회·취소·승인 만료·전역 중지 검사는 유지한다. 목적지는 고정되어 있고 리다이렉트와 숨은 재시도는 허용하지 않는다.

### 애플리케이션 제한

다음은 공급자가 보증한 토큰량이 아니라 이 앱이 정한 최대치다. 승인자는 크기 제한을 더 낮출 수 있다.

| 항목 | 최대치 |
| --- | --- |
| 한 요청의 이미지 | 문맥 이미지를 포함하여 6장 |
| 이미지 하나 | 2 MiB |
| 이미지 바이트 합계 | 12 MiB |
| 전체 직렬화 요청 | 18 MiB, 프롬프트·스키마·메타데이터·base64·외곽 구조 포함 |
| 계수 작업 대기 | 20초, 테스트/내부 설정으로 단축 가능 |
| 같은 영속 요청 슬롯의 계수 전송 | 1회, 계수 재시도 없음 |

기존 전체 입력 한도는 24프레임/6배치다. 각 배치의 최초 생성 슬롯과 기존 정책상 허용되는 두 번째 생성 슬롯에 각각 한 번의 계수가 가능하므로 구조상 최대 12개 계수 슬롯이다. 이는 계수 실패를 12번 재시도한다는 뜻이 아니며, 실제 요청은 공통 일일/분당 요청 제한과 예산 잔량에도 묶인다. 취소를 무시하는 비동기 작업은 실제 종료 전까지 로컬 실행 슬롯을 점유하고 늦게 도착한 측정값을 발급하지 않는다. 제한시간은 이미 전송된 요청을 원격에서 회수한다는 보증이 아니다.

## 예산 기록의 의미

새 기록에는 `inputAccounting: "acceptance-allowance"`를 저장하고 승인 바인딩 해시에 포함한다. 과거 기록은 이 필드 없이 그대로 읽는다. 요청 슬롯 키는 바꾸지 않아 모드를 바꾸어 같은 슬롯을 다시 전송할 수 없다. 기존 JSON 기록 구조를 재사용하므로 이 변경만을 위한 DB 마이그레이션은 추가하지 않았다.

새 방식의 예약 입력 토큰량은 **수락/회계용 배정량이지 첫 계수 요청의 증명된 상한이 아니다.** 기존 내부 열 이름에 `inputTokenBound`가 있어도 새 모드의 의미는 같다. 정확한 토큰량을 아직 모르므로 첫 계산 요청이 공급자의 실제 토큰 제한/배정량을 넘을 가능성은 남는다.

- 알려진 계수 결과가 운영 예산의 요청당 입력 배정량을 넘으면 실제 토큰 결과를 보존하고 `overrun` 및 전역 중지를 기록한다. 생성은 하지 않는다. 기존 회계 합계는 예약 최대값을 유지하며 초과 실측은 사용량 필드에 남는다. 이는 이미 발생한 초과를 되돌리는 기능이 아니다.
- 결과가 더 작은 입력 승인 한도만 넘으면 측정 성공으로 발급하지 않고 생성을 막는다.
- 응답 실패/불명확한 결과는 `uncertain`으로 최대 예약량을 유지한다. 실제 사용량이나 비용을 0으로 간주하거나 자동 재전송하지 않는다.
- 비용 기록은 기존 입력 단가를 사용하는 회계용 추정치이며 실제 청구서나 무료 보증이 아니다. 생성 응답의 실제 토큰 사용량도 사전 계수와 다를 수 있으며 기존 생성 정산/초과 중지가 계속 적용된다.

## 검증

- 전체 일반 회귀 **814개(이관 91 + 서버 637 + 클라이언트 86)** 통과. 실패·취소·생략 0, 종료 코드 0. 기존 격리 실행기로 앱 환경과 `.env`를 제외했다.
- 실제 임시 PostgreSQL 검사 **84개** 통과. 실패·취소·생략 0. 새 통합 검사는 별도 사전 상한 검증기 없이 성공 시에만 계수 → 생성으로 진행하며, 초과·취소·HTTP 실패 시 생성/중복 전송이 없는지 확인한다. 재접속 후 새 회계 의미 표기도 보존된다. 외부 HTTP 응답은 모두 테스트 대역이다.
- API 제품/테스트 TypeScript 검사와 서버 빌드 통과.
- 검사 중 요청 크기 위반이 일반 오류로 분류되던 문제를 발견해 실행기의 종료 가능한 입력 오류로 분류했다. 크기 검사를 완화하지 않았다.
- 사용자가 실행한 Docker의 일회용 루프백·메모리 DB만 사용했고 검사 컨테이너/DB 정리를 확인했다. Replit DB/Storage, 개인 영상, 실제 AI 계정은 사용하지 않았다.

## 현재 상태와 남은 일

로컬 작업본에서 구현/검증을 마쳤다. 커밋·푸시·서버 시작 등록·제품 AI 활성화는 하지 않았다. 기존 승인 이미지 로더와 바이트/해시 검사는 실제 구성에서도 필수다.

다음은 실제 런타임과 승인된 합성 입력의 근거 발급부 연결이다. 그 뒤 운영자 인증/최소 DB 권한 구성과 실제 운영 확인 기록을 연결해야 한다. 제품 시작 등록이나 실제 외부 합성 호출은 이 문서의 테스트 통과만으로 승인되지 않는다. 개인 영상 외부 전송은 계속 허용하지 않는다.
