# B5-B3b4 — 입력량 계산 요청의 별도 원장

갱신일: 2026-09-15 · **계산 요청의 저장·정산과 실제 DB 검증 완료. 실제 계수 실행기/자동 분석은 미연결.**

위 상태와 아래 내용은 B5-B3b4 당시 기록이다. 후속 B5-B3b5에서 `0010` 일회용 전송·계산 실행기·실측/생성·내부 복구 연결을 구현했다. 운영 자동 시작은 계속 꺼져 있다. [최신 실행 범위](B5_COUNT_EXECUTION.md).

## 구현한 것

`countTokens`를 `generateContent`와 다른 작업으로 기록하는 PostgreSQL 원장 `analysis_count_attempts`와 migration `0009`를 추가했다. 생성 요청의 기존 원장/재시도 차수를 계산 호출용으로 재해석하지 않는다.

- `reserve`: 계산 1회의 최대분을 **기존 전체/가이드별 UTC 일일 예산 두 곳**에 동시에 추가 예약한다. 별도 한도를 만들어 원래 한도를 우회하지 않는다. 생성 예약 뒤 남은 여유가 없으면 계산을 거절한다.
- `sending`: 계산 원장의 상태 변경과 **공유 프로젝트/모델 공급자 한도 차감**을 한 DB 확정으로 묶는다. 둘 중 하나라도 실패하면 모두 롤백한다. 확정 응답을 잃어도 같은 전송 기록을 다시 발급하지 않는다.
- `settle`: 확인된 입력량만 한 번 정산하고, 요청 1회는 유지한다. 출력은 0이다. 응답 유실/불확실 실패는 최대분을 보존하고 뒤늦은 확정 수치는 원래 날짜에만 정산한다.
- `release`: 아직 `reserved`인 계산만 반환한다. `sending` 이후에는 반환하지 않는다. 반환된 슬롯도 같은 키로 재사용하지 못한다.
- `recover`: 취소·삭제·소유권 만료/변경·날짜 변경 뒤 미전송은 반환하고, 전송 가능성이 있으면 `uncertain`으로 보존한다. 처리 중인 정상 소유권의 기록을 임의로 회수하지 않는다.
- 측정값이 입력 상한을 초과하면 원장의 초과 기록과 **기존 전체 분석 중단 상태**를 함께 확정한다. 재시작·삭제·다음 날짜로 이 중단을 자동 해제하지 않는다.

## 식별·중복·복구 규칙

계산의 고유 키는 `countTokens` 전용 구분자 + 가이드 + 실행 + 묶음 + 대응 생성 슬롯으로 결정한다. 소유권·임의 전송 ID·날짜·프로젝트/승인이 바뀌어도 같은 슬롯에 새 계산 기록을 만들 수 없다. 실제 프로젝트·승인·전체 요청/manifest 지문·모델·지침은 별도 해시로 묶어 바뀐 입력의 재사용도 차단한다.

`generationOrdinal=1`은 **기존 생성 0차에 저장된 허용 5xx 근거**가 있을 때만 사용한다. 계산 자체의 오류는 생성 재시도 자격을 만들지 않으며 계산 자동 재시도는 없다. 한 생성 슬롯당 계산은 최대 한 번이다. 이미 생성 전송이 시작됐거나 묶음이 완료됐으면 새 계산을 예약하지 않는다.

저장소가 다시 열려도 같은 원장을 읽는다. `listPendingAnalysisCounts`는 기본 20개/최대 50개를 고유 키 커서로 조회하는 내부 복구 기능이다. 실제 복구 루프의 서버 자동 시작 연결은 아직 없다. 복구가 늦더라도 미정산 최대분이 예산에서 빠지지 않는다.

## 예산 수치와 실제 청구를 구분한다

`totalTokens`는 입력의 토큰 수이지 청구서나 결제 승인 증거가 아니다. Google은 토큰 계산을 별도 `models.countTokens` 요청으로 정의한다. [공식 요청·응답 계약](https://ai.google.dev/api/tokens)

이번 내부 예산은 보수적으로 계산 입력도 집계한다. 계산용 `costMicrousd`는 **원래 예약 정책의 입력 단가로 환산한 회계용 가정값**이며 실제 계산 API 요금이라고 표시하지 않는다. 출력 단가/출력 토큰은 더하지 않고 각 요청의 환산 금액을 정수로 올림한다. 무료 등급·실제 단가·비용 권한을 이 값으로 증명하지 않는다.

공급자 요청/입력 한도도 계산과 생성을 같은 보수적 풀에서 차감하고 정산으로 돌려주지 않는다. 이는 계산 API의 실제 공급자 한도가 생성과 동일하다는 주장이 아니다. 실제 계수 연결 전에 해당 endpoint의 적용 한도와 외부 호출자 포함 범위를 확인해야 한다.

## 저장·호환성 경계

- 모든 변경은 기존 `global control → 원래 global-day → guide-day → guide` 잠금 순서를 따른다. 전송 상태·공급자 차감·일일 예산·중단 상태는 필요한 변경을 한 번에 확정한다.
- 기록에는 원본/이미지/지침/키/승인 원문을 저장하지 않는다. 가이드·실행·소유권 식별자, 해시, 날짜·수치만 남긴다. 가이드 삭제로 계산 사용량이 초기화되지 않는다.
- 생성 예약 종료는 생성의 미사용분만 반환한다. 별도 계산 기록은 자체 정산/복구로 처리하므로 서로의 사용량을 지우지 않는다.
- 새 기능은 **PostgreSQL `0009` 전용 내부 기능**이다. 기존 JSON v5의 생성 원장은 그대로이며 계산 원장을 JSON에 구현하거나 PostgreSQL과 혼용하지 않았다.
- 기존 `0008`/그 이전 데이터를 초기화하지 않는 추가 migration이다. 계산 기록이 생긴 DB를 이전 코드로 되돌리거나 원장/집계 일부만 삭제하면 안 된다. 운영 적용은 아직 하지 않았다.

## 검증

- 순수 계산/상태 전환 신규 **17개**: 별도 예약, 한도/정책 일치, 키 분리, 중복, 정확한 한 번의 반환/정산, 불확실·초과, 취소/만료/삭제, 날짜, 변조, 생성 재시도 근거.
- 실제 PostgreSQL 신규 **12개**: 20개 동시 예약·전송·정산, 재접속/응답 확인 유실 모사, 생성과 공유하는 요청·일일 한도, insert/update/중단 trigger 실패, 취소/철회, 복구 커서, 삭제 후 정산, SQL 제약.
- 기본 **459 processor + 4 client = 463개**, 타입·processor 빌드·린트·Site 빌드 통과. 실제 PostgreSQL 16.15 **35/35**, migration `0000–0009` 포함. 총 **498개**, 반복 실행은 중복 합산하지 않는다.
- 시험 DB는 기존 로컬 이미지의 loopback/tmpfs 폐기용 환경이다. 끝난 뒤 새 시험 컨테이너/자료만 정리했으며 기존 DB·사용자 자료는 유지했다.
- 실제 TCP/COMMIT 응답 유실·프로세스 강제 종료·Google 호출까지 연결한 통합 시험은 아니다. 이번 외부 API 호출 **0회**, 운영 DB/저장소·키/과금·화면·푸시/배포 변경 없음.

## 다음 — B5-B3b5 계수 실행 경계와 실측 보관 연결

이번 `sending` 결과/공급자 영수증은 **최종 전송 허가가 아니다.** 실제 계수 실행기는 확정 이후에도 현재 동의·승인 입력·무료 조건·검토된 입력 상한·소유권·취소·짧은 유효기간을 같은 최종 잠금 안에서 확인하고, 정확히 한 번만 요청을 시작해야 한다. 그 뒤 응답을 위 원장에 정산하고 최신 실측 보관과 연결한다.

`MeteredGeminiInputCounter` 구현, 최종 잠금/전송 경계, 실제 이미지/전체 요청 대조, 복구 루프 연결은 다음 단계다. 기존 생성용 `launchAnalysisRequest`를 계산 전송용으로 재사용하지 않는다. 운영 준비 검증기와 입력 상한 근거 발급·무료 프로젝트/모든 호출자의 한도 근거·운영 DB/저장소 조건은 계속 남아 있다. 자동 분석은 꺼진 상태를 유지한다.
