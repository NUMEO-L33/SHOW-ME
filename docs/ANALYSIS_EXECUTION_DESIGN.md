# AI 실행·운영 예산 설계 v1.6

작성일: 2026-09-14 · 범위: 전체 계획 B1–B5 · 상태: B1–B3·B4-A·B4-B1 결과 저장 로컬 완료, B4-B2 자동 실행 연결 다음

현재 HTTP 경계는 [분석 API](ANALYSIS_API.md)를 따른다. 이 문서는 **아직 자동 실행을 허용하지 않은 접수·예산·작업 실행**을 정의한다. 기본 접수기는 연결됐지만 실제 준비 조건 검증기가 없어 신규 요청은 차단한다. 구현 범위는 8–13절의 체크포인트로 구분하고 최신 상태는 13절을 따른다. 이전 절의 테스트 수·미구현 항목은 해당 체크포인트 당시 기록이다.

## 1. 기본 결정

- 기존 Node/Express + PostgreSQL을 유지한다. 별도 Redis/외부 큐는 추가하지 않고 `analysis_runs`의 queued 행을 내구성 있는 대기열로 쓴다.
- 기존 `AnalysisAdmission`이 운영 접수 경계다. 실행 준비·동의·입력·초안 버전·예산을 모두 확인하고 DB에 예약과 실행을 함께 저장한 후 응답한다. HTTP 처리 중 Google을 호출하지 않는다.
- AI 실행 슬롯은 미디어 큐와 분리한다. 초기 프로세스 동시 실행 1개, 가이드별 활성 실행 1개. 여러 복제본의 전체 동시 실행 상한도 DB에서 제한하며 인메모리 제한으로 대신하지 않는다.
- 서버 소유 모델/프롬프트를 예약에 고정한다. 모델 변경·가격표 변경으로 기존 예약을 새 단가에 재해석하지 않는다. 가격표와 입력 토큰 상한을 확인할 수 없으면 전송하지 않는다.
- 운영 허용값이 없거나 0이면 거절한다. 로컬 가상 시험의 하루 10회 파일 예약과 `.env` 동의는 운영 사용 권한이 아니다. 실제 요청/금액 한도는 사용자 확인 후 별도로 입력한다.

### 사용자 비용·시험 결정 — 2026-09-14

- 지금은 **AI·서버/저장소 모두 무료 범위만** 허용한다. 서비스 시작 시 유료 전환할 계획이지만 지금 계정의 과금을 켜거나 양수 지출 한도를 승인한 것은 아니다. 유료 전환 직전에 AI와 서버 예산을 각각 확인한다.
- B2–B4는 외부 통신 없는 로컬/모의 검증으로 진행할 수 있다. B5 실호출과 지인 배포는 해당 계정·서비스의 무료 조건과 상한을 확인한 뒤에만 한다. 무료 사용 가능성을 확인하지 못하면 로컬 검증을 유지하며 유료 서비스나 다른 저장소로 임의 전환하지 않는다.
- 테스트 자료는 사용자가 제공할 **가상의 개인정보가 포함된 화면/영상**이다. 아직 자료는 받지 않았다. 실제 개인정보가 섞이지 않았는지 확인할 전용 테스트 자료 경로를 준비해야 하며, 임의 사용자 영상 업로드 전체의 분석 허용으로 확장하지 않는다.
- 향후 접수 설정은 무료 시험(`free_only`)과 승인된 유료 운영(`paid_capped`)을 구분하는 것으로 설계한다. 이 이름의 환경변수/실행 모드를 이번에 구현한 것은 아니다. 무료 모드에서 공급자의 무료 상태·요청/토큰 제한을 확인하는 별도 전송 게이트가 필요하다.
- B1의 양수 가격표는 보수적 계산 계약이지 결제 허가가 아니다. 무료 승인에 맞춘다는 이유로 단가를 0으로 바꾸거나 유료 지출 한도를 임의로 채워 넣지 않는다. B1을 실제 무료 접수 모드에 연결하기 전, 계산용 사용량과 지출 권한을 분리하는 계약·검증을 추가한다. 현재 신규 분석 503은 유지한다.

## 2. 데이터 계약과 migration 순서

기존 `analysis_runs`는 `(guideId, id)`가 키이고 상태와 JSON payload를 보관한다. `guide_drafts`는 revision·입력 지문·문서를 보관한다. 아래는 최종 계약과 현재 저장 범위다.

| 대상 | 최종 필드/키와 규칙 | 현재 구현 범위 |
|---|---|---|
| 실행 큐 인덱스 | 다음 실행 시각·lease·생성 시각을 조회 가능한 필드/인덱스로 두고 payload와 대조 | B4-A: createdAt/availableAt/attemptCount 열·인덱스·일치 검사. queued는 생성 시각, running은 lease 만료 시각. 재시도 backoff 시각은 B4-B |
| `analysis_batches` | guide/run/batchIndex, 입력 지문, 대상/문맥 ID, 실행 상태·시도·lease·검증된 결과. 최대 6묶음 | B4-B1: queued/succeeded·대상/문맥 ID·검증된 완료 결과와 정산 연결 저장. lease는 run 소유권과 대조. 자동 실행·재시도 연결은 B4-B2 |
| `analysis_budget_windows` | UTC 날짜·scope(global 또는 guide), 한도 버전, reserved/consumed 단위 | 날짜/scope 복합 키, 정책 버전·한도·`used`. 최대 예약에서 확정 정산/안전한 해제분만 한 번 차감 |
| `analysis_reservations` | guide/run, 모델/가격표/정책 버전, 최대분·상태. 같은 실행 재접수는 같은 예약 | guide/run 복합 키, 날짜·최대분·동의/요청/정책 스냅샷. 삭제 시 상세만 null |
| `analysis_request_attempts` | reservation/batch/dispatch 번호, 최대분, 상태·확인된 사용량. 기록 없이 전송 금지 | guide/run/batch/ordinal 키, run 내 dispatch ID 고유, reserved/sending/settled/uncertain/overrun/released, 숫자 사용 기록 |
| `analysis_accounting_controls` | 전체 신규 예약·전송 기록 중단 상태 | global 단일 행. 상한 위반과 같은 트랜잭션으로 halted=true, 자동 해제/재생성 없음 |

`0003_analysis_funding.sql`은 저장용 테이블 3개, `0004_analysis_accounting.sql`은 요청 원장·전체 중단 제어 테이블을 추가하고 제어 행을 한 번 생성한다. 기존 초안·실행을 재생성하거나 예전 무예산 실행에 예약을 소급하지 않는다. 이후 실행 필드 확장 시 추가 migration→필요한 payload backfill→이중 값 일치 검증→새 읽기/쓰기 경로→복구 시험 순서로 적용한다. 실제 DB에 migration을 적용하지 않았다.

B4-A는 `0005_analysis_work_queue.sql`을 추가했다. 먼저 nullable 조회 열을 추가하고 기존 payload를 backfill한 다음 필수 열·일치 제약과 조회 인덱스를 적용한다. B4-B1의 `0006_analysis_batch_completion.sql`은 묶음 상태 열을 추가·backfill한 뒤 필수 값과 payload 일치 제약을 적용한다. 현재 PostgreSQL 읽기/쓰기는 `0006`까지 필요하다. JSON은 기존 v1/v2/v3 자료를 보존하는 v4이며 다음 쓰기 때 승격한다. 실환경 적용·이전 payload migration 검증은 B5에 남긴다.

예산 기록은 가이드 삭제 cascade로 없애지 않는다. 가이드 삭제는 이미지·제안·동의 상세·편집 키 연결을 제거하고, 해당 날짜의 비용 합계/불확실 예약 등 최소 운영 집계는 별도로 유지한다. 가이드 재생성·삭제로 전체 일일 한도가 초기화되어서는 안 된다. 장기 비용 기록 보존 기간은 운영 설정에서 명시한다.

계정 없는 현재 서비스의 범위는 global+guide다. 가이드 키 여러 개를 만들면 사람별 제한을 우회할 수 있으므로 **전체 일일 상한이 필수**다. `ownerId`가 null인데 임의로 신뢰할 수 있는 사용자별 한도가 있다고 표시하지 않는다. IP 요청 속도 제한은 별도 보조 장치다.

## 3. 접수 트랜잭션

1. 인증된 가이드·ready 프레임·최신 동의·서버 모델을 확인한다. 날짜는 브라우저 시간이 아닌 서버/DB UTC 기준이다.
2. 모든 비용 관련 트랜잭션은 **global 제어 행→global 날짜→guide 날짜→guide→run/batch** 순서로 잠금을 얻는다. 여러 날짜/가이드가 있으면 각 범주 안에서 날짜·ID 오름차순으로 잠근다. 전체 제어 행을 먼저 잠가 날짜를 넘는 새 예약과 상한 위반 기록도 직렬화한다. 잠금 순서를 뒤집지 않는다. worker 정산도 같은 순서를 사용한다.
3. 동일 실행이 이미 있으면 본문·입력 지문·버전이 같은지 검사하고 그대로 반환한다. 새 예약·worker 실행·정산을 중복 발생시키지 않는다.
4. 현재 미디어/초안/활성 실행을 다시 확인한다. 전체와 가이드 양쪽의 여유에서 실행 최대분을 예약한다. 둘 중 하나라도 실패하면 모든 변경을 롤백한다.
5. 최초 초안+queued 실행+최대 6개 묶음+예산 예약을 한 트랜잭션으로 확정한다. 그 뒤에만 202다. 별도 큐 알림 실패가 발생해도 DB 스캔이 작업을 다시 찾는다.
6. 응답 유실/HTTP 5초 시간 초과는 접수 실패 확정이 아니다. 동일 ID 조회·재전송으로 복구하고 임의 환불/새 실행 생성을 하지 않는다.

현재 JSON 저장소는 단일 인스턴스 개발용이다. B2-A는 같은 파일에 예약과 실행을 함께 저장하고 원자 교체한다. 같은 인스턴스의 직렬화만 보장하며 여러 인스턴스/프로세스가 한 파일을 공유하도록 승인하지 않는다. 실제 운영 승인은 여러 PostgreSQL 연결의 경합 시험 이후다.

## 4. 비용 계산·예약·정산

금액은 소수 부동소수 대신 **micro-USD 정수(1달러의 백만분의 1)**로 계산한다. 환율·세금·다른 앱 사용량·실제 청구 총액을 보장하는 예산이 아니며, 이 서버가 관리하는 요청의 승인된 가격표 기준 상한이다. 테스트 숫자는 실제 Gemini 요금이 아니다.

- 단가: 모델과 가격표 버전, 입력/출력 백만 토큰당 micro-USD. 캐시 할인·무료 할당량을 미리 차감하지 않는다. 운영 단가는 B5 전에 공식 조건으로 확인한다.
- B1은 양수 단가와 네 종류 모두 양수인 상한만 예약 계산에 허용한다. 0원으로 가정한 가격표나 한 항목이라도 0인 한도는 실행 승인용 우회로로 쓰지 않는다. 실제 무료 프로젝트라 해도 승인된 보수적 가격표와 요청/토큰 상한을 따로 둔다.
- 요청 최대 비용: `ceil((입력 상한 × 입력 단가 + 출력 상한 × 출력 단가) / 1,000,000)`.
- 실행 예약: `ceil(프레임 수 / 4)`묶음 × `(1 + 허용 재시도 수)` × 요청별 최대 사용분. 요청마다 먼저 비용을 올림해 전체 합산 반올림으로 과소 예약하지 않는다.
- 최대 24프레임, 묶음당 대상 4장+앞뒤 문맥 각 1장. 입력 토큰 상한은 **모든 이미지·문맥·프롬프트·schema**를 포함하는 서버 측 검증 가능한 최대치여야 한다. 이미지 바이트 수를 곧바로 토큰 수로 가정하지 않는다. 신뢰할 수 있는 상한이 없으면 실행 거절.
- 출력 상한은 현재 어댑터의 8192 이내이고 생각 토큰도 사용량에 포함한다. 제공자 설정의 의미·추가 비용 조건을 실제 연결 전 재검증한다.
- 기본 재시도 상한은 묶음당 1회다. 재시작/복구도 같은 durable 전송 횟수를 사용하며 리셋하지 않는다. worker lease 소유권 횟수(최대 3)와 외부 전송 횟수는 별개다.
- 전송 직전 요청 단위 예약을 sending으로 확정한다. 정상 사용량이 확인되면 실제분만 consumed로 옮기고 남은 토큰/금액을 해제한다. **보낸 요청 횟수는 실패했다고 반환하지 않는다.**
- 실행 전체 예약에서 해당 요청의 몫을 배정하는 것이므로 같은 날짜의 총액에 이중 예약하지 않는다. 실행 안의 요청 원장 합계가 최대 예약을 넘을 수 없다. 정산은 전송 ID의 상태를 조건부 갱신해 정확히 한 번 반영하며, 이미 확정된 정산의 재전송은 집계에서 다시 빼지 않는다.
- timeout·연결 종료·비정상 사용량·정산 응답 유실·프로세스 종료로 사용량이 불확실하면 요청 최대분을 유지한다. 거절/5xx도 공급자가 사용량을 확인해 주지 않으면 0원으로 처리하지 않는다.
- 아직 sending으로 전환되지 않았고 해당 작업이 다시 전송할 수 없도록 DB에서 종료된 예약만 해제한다. 사용량이 예약보다 큰 응답은 계약 위반으로 보존·신규 접수 중단·운영 확인 처리한다. 조용히 잘라서 한도 안이었다고 기록하지 않는다.
- UTC 날짜가 바뀌어도 미전송/불확실 이전 예약은 자동 삭제하지 않는다. 자정을 넘어 시작하는 전송은 새 날짜의 global+guide 예산도 먼저 확보하며, 이전 날짜 집계와 이전 예약의 해제 가능 여부를 같은 트랜잭션으로 처리한다. 명확하지 않으면 대기/거절한다.

B1은 위 숫자 계산과 여유 검사, 요청 단위 알려진/불확실 사용량 정산의 **순수 함수**만 구현한다. DB 잠금·중복 방지·day rollover·키/전송/실제 단가/운영 허용은 B2–B5다. 계산 함수 통과만으로 비용 보호가 운영에 적용되었다고 보고하지 않는다.

## 5. dispatcher와 묶음 처리

대기 목록을 제한된 수로 읽고 DB의 조건부 claim으로 단 하나의 worker가 lease를 얻는다. 단순 조회 후 실행하거나 프로세스 메모리 키만으로 중복을 막지 않는다. 저장소 오류는 제한된 backoff를 적용하고 준비 상태를 낮춘다.

전송 전 확인 순서: 활성 동의/입력 지문→현재 작업 소유권·lease→가이드 삭제 아님→묶음 상태→남은 시간/예산→요청 예약→비공개 이미지 로드·제한 검사→소유권 재확인→전송. 이미 로드한 이미지를 요청 경계 밖에 계속 보관하지 않는다.

- 요청 60초 이내, 실행 시도 180초 이내. 시간 내 끝내지 못한 묶음은 실패/복구 대상으로 저장한다. 성공 묶음의 결과는 유지하며 전체 succeeded로 표시하지 않는다.
- 재시도 결정은 한 계층에서만 한다. dispatcher가 묶음 재시도를 맡으면 Gemini 어댑터의 자체 재시도는 0으로 설정한다. 429/인증 오류/거절/잘못된 출력은 자동 반복하지 않는다. 일부 5xx만 남은 시간·durable 횟수·새 요청 예약 안에서 허용한다.
- lease가 만료된 sending은 전송 여부가 불확실하다. uncertain 사용분을 유지하고 허용된 재시도 슬롯을 따로 예약해야 다시 보낼 수 있다. 외부 요청의 exactly-once 완료를 약속하지 않는다.
- 모든 묶음 결과를 검증한 뒤 최종 run을 성공 처리한다. 현재 최초 미수정 revision 0만 자동 초안 적용, 사람이 수정한 초안은 제안만 보관한다. 부분 결과를 정상 완성 초안으로 자동 적용하지 않는다.
- 취소/전체 삭제를 실행 중에도 주기적으로 확인하고 AbortSignal을 연결한다. 공급자가 이미 받은 요청의 계산/과금 즉시 중단은 보장하지 않는다. 늦은 응답은 run/batch/attempt/지문/lease를 검사해 버린다.
- 기존 `analysis-runner.ts`는 결과를 메모리로 모으며 부분 성공을 영속 보관하지 않는다. B4에서 이 부분을 저장 계약에 연결해야 하고, 현재 내부 실행기를 그대로 운영 dispatcher에 붙이면 완료가 아니다.

## 6. API/UI 확장 원칙

현행 202/200/400/404/409/413/415/429/503 계약은 유지한다. 운영 한도 초과는 제한된 `ANALYSIS_BUDGET_LIMIT` 코드, 준비/정책 미확정은 `ANALYSIS_UNAVAILABLE`로 구분한다. 새 코드는 구현 시 HTTP 계약 문서/테스트를 함께 갱신한다.

진행 DTO에는 검증된 완료 묶음 수/전체 묶음 수·안전한 실패 범위·서버가 판단한 재시도 가능 여부를 추가한다. 정책/예약 원장·객체 키·가격표 내부 정보·키를 브라우저에 노출하지 않는다. C1 화면은 503을 “분석 중”으로 표시하지 않는다. 재접수 확인 지연은 기존 runId를 유지한다.

## 10. B2-B 요청별 원장·정산 체크포인트 — 2026-09-14

### 현재 구현된 내부 계약

`analysis-accounting-contract.ts`는 엄격한 입력/저장 형식을, `analysis-accounting.ts`는 순수 전이를 정의한다. JSON/PostgreSQL 저장소의 `executeAnalysisAccounting`이 원장·두 예산 구간·전체 중단 상태를 함께 저장한다. HTTP 경로나 UI는 추가하지 않았다. 원장에는 내부 식별자·수치·시각만 기록하며 이미지·동의 본문·가격표·프롬프트·공급자 원문·키를 넣지 않는다.

| 명령/상태 | 허용되는 동작 | 집계 영향 |
|---|---|---|
| allocate → reserved | 활성 실행의 유효한 묶음/재시도 슬롯에 dispatch ID 고정 | 실행 최대 예약에서 배정만 함, 이중 예약 없음 |
| sending | 아직 보내지 않은 reserved 한 건을 전송 기록으로 전환 | 최대분 유지, 재전송 시 새 전송으로 해석 금지 |
| settle(known) → settled | sending/uncertain의 확인된 사용량 정산 | 보낸 요청 수 1은 유지, 남는 토큰/금액만 해제 |
| settle(unknown) → uncertain | 응답 유실 등 사용량 불확실 | 최대분 유지, 나중에 확인되면 known 정산 가능 |
| settle(상한 초과) → overrun | 최대분보다 큰 정상 형식의 수치 응답 | 최대분 유지 + 전체 신규 예약/전송 기록 중단 |
| release → released | 실행이 취소/실패/성공으로 종료된 뒤 reserved 요청만 해제 | 해당 미전송 요청 최대분 해제, 같은 슬롯 재사용/전송 불가 |

- 같은 guide/run/batch/ordinal과 dispatch ID의 재시도는 기존 기록을 반환한다. 다른 ID의 같은 슬롯, 같은 ID의 다른 슬롯, 이미 정산한 내용과 다른 사용량은 충돌한다. `replayed: true`는 **전송 지시가 아니며 다시 호출해서는 안 된다**. 새 sending 전이도 운영 전송 권한을 부여하지 않는다.
- 최초 슬롯이 settled/uncertain이 된 뒤에만 정책 안의 재시도 슬롯을 배정할 수 있다. 이 검사는 예약 범위만 제한한다. HTTP 429/거절/성공 결과 등 실제 재시도 자격 판단과 worker 소유권은 B4가 추가해야 한다.
- 집계 `used`는 **전체 실행 최대 예약 합계 − 원장에 확정된 해제분**이다. 아직 배정하지 않은 재시도 몫은 그대로 남는다. 원래 예약의 최대분·가격표를 바꾸지 않으며 과거 실행 재접수가 정산 결과를 되돌리지 않는다.
- JSON은 단일 파일 원자 교체, PostgreSQL은 전체 제어→두 예산 구간→guide 잠금 아래 단일 트랜잭션으로 저장한다. 정산/상한 위반 기록을 저장하다 실패하면 집계나 중단 상태만 따로 남기지 않는다. 응답만 유실됐다면 같은 명령 재접수로 확정 여부를 복구한다.
- 취소 뒤에도 이미 보낸 요청의 수치 정산은 가능하나 초안/분석 결과는 수정하지 않는다. 삭제 시 상세와 묶음은 지우고 수치 원장·집계는 보존한다. **삭제 뒤 늦은 정산은 거절**하며 불확실 최대분을 자동 환불하지 않는다. 요청 원장은 가이드가 아닌 보존되는 예약에 restrict FK로 연결한다.
- overrun은 원장과 halted=true를 함께 저장한다. 신규 예약과 새 sending/allocate는 중단되지만 기존 기록 조회·정산·안전한 해제는 계속 가능하다. 중단은 날짜 변경·삭제·재시작으로 풀리지 않으며 제어 행 누락/손상도 거절한다. 코드에 자동 해제 API는 없다. 원인 조사·운영 복구 절차는 B5 전 확정한다.
- 현재 새 배정/전송 기록은 원래 예약 UTC 날짜 안에서만 허용한다. 날짜가 바뀌면 `ANALYSIS_DAY_ROLLOVER`로 거절하며 다른 날의 예산을 몰래 사용하지 않는다. 실제 전송 전 날짜 재검사와 새 날짜 예산 확보는 B4다. 정산은 늦게 와도 원래 날짜의 집계에 반영한다.
- JSON v3는 정상 v1/v2를 읽고 다음 쓰기에 기존 예약을 그대로 승격한다. 원장 누락·중복 키·잘못된 금액·집계 불일치·overrun인데 열린 제어 상태는 실패 처리한다. v1/v2 전용 프로그램으로 되돌리거나 버전/필드를 수동으로 지우지 않는다. PostgreSQL도 `0004` 이후 호환 코드만 사용한다.

### 검증과 남은 경계

## 12. B4-A 대기 작업·소유권 인계 체크포인트 — 2026-09-14

**B4 전체 완료가 아니다.** 기존 묶음 저장은 아직 `queued`만 지원하므로 B4를 A: 조회·소유권 저장, B: 작업 처리·묶음 결과·자동 복구로 나눴다. 이번에는 공급자 호출 함수나 주기 실행기를 추가하지 않았고 서버 시작 코드도 바꾸지 않았다.

- `listAnalysisWork`는 ready 가이드·살아 있는 예약의 queued/만료 running을 다음 인수 가능 시각·생성 시각 순서로 최대 50개(기본 20개) 조회한다. 읽기는 소유권을 부여하지 않는다. 삭제/취소/종료/무예산 옛 실행은 대상이 아니다. 미디어가 바뀐 경우 인수 때 지문을 다시 대조한다.
- `claimAnalysisWork`는 expectedAttemptCount 비교와 새 attemptId로 한 번만 인수한다. 전체 funded 유효 소유권은 1개로 고정한다. PostgreSQL은 모든 새 인수가 **global 제어→guide 잠금**을 거친다. 예산 수치를 바꾸지 않아 날짜 구간 잠금은 필요 없으며 기존 정산 잠금 순서의 부분 순서를 유지한다. JSON은 단일 인스턴스 내 직렬화로만 보장한다.
- 최대 lease 180초, 최대 인수 횟수 3이다. 만료 전 다른 인수는 거절하고 만료 후 새 ID/횟수로 인계한다. 3번째 lease가 만료되면 AI_TIMEOUT 실패로 종료하며 4번째 실행이나 자동 환불을 만들지 않는다. 동일 ID/이전 횟수/lease 길이의 정확한 응답 유실 재조회는 기존 살아 있는 소유권을 반환할 뿐 연장하거나 횟수를 올리지 않는다. `replayed`는 worker/공급자를 다시 실행하라는 지시가 아니다.
- 인계 때 기존 sending 요청을 uncertain으로 바꾸고 원장과 새 소유권을 함께 확정한다. 사용량·과금 여부가 불확실하므로 최대 예약은 유지한다. 이미 known 정산된 수치는 되돌리지 않으며 정산과 인계가 경합해도 알려진 사용량을 unknown으로 덮지 않는다. 저장 실패는 소유권/원장 모두 이전 상태를 유지한다.
- 인수 이력이 있는 실행의 allocate/sending(재조회 포함)은 정확한 owner ID·횟수·유효 lease를 요구한다. 미인수 queued에 대한 예전 계산 시험 계약은 내부용으로 유지하며 전송 허가는 아니다. 수치만 반영하는 늦은 settle은 소유권이 없어도 기존 조건 아래 가능하지만 초안이나 결과를 적용하지 않는다. 기존 무예산 runner의 claim/finish/fail은 funded 실행을 계속 거절한다.
- PostgreSQL 인수와 정산은 `read committed`를 명시해 잠금 대기 전에 생긴 오래된 스냅샷으로 소유권을 판단하지 않도록 한다. 기본 시각은 잠금을 얻고 관련 자료를 읽은 뒤 DB의 `clock_timestamp()`에서 받는다. 명시적 `Date` 인자는 신뢰하는 모의 시험용이며 HTTP 필드가 아니다. 인수 검사 사이의 시계 역행은 거절한다. 최종 DB 쓰기 지연 이후의 실제 전송 허가·소유권 검사는 B4-B 실행기가 별도로 해야 한다.
- `0005`에서 조회 열을 추가·backfill하고 payload와 SQL 제약/읽기 시 일치 검사로 대조한다. 자료를 삭제하거나 시도 횟수를 0으로 초기화하지 않는다. schema 생성기 재실행은 추가 차이 없음이었다. 현재 접수기의 미래 DB 확인 계약도 `postgres-0005`로 올렸지만 실제 검증기는 여전히 없으며 기본 POST는 503이다.
- 신규 작업 테스트 **24개**: 제한 조회, 동일/상이한 20건 인수 경합, 여러 가이드의 단일 소유권, 재열기·만료·세대/횟수 제한, 인계와 불확실/확정 정산, 취소/삭제/미디어 교체, 전체 중단·날짜 변경, 입력 검증, 쓰기 실패/응답 유실, 모의 PostgreSQL 잠금·DB 시각·조회 조건·열 일치·롤백. 최종 `npm run check`: processor 271 + client 4 = **275개**, 타입·processor 빌드·lint·frontend build 통과. 기존 Vite 설정/라우트 분류 안내는 남는다.

### 남은 B4-B/B5 경계

- 자동 조회 루프·저장 오류 backoff/준비 상태, 실제 provider 경계·이미지 로딩/제한, 묶음 성공 결과·완료 초안, 재시도 자격과 단일 재시도 계층, 취소/삭제 폴링·AbortSignal은 B4-B다.

- 실제 PostgreSQL migration·다중 연결 경합·DB 제약·backfill은 **아직 실행하지 않았다**. 모의 트랜잭션은 SQL 엔진 검증이 아니다. 실환경 DB/무료 프로젝트/전체 토큰 상한·사용자 승인 가상 자료 검증은 B5에서 한다. 이번에 DB 연결·Google 호출·이미지 전송·환경변수/과금 변경·UI·푸시·배포는 하지 않았다.

## 13. B4-B1 묶음 결과·정산 원자 저장 체크포인트 — 2026-09-14

B4-B를 **B1: 결과 저장 / B2: 자동 실행·복구 연결**로 나눴다. 이번 완료는 저장 경계뿐이다. `completeAnalysisBatch`는 내부 저장소 명령이며 HTTP 엔드포인트·자동 dispatcher·공급자 호출을 추가하지 않는다.

- 묶음은 `queued` 또는 `succeeded`다. 성공 묶음에는 입력 지문, 전송 ID/차수, 작업 소유권 ID/횟수, 검증된 출력, 확정 입력/출력 토큰, 완료 시각을 보관한다. 대상/문맥 ID는 원래 manifest와 같아야 하며 완료 기록은 동일한 전송의 `settled/known` 원장과 사용량까지 일치해야 한다. 조회에서도 손상·누락·상태 열 불일치를 거절하고 내부 원장을 공개 DTO로 내보내지 않는다.
- 새 결과는 현재 ready 가이드·같은 입력·살아 있는 예약·정확한 유효 소유권을 요구한다. 전송 시각은 현재 인수 시각 이상이어야 하며 같은 묶음의 더 최신 전송 차수가 있으면 이전 결과를 거절한다. 만료/교체/취소/삭제 뒤의 새 결과는 초안을 변경하지 않는다. 늦은 숫자 정산은 기존 별도 정산 계약 아래 가능하지만 결과 적용 권한은 아니다.
- 부분 성공은 결과와 해당 요청 사용량만 함께 저장한다. run의 인수 시각(`updatedAt`)과 초안은 바꾸지 않는다. 재열기·소유권 인계 후에도 성공 묶음을 읽을 수 있고 성공 묶음에 새 요청을 배정하거나 전송 기록을 만들 수 없다. 실제 worker가 이 결과를 골라 재사용하는 연결은 B4-B2다.
- 모든 묶음이 성공하면 원래 단계 순서로 합쳐 전체 출력과 마지막 단계 규칙을 다시 검증하고 run을 완료한다. 최초 미수정 revision 0 초안만 자동 적용하며 사용자 수정본은 유지하고 완성 결과를 별도 제안으로 남긴다. run의 토큰 합계는 **채택된 성공 묶음들의 사용량**이다. 재시도·불확실 요청까지 포함한 예산 기록은 요청 원장이 기준이며 아직 미배정된 재시도 예약을 임의 반환하지 않는다.
- 성공 저장 응답이 유실되면 같은 출력·소유권·전송·사용량을 가진 완료 기록만 읽기 전용 재조회한다. 취소나 사용자 편집 뒤에도 정확히 같은 기록을 반환할 수 있지만 초안을 재적용하거나 lease를 되살리지 않는다. 내용이 다른 중복 결과는 거절한다. 실패 결과의 별도 재생 기록은 없으므로 종료 뒤에는 run과 원장을 조회해 확인한다.
- 잘못된 AI 출력이라도 유효한 확정 사용량은 정산한 뒤 `AI_INVALID_OUTPUT`으로 종료하며 원문 출력은 저장하지 않는다. 상한 초과는 출력 오류보다 우선해 최대 예약·전체 중단 상태·실행 실패를 함께 보존한다. 둘 다 부분 결과를 완성 초안으로 적용하지 않는다.
- JSON v4는 결과·원장·예산·최종 초안을 한 번의 원자 파일 교체로 확정한다. PostgreSQL은 명시적 `read committed`에서 **global 제어→원래 global 날짜→guide 날짜→guide** 순서로 잠그고 관련 읽기 뒤 DB 시각으로 lease를 확인한다. 결과·정산·초안·중단 제어는 같은 트랜잭션이다. 확정 직전 동기 검사가 실패하거나 비동기 함수를 넘기면 쓰지 않는다.
- JSON v1/v2/v3 읽기는 파일을 바꾸지 않으며 다음 쓰기에 v4로 승격한다. v3의 묶음 계약은 queued 전용으로 유지해 성공 자료를 버전만 낮춰 읽을 수 없게 한다. `0006`은 기존 payload에서 상태를 채운 뒤 제약을 적용하고 자료를 삭제하거나 초기화하지 않는다. schema 생성 재검사는 추가 변경 없음이었다. 이전 프로그램과 혼용하거나 파일 버전을 수동으로 낮추지 않는다. 미래 접수 준비 보고서도 `postgres-0006`을 요구한다.

### 검증과 다음 범위

신규 테스트 **28개**: 최대 6묶음 역순 완료·부분 저장·사용자 수정 보존, 재열기/인계와 완료 묶음 재사용, 중복 20건·서로 다른 응답 경합, 오래된 소유권/전송·취소/삭제/입력 변경, 잘못된 출력·상한 초과·UTC 자정의 늦은 정산, 호출자 객체 변경, 저장 실패/응답 유실, v3 승격/손상 차단, PostgreSQL 잠금·DB 시각·상태 열·각 쓰기 경계 및 중단 제어 롤백 모의 시험. `npm run check`: processor 299 + client 4 = **총 303개**, 타입·processor 빌드·lint·frontend build 통과. 기존 Vite 설정/라우트 분류·빌드 성능 안내는 남는다.

실제 PostgreSQL 연결·migration 적용·다중 연결 경합·SQL 엔진 검증은 하지 않았다. 테스트 출력과 사용량은 가상이며 Google 호출·사용자 영상 전송·환경변수/과금·UI·푸시/배포 변경도 없다. 기본 신규 분석은 계속 **503**, 무료 전용 정책도 그대로다.

다음 **B4-B2**는 자동 조회·처리 루프, 저장 오류 backoff, 공급자/비공개 이미지 경계, 재시도 자격과 단일 재시도 계층, 취소/삭제 확인·AbortSignal, 종료 요청/미배정 예약 정리와 날짜 변경 예산 처리다. 새 날짜 예산 확보 전까지 날짜를 넘는 새 인수/전송은 차단하며, 이미 보낸 요청의 완료는 유효 소유권 아래 원래 날짜에 정산할 수 있다. 실제 준비 조건 검증기와 무료 조건·승인된 가상 자료·실환경 DB 확인은 B4-B2/B5에서 별도로 완료해야 자동 분석을 열 수 있다.
