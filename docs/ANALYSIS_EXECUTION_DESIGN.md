# AI 실행·운영 예산 설계 v1.1

작성일: 2026-09-14 · 범위: 전체 계획 B1–B5 · 상태: 설계, B1 계산 모듈 로컬 완료

현재 HTTP 경계는 [분석 API](ANALYSIS_API.md)를 따른다. 이 문서는 **아직 연결되지 않은 접수·예산·작업 실행**을 정의한다. 문서 작성이나 B1 계산 모듈만으로 자동 분석을 활성화하지 않는다.

## 1. 기본 결정

- 기존 Node/Express + PostgreSQL을 유지한다. 별도 Redis/외부 큐는 추가하지 않고 `analysis_runs`의 queued 행을 내구성 있는 대기열로 쓴다.
- 기존 `AnalysisAdmission`이 운영 접수 경계다. 실행 준비·동의·입력·초안 버전·예산을 모두 확인하고 DB에 예약과 실행을 함께 저장한 후 응답한다. HTTP 처리 중 Google을 호출하지 않는다.
- AI 실행 슬롯은 미디어 큐와 분리한다. 초기 프로세스 동시 실행 1개, 가이드별 활성 실행 1개. 여러 복제본의 전체 동시 실행 상한도 DB에서 제한하며 인메모리 제한으로 대신하지 않는다.
- 서버 소유 모델/프롬프트를 예약에 고정한다. 모델 변경·가격표 변경으로 기존 예약을 새 단가에 재해석하지 않는다. 가격표와 입력 토큰 상한을 확인할 수 없으면 전송하지 않는다.
- 운영 허용값이 없거나 0이면 거절한다. 로컬 가상 시험의 하루 10회 파일 예약과 `.env` 동의는 운영 사용 권한이 아니다. 실제 요청/금액 한도는 사용자 확인 후 별도로 입력한다.

### 사용자 비용·시험 결정 — 2026-09-14

- 지금은 **AI·서버/저장소 모두 무료 범위만** 허용한다. 서비스 시작 시 유료 전환할 계획이지만 지금 계정의 과금을 켜거나 양수 지출 한도를 승인한 것은 아니다. 유료 전환 직전에 AI와 서버 예산을 각각 확인한다.
- B2–B4는 외부 통신 없는 로컬/모의 검증으로 진행할 수 있다. B5 실호출과 지인 배포는 해당 계정·서비스의 무료 조건과 상한을 확인한 뒤에만 한다. 무료 사용 가능성을 확인하지 못하면 로컬 검증을 유지하며 유료 서비스나 다른 저장소로 임의 전환하지 않는다.
- 테스트 자료는 사용자가 제공할 **가상의 개인정보가 포함된 화면/영상**이다. 아직 자료는 받지 않았다. 실제 개인정보가 섞이지 않았는지 확인할 전용 테스트 자료 경로를 준비해야 하며, 임의 사용자 영상 업로드 전체의 분석 허용으로 확장하지 않는다.
- 향후 접수 설정은 무료 시험(`free_only`)과 승인된 유료 운영(`paid_capped`)을 구분하는 것으로 설계한다. 이 이름의 환경변수/실행 모드를 이번에 구현한 것은 아니다. 무료 모드에서 공급자의 무료 상태·요청/토큰 제한을 확인하는 별도 전송 게이트가 필요하다.
- B1의 양수 가격표는 보수적 계산 계약이지 결제 허가가 아니다. 무료 승인에 맞춘다는 이유로 단가를 0으로 바꾸거나 유료 지출 한도를 임의로 채워 넣지 않는다. B1을 실제 무료 접수 모드에 연결하기 전, 계산용 사용량과 지출 권한을 분리하는 계약·검증을 추가한다. 현재 신규 분석 503은 유지한다.

## 2. 데이터 계약과 migration 순서

기존 `analysis_runs`는 `(guideId, id)`가 키이고 상태와 JSON payload를 보관한다. `guide_drafts`는 revision·입력 지문·문서를 보관한다. 이 둘은 이미 구현됐다. 아래 추가는 B2 이후 대상이다.

| 대상 | 필수 필드/키 | 불변 규칙 |
|---|---|---|
| 실행 큐 인덱스 | 기존 run에 다음 실행 시각·lease·생성 시각의 조회 가능한 필드/인덱스 | 기존 payload와 중복 값은 저장소의 단일 쓰기 경로에서 함께 갱신하고 역직렬화 시 대조 |
| `analysis_batches` | guide/run/batchIndex, 입력 지문, 대상/문맥 ID, queued/running/succeeded/failed, 시도 번호·lease, 검증된 결과 | 최대 6묶음. 성공 묶음은 같은 입력에서 재전송하지 않음 |
| `analysis_budget_windows` | UTC 날짜·scope(global 또는 guide), 한도 버전, reserved/consumed 단위 | 요청 수·입력/출력 토큰·micro-USD 모두 비음수 정수. 검증된 상한 안에서만 예약 |
| `analysis_reservations` | guide/run, 예약 ID, 모델/가격표/정책 버전, 최대 사용분, 상태 | 같은 실행의 재접수는 같은 예약. 다른 본문/지문은 충돌 |
| `analysis_request_attempts` | reservation/batch/dispatch 번호, 최대 사용분, reserved/sending/settled/uncertain, 실제 사용량 | 외부 재전송마다 별도 durable 행. 기록 없이 전송하지 않음 |

추가 migration→기존 payload backfill→이중 값 일치 검증→새 읽기/쓰기 경로→복구 시험 순서로 적용한다. 이미 정상 처리된 가이드·분석·초안을 재생성하지 않는다. 테이블 이름/DDL은 B2에서 실제 migration으로 확정한다.

예산 기록은 가이드 삭제 cascade로 없애지 않는다. 가이드 삭제는 이미지·제안·동의 상세·편집 키 연결을 제거하고, 해당 날짜의 비용 합계/불확실 예약 등 최소 운영 집계는 별도로 유지한다. 가이드 재생성·삭제로 전체 일일 한도가 초기화되어서는 안 된다. 장기 비용 기록 보존 기간은 운영 설정에서 명시한다.

계정 없는 현재 서비스의 범위는 global+guide다. 가이드 키 여러 개를 만들면 사람별 제한을 우회할 수 있으므로 **전체 일일 상한이 필수**다. `ownerId`가 null인데 임의로 신뢰할 수 있는 사용자별 한도가 있다고 표시하지 않는다. IP 요청 속도 제한은 별도 보조 장치다.

## 3. 접수 트랜잭션

1. 인증된 가이드·ready 프레임·최신 동의·서버 모델을 확인한다. 날짜는 브라우저 시간이 아닌 서버/DB UTC 기준이다.
2. 모든 비용 관련 트랜잭션은 global 날짜→guide 날짜→guide→run/batch 순서로 잠금을 얻는다. 여러 날짜/가이드가 있으면 각 범주 안에서 날짜·ID 오름차순으로 잠근다. 잠금 순서를 뒤집지 않는다. worker 정산도 같은 순서를 사용한다.
3. 동일 실행이 이미 있으면 본문·입력 지문·버전이 같은지 검사하고 그대로 반환한다. 새 예약·worker 실행·정산을 중복 발생시키지 않는다.
4. 현재 미디어/초안/활성 실행을 다시 확인한다. 전체와 가이드 양쪽의 여유에서 실행 최대분을 예약한다. 둘 중 하나라도 실패하면 모든 변경을 롤백한다.
5. 최초 초안+queued 실행+최대 6개 묶음+예산 예약을 한 트랜잭션으로 확정한다. 그 뒤에만 202다. 별도 큐 알림 실패가 발생해도 DB 스캔이 작업을 다시 찾는다.
6. 응답 유실/HTTP 5초 시간 초과는 접수 실패 확정이 아니다. 동일 ID 조회·재전송으로 복구하고 임의 환불/새 실행 생성을 하지 않는다.

현재 JSON 저장소는 단일 인스턴스 개발용이다. B2에서 동일한 상태 전이 계약은 시험하되 JSON 파일 두 개에 예약과 실행을 따로 써서 원자성을 주장하지 않는다. 실제 운영 승인은 여러 PostgreSQL 연결의 경합 시험 이후다.

## 4. 비용 계산·예약·정산

금액은 소수 부동소수 대신 **micro-USD 정수(1달러의 백만분의 1)**로 계산한다. 환율·세금·다른 앱 사용량·실제 청구 총액을 보장하는 예산이 아니며, 이 서버가 관리하는 요청의 승인된 가격표 기준 상한이다. 테스트 숫자는 실제 Gemini 요금이 아니다.

- 단가: 모델과 가격표 버전, 입력/출력 백만 토큰당 micro-USD. 캐시 할인·무료 할당량을 미리 차감하지 않는다. 운영 단가는 B5 전에 공식 조건으로 확인한다.
- B1은 양수 단가와 네 종류 모두 양수인 상한만 예약 계산에 허용한다. 0원으로 가정한 가격표나 한 항목이라도 0인 한도는 실행 승인용 우회로로 쓰지 않는다. 실제 무료 프로젝트라 해도 승인된 보수적 가격표와 요청/토큰 상한을 따로 둔다.
- 요청 최대 비용: `ceil((입력 상한 × 입력 단가 + 출력 상한 × 출력 단가) / 1,000,000)`.
- 실행 예약: `ceil(프레임 수 / 4)`묶음 × `(1 + 허용 재시도 수)` × 요청별 최대 사용분. 요청마다 먼저 비용을 올림해 전체 합산 반올림으로 과소 예약하지 않는다.
- 최대 24프레임, 묶음당 대상 4장+앞뒤 문맥 각 1장. 입력 토큰 상한은 **모든 이미지·문맥·프롬프트·schema**를 포함하는 서버 측 검증 가능한 최대치여야 한다. 이미지 바이트 수를 곧바로 토큰 수로 가정하지 않는다. 신뢰할 수 있는 상한이 없으면 실행 거절.
- 출력 상한은 현재 어댑터의 8192 이내이고 생각 토큰도 사용량에 포함한다. 제공자 설정의 의미·추가 비용 조건을 실제 연결 전 재검증한다.
- 기본 재시도 상한은 묶음당 1회다. 재시작/복구도 같은 durable 전송 횟수를 사용하며 리셋하지 않는다. worker lease 소유권 횟수(최대 3)와 외부 전송 횟수는 별개다.
- 전송 직전 요청 단위 예약을 sending으로 확정한다. 정상 사용량이 확인되면 실제분만 consumed로 옮기고 남은 토큰/금액을 해제한다. **보낸 요청 횟수는 실패했다고 반환하지 않는다.**
- 실행 전체 예약에서 해당 요청의 몫을 배정하는 것이므로 같은 날짜의 총액에 이중 예약하지 않는다. 실행 안의 요청 원장 합계가 최대 예약을 넘을 수 없다. 정산은 전송 ID의 상태를 조건부 갱신해 정확히 한 번 반영하며, 이미 확정된 정산의 재전송은 집계에서 다시 빼지 않는다.
- timeout·연결 종료·비정상 사용량·정산 응답 유실·프로세스 종료로 사용량이 불확실하면 요청 최대분을 유지한다. 거절/5xx도 공급자가 사용량을 확인해 주지 않으면 0원으로 처리하지 않는다.
- 아직 sending으로 전환되지 않았고 해당 작업이 다시 전송할 수 없도록 DB에서 종료된 예약만 해제한다. 사용량이 예약보다 큰 응답은 계약 위반으로 보존·신규 접수 중단·운영 확인 처리한다. 조용히 잘라서 한도 안이었다고 기록하지 않는다.
- UTC 날짜가 바뀌어도 미전송/불확실 이전 예약은 자동 삭제하지 않는다. 자정을 넘어 시작하는 전송은 새 날짜의 global+guide 예산도 먼저 확보하며, 이전 날짜 집계와 이전 예약의 해제 가능 여부를 같은 트랜잭션으로 처리한다. 명확하지 않으면 대기/거절한다.

B1은 위 숫자 계산과 여유 검사, 요청 단위 알려진/불확실 사용량 정산의 **순수 함수**만 구현한다. DB 잠금·중복 방지·day rollover·키/전송/실제 단가/운영 허용은 B2–B5다. 계산 함수 통과만으로 비용 보호가 운영에 적용되었다고 보고하지 않는다.

## 5. dispatcher와 묶음 처리

대기 목록을 제한된 수로 읽고 DB의 조건부 claim으로 단 하나의 worker가 lease를 얻는다. 단순 조회 후 실행하거나 프로세스 메모리 키만으로 중복을 막지 않는다. 저장소 오류는 제한된 backoff를 적용하고 준비 상태를 낮춘다.

전송 전 확인 순서: 활성 동의/입력 지문→현재 작업 소유권·lease→가이드 삭제 아님→묶음 상태→남은 시간/예산→요청 예약→비공개 이미지 로드·제한 검사→소유권 재확인→전송. 이미 로드한 이미지를 요청 경계 밖에 계속 보관하지 않는다.

- 요청 60초 이내, 실행 시도 180초 이내. 시간 내 끝내지 못한 묶음은 실패/복구 대상으로 저장한다. 성공 묶음의 결과는 유지하며 전체 succeeded로 표시하지 않는다.
- 재시도 결정은 한 계층에서만 한다. dispatcher가 묶음 재시도를 맡으면 Gemini 어댑터의 자체 재시도는 0으로 설정한다. 429/인증 오류/거절/잘못된 출력은 자동 반복하지 않는다. 일부 5xx만 남은 시간·durable 횟수·새 요청 예약 안에서 허용한다.
- lease가 만료된 sending은 전송 여부가 불확실하다. uncertain 사용분을 유지하고 허용된 재시도 슬롯을 따로 예약해야 다시 보낼 수 있다. 외부 요청의 exactly-once 완료를 약속하지 않는다.
- 모든 묶음 결과를 검증한 뒤 최종 run을 성공 처리한다. 현재 최초 미수정 revision 0만 자동 초안 적용, 사람이 수정한 초안은 제안만 보관한다. 부분 결과를 정상 완성 초안으로 자동 적용하지 않는다.
- 취소/전체 삭제를 실행 중에도 주기적으로 확인하고 AbortSignal을 연결한다. 공급자가 이미 받은 요청의 계산/과금 즉시 중단은 보장하지 않는다. 늦은 응답은 run/batch/attempt/지문/lease를 검사해 버린다.
- 기존 `analysis-runner.ts`는 결과를 메모리로 모으며 부분 성공을 영속 보관하지 않는다. B4에서 이 부분을 저장 계약에 연결해야 하고, 현재 내부 실행기를 그대로 운영 dispatcher에 붙이면 완료가 아니다.

## 6. API/UI 확장 원칙

현행 202/200/400/404/409/413/415/429/503 계약은 유지한다. 운영 한도 초과는 제한된 `ANALYSIS_BUDGET_LIMIT` 코드, 준비/정책 미확정은 `ANALYSIS_UNAVAILABLE`로 구분한다. 새 코드는 구현 시 HTTP 계약 문서/테스트를 함께 갱신한다.

진행 DTO에는 검증된 완료 묶음 수/전체 묶음 수·안전한 실패 범위·서버가 판단한 재시도 가능 여부를 추가한다. 정책/예약 원장·객체 키·가격표 내부 정보·키를 브라우저에 노출하지 않는다. C1 화면은 503을 “분석 중”으로 표시하지 않는다. 재접수 확인 지연은 기존 runId를 유지한다.

## 8. B1 구현 체크포인트 — 2026-09-14

- `processor/src/analysis-budget.ts`: 명시된 모델/가격표로 최대 6묶음과 묶음당 재시도 1회까지 요청·입력/출력 토큰·micro-USD 최대분을 계산한다. BigInt 중간 계산, 요청별 올림, 안전 정수 상한을 적용한다.
