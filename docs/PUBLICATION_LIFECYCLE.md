# 공유 철회와 게시 만료의 내부 처리 — 2026-09-21

후속 구현: 보존 분리는 `PRIVATE_RETENTION.md`, HTTP 경계는 `PUBLICATION_API.md`, 선택적인 실행기/lifecycle 연결은 `PUBLICATION_RUNTIME.md`에서 구현했다. 아래는 철회/게시 만료를 만든 당시의 단계별 기록이며, 최신 완료·미완료와 검증 수치는 `SESSION_CHECKPOINT.md`를 따른다. 화면 연결·기본 게시 활성화·실환경 검증은 여전히 남아 있다.

기존 계획 E3의 내부 철회·15일 만료 처리다. `PUBLICATION_COMMIT.md`의 불변 게시본 위에 철회 명령, 현재 접근 가능 여부 조회, 만료 발견/정리를 연결했다. **제품 HTTP·뷰어·버튼·자동 시작에는 아직 등록하지 않았다.** 기존 개발 MD의 목표/완료 조건은 변경하지 않았다.

## 철회와 동시 작업

- `stopPublication`은 소유자 인증을 대신하지 않는 내부 메서드다. `withdraw`는 화면이 확인한 head version과 pending job ID를 함께 비교한다. 처음 게시 전에는 head version 0을 쓴다. 관측 뒤 새 게시나 다른 요청이 들어오면 null로 충돌을 알리고 새 상태를 확인해야 한다. 오래된 요청을 현재 상태에 맞춰 몰래 재시도하지 않는다.
- 부모 가이드 잠금 안에서 공개 활성 참조 제거, 관측한 queued/running 작업 취소, 해당 자산 묶음 cleanup 전환을 한 트랜잭션에 저장한다. JSON도 단일 원자적 파일 교체다. DB 예외·무시된 쓰기에서는 전부 롤백한다. 이미 성공한 job/snapshot 이력은 수정하지 않는다.
- 이미 이미지가 준비된 작업도 취소된다. 철회가 먼저 확정된 뒤 늦게 도착한 commit/claim/준비 완료는 게시를 되살리지 못한다. 처리 중 put이 취소를 무시하면 실제 종료 전 `writerSettled=false`를 유지하고, 실제 종료 뒤 늦은 출력까지 다시 정리한다.
- 첫 게시 전 철회도 당시 job만 취소한다. 응답 유실 뒤 같은 요청을 다시 보내더라도 이후 새로 요청한 작업을 취소하지 않는다. head가 바뀐 요청은 충돌로 처리하며, head가 없고 원래 job이 이미 취소된 경우에는 무변경 결과를 반환한다.
- 만료 전 사용자가 새 요청을 명시적으로 접수하면 재게시할 수 있다. 공개 slug·최초 게시 시각·만료는 유지하고 새로운 독립 처리본만 활성화한다. 과거 commit 재전송은 과거 게시본을 활성화하지 않는다. 전체 삭제 표시가 먼저 저장된 경우 철회/게시 명령은 그 결정을 바꾸지 않는다.

## 접근 판단과 15일 만료

- `getAccessiblePublication({slug, publicationId?})`는 매번 삭제 대기 여부, 현재 활성 게시본, 정확한 만료 시각, 현재 ready/종료 확인 자산 및 receipt 일치를 검사한다. 과거 이미지 ID를 넣으면 최신 게시본으로 자동 대체하지 않고 거절한다. 처리본이 사라졌거나 상태/receipt가 다르면 원본으로 대체하지 않는다.
- PostgreSQL은 slug로 후보를 찾은 뒤 부모 가이드 공유 잠금을 얻고 head/자산/작업과 DB 시각을 다시 읽는다. 잠금 대기 전에 본 상태나 시각으로 접근을 허용하지 않는다. 이는 한 시점의 내부 권한 판단이지 향후 스트림 전체에 쓸 무기한 티켓이 아니다.
- 첫 게시로부터 정확히 15×24시간이 된 순간부터 새 접근을 거절한다. 정리 worker가 늦거나 저장소 삭제가 실패해도 접근을 되살리지 않는다. 만료된 head의 새 준비 접수·claim·확인·완료도 막고, 기존 요청 조회와 취소/정리는 허용한다.
- 이 메서드는 **내부 object key를 가진 저장 결과**다. 공개 DTO가 아니므로 그대로 응답하면 안 된다. 다음 API 연결에서는 허용 목록 응답, 각 이미지 요청별 현재 권한 재검사, no-store, 스트림 시작 전 재확인, 인증·빈도 제한을 연결해야 한다. 내려받은 파일/이미 시작한 응답/외부 캐시를 회수한 것으로 표시하지 않는다.

## 만료 발견과 자산 정리

- `listExpiredPublications`는 현재 게시 중인 만료 head 또는 철회 상태에서 새 준비 작업이 남은 만료 head를 찾는다. 최대 20개, `(expiresAt, publicSlug)` 전체 cursor를 사용하며 SQL과 JSON 모두 동일한 시각/바이트 순서로 비교한다. migration 0016이 이 순서의 인덱스를 추가한다.
- `PublicationRecoveryWorker`는 한 회차에 게시 만료 최대 20개를 먼저 처리한 뒤 기존 lease 만료와 cleanup 순환 조회를 수행한다. 만료 명령은 잠금 안에서 head version과 새로운 DB 시각을 다시 검사한다. 개별 실패 뒤 cursor가 진행하고 한 바퀴 뒤 재시도한다.
- 철회/만료 때 공개 참조와 pending writer를 먼저 차단하고, 물리 파일 삭제는 기존 내구 cleanup 기록으로 수행한다. 삭제 실패/timeout은 기록을 유지하며 재접속 후 다시 처리한다. 새 이미지 put이나 원본 삭제를 이 루프에서 수행하지 않는다.
- 기존 중단/30초 회차/진행 중 I/O 추적을 재사용한다. DB/삭제 요청이 끝나지 않으면 새 요청을 계속 쌓지 않는다. 그런 동안에도 접근 조회는 만료 시각 자체로 거절한다. 프로세스가 원격 put 중 죽어 종료가 불확실한 writer를 임의로 종료 처리하지 않는다.

## 남은 7일/15일 보존 분리 — 공개 활성화 금지

이번 단계는 공개 참조와 **게시 처리본**의 만료 처리까지다. 기존 `index.ts`의 7일 미공개 정리는 아직 부모 가이드를 전체 삭제한다. 이를 게시 상태에 그대로 적용하면 15일 전에 게시본이 지워질 수 있다. 반대로 게시 가이드를 통째로 제외하면 원본 보관을 승인 없이 연장하게 되므로 그런 변경도 하지 않았다.

다음은 별도 비공개 만료 상태와 정리 소유권을 두고 원본/미가림 프레임/초안 정리를 게시 처리본과 분리하는 것이다. 비공개 자료 만료 후 새 분석·편집·게시 준비는 거절하되 남은 게시본 조회·공유 철회·전체 삭제는 가능해야 한다. 정리 재시도나 조회가 보존 시각을 갱신하지 않아야 하며, 오래된 게시/초안 이력의 최종 정리도 확인해야 한다. 이 연결과 API 검증 전에는 제품 게시/자동 loop를 켜지 않는다.

## 검증 및 배포 경계

- 새 일반 검사 14개: 실제 PNG 준비 후 철회/재접속/정리, 첫 게시 전 queued/running 차단, 관측한 head/job 비교, 새 재게시와 과거 요청/이미지 차단, 만료 경계의 접근/준비 거절, 철회 상태의 만료 발견, 늦은 put, 쓰기 실패 롤백, 삭제 선행, 손상된 처리본 거절, 삭제 실패 재시도, cursor/입력 제한, 제품 미등록을 검사했다. 관련 집중 검사 40개 통과.
- 실제 PostgreSQL 16.15 검사 127개 통과(추가 5개). 실제 이미지와 재접속, 철회 3개 쓰기 위치×예외/무시의 전체 롤백, 독립 연결의 철회/늦은 commit/사전 이미지 조회 경합, 첫 게시 전 취소 및 철회 상태 만료, 잠금 대기 중 만료 경계 통과를 확인했다. 시각 테스트 하나는 명시적 메타데이터 fixture이며 실제 변환 검사는 별도로 수행했다.
- 초기 테스트 타입 검사에서 새 mock의 rest 인자 자료형 누락 2건을 고쳤다. 최종 점검에서 PostgreSQL 준비 명령의 시각을 모든 상태 조회 뒤에 얻도록 보완하고 전체 검사를 다시 실행했다. 최종 결과는 `SESSION_CHECKPOINT.md`에 기록한다.
- 최종 일반 전체 **980개 통과**(이관 99 / 서버 782 / 클라이언트 99), PostgreSQL **127개 통과**, 모두 실패·취소·생략 0, 종료 코드 0. 최종 서버 제품/테스트 타입 검사·빌드·diff 공백 검사도 통과했다. 최종 검사 뒤 제품 코드는 바꾸지 않고 기록만 보완했다.
- JSON v8은 유지한다. 새 migration 0016은 인덱스만 추가하며 기존 SQL/실행 역할 권한을 변경하지 않는다. 앞선 구현과 함께 로컬 미커밋·미푸시 상태다.
- 합성 자료·로컬 LocalStorage·일회용 PostgreSQL만 사용했다. 첫 임시 컨테이너 `showme-b5-bcc30de23af54ad6a5f5ac5f9fdc4123`과 최종 재검사 `showme-b5-3de423fce2334908ae5d013b92105d11`은 실행기의 `postgres_fixture_removed`로 정리를 확인했다. 운영 Replit DB/Storage, .env·키·개인 영상·외부 AI를 사용하지 않았다. 공개·배포·재시작·새 화면 검증도 수행하지 않았다.

남은 순서: 7일 비공개 자료와 15일 게시본 보존 분리 → 인증 API/실행 루프/화면 연결 → 합성 실환경 검증. E3 전체나 운영 완료가 아니다.
