## 2. 공식 무료 조건과 현재 설계의 차이

2026-09-15 공식 공개 문서 확인 기준이며, 계정 화면의 실제 적용 조건은 별도로 확인해야 한다. 가격표에서 금액이 로딩되지 않은 칸은 추정하지 않았다.

- **Gemini:** `gemini-3.5-flash-lite` Standard에는 무료 입력/출력 구간이 있다. 유료 등급은 별도이며, 무료 구간의 입력·출력은 제품 개선에 이용될 수 있다. 따라서 지금은 승인된 합성 자료만 허용한다. [Google 가격표](https://ai.google.dev/gemini-api/docs/pricing#gemini-3.5-flash-lite)
- **프로젝트 확인:** AI Studio Projects의 Billing Tier와 Billing/Usage 화면에서 실제 프로젝트의 상태를 확인해야 한다. `.env`의 확인값이나 성공 HTTP 응답으로 대신할 수 없다. [Google 과금·상태 확인](https://ai.google.dev/gemini-api/docs/billing)
- **Replit 무료 플랜:** Starter는 무료 게시 앱 1개(30일 후 내려가며 재게시 가능), 운영 DB·Object Storage·Autoscale/static 게시에 쓸 월 크레딧을 안내한다. 이는 지금 설계의 Reserved VM까지 무조건 무료라는 뜻이 아니다. [Starter 조건](https://docs.replit.com/billing/plans/starter-plan)
- **상시 서버:** 기존 프로세서는 잠들지 않는 Reserved VM을 전제로 한다. 공식 문서는 Reserved VM을 고정 월 비용 형태로 설명한다. 계정별 포함 크레딧/지원 유형/초과 차단 확인 전 배포하지 않는다. 무료 Autoscale로 바꾸는 것도 실행·복구 구조 검토가 필요한 별도 선택이다. [배포 유형](https://docs.replit.com/features/publishing/deployment-types), [게시 비용](https://docs.replit.com/billing/deployment-pricing)
- **DB·저장소:** 개발 DB 무료와 운영 DB 사용량 과금은 구분된다. App Storage도 용량·전송·작업량에 따라 사용량이 계산되고 객체의 최소 과금 기간은 7일이다. 무료 크레딧의 잔여량·초과 동작을 확인해야 하며, 실제 저장소 읽기 시험도 무조건 무료라고 간주하지 않는다. [DB 과금](https://docs.replit.com/billing/about-usage-based-billing), [저장소 과금](https://docs.replit.com/billing/object-storage-billing)

**코드와 문서를 대조한 비용 위험:** 현재 미디어 dispatcher는 기본 5초마다 대기 작업을 조회하고, 자산 정리는 1분마다 실행한다. Replit 문서는 운영 DB가 마지막 요청 후 5분간 활성 상태를 유지한다고 설명한다. 따라서 이 루프를 그대로 배포하면 방문자가 없어도 DB가 계속 활성 상태일 가능성이 높다. 이는 코드와 공식 조건을 근거로 한 추론이며 실제 청구 측정은 아니다. 이번에는 주기를 바꾸거나 종료 복구를 끄지 않았다.

## 3. readiness 구현 전에 해결할 계약

1. **서버 소유의 실제 근거:** 승인 대상 합성 자료와 현재 키의 프로젝트를 묶고, 근거의 조회 시각·만료·철회·실패 시 차단을 정의한다. 수동 화면 확인은 개발 진행에 필요한 정보이지, 매번 발급되는 30초 readiness snapshot의 자동 검증을 대신하지 않는다. 가상 fixture나 확인값만으로 검증기를 만들지 않는다.
2. **공급자 한도와 앱 예산 구분:** Google은 모델별 RPM/입력 TPM/RPD 등을 적용하고 프로젝트 단위로 공유한다. RPD 갱신은 미국 태평양 자정이며 앱 예산은 UTC 자정이다. 앱의 하루 10회 시험 한도·UTC 원장을 Google 잔여 한도라고 표현하지 않는다. [Google 할당량](https://ai.google.dev/gemini-api/docs/rate-limits)
3. **점검 당시 보고서의 한계:** 당시 `entitlement.dailyQuota`는 요청/입력/출력의 일일 수치만 받았다. 이 구조에 RPM/TPM을 복사하거나 공급자가 제공하지 않은 일일 출력 한도를 지어 넣으면 안 된다. 7절에서 단위 계약/계산은 보완했으나 실제 공유 사용량 차감·검증은 아직 남아 있다. 모의 보고서는 운영 증거가 아니다.
4. **전체 입력 상한:** 프롬프트·출력 schema·대상/문맥 이미지·메타데이터를 모두 포함하는 모델별 입력 토큰 상한의 근거가 필요하다. 이미지 크기·프레임 수 제한만으로 완료 처리하지 않는다. 준비 검증의 `inspect`는 이미지를 전송하면 안 되므로 `countTokens`에 이미지를 보내는 우회도 허용하지 않는다.
5. **비공개 이미지 로더:** 저장된 guide/step/처리 시도에서만 키를 도출하고 입력 승인·manifest와 묶는다. 임의 경로/URL·다른 가이드·교체된 프레임을 거부하고, JPEG 실제 형식/치수/2 MiB 상한·시간 제한·취소·늦은 읽기 종료를 검증한다. 공급자/로그에 object key·원본 영상·편집 키를 넘기지 않는다. 저장소 어댑터가 있다는 것과 이 분석용 로더가 있다는 것은 다르다.

- 기존 Replit 포함 크레딧과 월 추가 사용 예산만 다룬다. 새 구독·크레딧 구매·자동충전·더 큰 한도·공개 배포를 허용한 것이 아니다.
- `Set a usage alert`는 알림이며 중단 한도가 아니다. `Set a usage budget`과 구분한다. 공식 문서상 크레딧 이후 지출에 적용되며 도달 시 사용량 기반 서비스가 중단된다. 계정의 다른 서비스에도 영향이 있을 수 있다. [Replit 한도 안내](https://docs.replit.com/billing/managing-spend)
- 크레딧 자동충전은 별도 기능이다. 항목이 없다는 사실만 기록하며 예산 값으로 자동충전/구독 결제를 포함한 전체 청구액의 상한을 보장하지 않는다.
- 기존 앱의 예산 수치·실행기·환경값은 변경하지 않았다. 사람의 계획 승인과 짧은 유효기간의 실환경 전송 허가는 별개다.

이 시점까지는 문서만 변경했다. 다음 절의 최신 보고 이후에는 계정 화면 확인을 반복하지 않고 외부 전송 없는 로컬 개발을 진행한다. 이후 운영 연결 단계에서 대상 프로젝트/DB·Storage 범위를 확인한다.

## 7. 최신 결정과 B5-B3a 로컬 구현 — 2026-09-15

사용자의 **“설정했으니 진행해 일단 0.02로 되어있어”**를 **Replit 월 추가 사용 예산 USD 0.02 저장 완료 보고**로 반영한다. 저장 상태를 직접 조회/자동 검증한 것은 아니다. 이 보고는 로컬 개발을 진행할 근거이며, Gemini 유료 전환·자동충전·새 구독·배포 활성화 승인이 아니다. 기존 UI/호스팅 구조는 유지한다.

### 추가한 코드

- `analysis-provider-quota.ts`: 공급자 한도를 RPM/입력 TPM/RPD로 분리한다. 프로젝트·모델별 **실제 전송 시도 원장**을 가정하는 순수 계산기이며 최근 60초와 미국 태평양 날짜를 따로 계산한다. DST 23/25시간 날짜와 자정 직후 이전 날짜의 60초 사용량도 유지한다. 재시도·결과 불확실 요청은 별도 시도로 최대 입력량을 계속 계산한다. 최근 28일 최고치·만료/범위 불일치/불완전 자료는 거절한다. [Google 한도 정의](https://ai.google.dev/gemini-api/docs/rate-limits)
- 접수 보고서: 잘못된 `dailyQuota` 대신 `providerLimits`를 받으며 구형 계약은 거절한다. 하루 앱 입력/출력 예산을 분당 공급자 토큰 한도와 비교하지 않는다. UTC 또는 태평양 날짜가 바뀌면 이전 준비 보고서를 재사용하지 않는다. 이 숫자 검증 자체가 실제 잔여 한도나 전송 허가는 아니다.
- `analysis-images.ts`: 서버가 명시적으로 제공한 합성 자료 승인만 사용한다. 가이드·전체 manifest·모든 대상/문맥 step·개별 파일 SHA-256·유효기간·철회를 묶고 현재 처리 시도의 대표 프레임 키만 읽는다. 임의 URL/경로·다른 가이드·원본·썸네일·이전 시도·같은 이름으로 교체된 파일은 거부한다.
- 이미지 제한: 최대 2 MiB/4096×4096, 유한 스트림 조각 수, 기본 4.5초(설정 최대 5초), 단일 baseline JPEG만 허용한다. EXIF/다중 이미지/뒤따르는 데이터/누락된 표를 거부하며 FFmpeg로 실제 RGB 한 프레임을 디코딩하고 픽셀을 즉시 버린다. 프로세스는 shell 없이 숨겨 실행하고 pipe만 허용한다. 읽기 취소/만료 때 스트림과 디코더를 중단하고 늦게 도착한 스트림도 닫는다. 임시 이미지·공개 URL·원문 오류 로그를 만들지 않는다.
- dispatcher는 이미지 읽기 함수에 실행의 manifest fingerprint를 전달한다. **실제 로더·공급자 한도 계산기·readiness의 서버 시작 연결은 추가하지 않았다.** 기본 새 분석 요청 503, Google 호출 없음, 운영 DB/Storage 호출·migration·푸시·배포 없음.

### 이번 범위 밖 / 다음 단계 B5-B3b

1. 현재 공급자 계산기는 **한도 검토 함수이지 분산 속도 제한 장치가 아니다.** 실제 전송 잠금 안에서 공유 DB 원장을 읽고 다음 시도를 원자적으로 차감하는 연결이 필요하다. 같은 프로젝트의 다른 키/앱 사용량도 포함하거나 차단해야 하며, 실제 공급자 여유를 보장하지 않는다.
2. 전체 프롬프트·schema·메타데이터·최대 대상/문맥 이미지의 모델별 입력 토큰 상한은 미완성이다. 성공한 이미지 2장의 사용량을 최대 입력 상한으로 사용하지 않는다. 이번에 `countTokens`나 분석 API로 이미지를 보내지 않았다.
3. 합성 승인 생성/철회와 키-프로젝트 무료 등급 근거를 확인하는 실제 readiness 어댑터는 미구현이다. 로더의 해시 일치는 **내용이 합성이라는 자동 판정이 아니다.** 전송 직전 readiness도 같은 입력 승인의 철회/만료를 확인하도록 통합해야 한다.
4. 실제 Replit DB/Storage 읽기·재시작·운영 조건과 제한 실호출은 B5-B4/C에 남는다. B5-A 실제 PostgreSQL 17개는 이전 기록이며 이번 변경에서 재실행하지 않았다.

### 최종 로컬 검증

`npm run check` 재실행 결과: **processor 385 + client 4 = 총 389개 통과, 실패/건너뜀 0**, 타입 검사·processor 빌드·린트·Site 빌드 통과. 새 시험은 한도 8개 + 이미지 20개 + 날짜 경계 접수 1개 = **29개**이며 기존 접수/dispatcher 경계 시험도 강화했다. 실제 LocalStorage·합성 JPEG·FFmpeg 디코딩은 사용했지만 Google/운영 저장소/실제 DB는 호출하지 않았다.

첫 전체 검사는 동시 프로세스 실행 중 Node 메모리 부족으로 중단됐다. 시험을 삭제/건너뛰지 않고 `processor:test`의 파일 동시 실행 수를 2로 제한한 뒤 위 전체 검사를 재통과했다. 기존 Vite 설정/라우트 자동 분류 안내는 남아 있다. 소스·문서의 키 포함 여부는 값 노출 없이 검사하여 발견되지 않았고 `git diff --check`를 통과했다. UI/호스팅·모델·실제 키·환경·DB migration은 변경하지 않았다.
