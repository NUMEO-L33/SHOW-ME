# 제작 의도와 편집 내용 서버 저장 — 2026-09-17

대상: `codex/replit-migration-hardening`, `46386de` 이후 보완본.
이 문서는 이전 [브라우저 전용 의도 저장 단계](REPLIT_INTENT_AND_JOB_UI.md)의 저장 범위를 확장한다.

**후속 변경:** 아래 수동 저장 UI는 `5ba696d` 당시 기록이다. 최신 편집 저장 UX와 추가 검증은 [비공개 편집 자동 저장](REPLIT_AUTOSAVE.md)을 따른다.

## 이번에 연결한 범위

- 합성/실제 영상 추출 후 최초 제작 의도(목적·대상·추가 요청)를 비공개 서버 초안에 저장한다. 이미 서버에 저장된 초안은 브라우저의 오래된 의도로 덮어쓰지 않는다.
- 편집 화면의 **서버 저장**으로 제목, 설명, 직접 지정한 누를 위치, 단계 합치기·제거를 함께 저장한다. 저장 확인 후 새로고침하면 서버 내용을 다시 불러온다.
- **제작 의도 수정 → 서버에 함께 저장**은 제작 의도와 현재 편집 내용을 함께 저장한다. 수동으로 고친 제목을 목적 문구로 바꾸지 않는다.
- 저장 중·미저장·실패·충돌을 구분한다. HTTP 200만으로 성공 처리하지 않고, 응답의 작업 ID·버전·영상 식별값·문서 내용이 요청과 일치해야 저장됨을 표시한다.
- 실패 시 현재 입력을 남긴다. 두 창의 동시 수정은 버전 충돌로 거부하며 자동 덮어쓰지 않는다. **최신 저장본 불러오기**는 미저장 입력을 버린다는 확인 후 실행하고, 읽기 실패 시 입력을 보존한다.
- 저장 자체가 완료됐지만 응답만 끊긴 경우 동일한 직전 요청을 안전하게 재시도할 수 있다. 다른 수정이 더 진행됐다면 충돌로 처리한다.
- 원래 없던 누를 위치를 임의로 표시하지 않는다. 사용자가 화면/방향키로 지정한 뒤부터 표시한다.

일반 편집은 자동 저장이 아니다. 저장하지 않은 변경은 새로고침/창 닫기 때 잃을 수 있어 경고한다. 제작 의도 입력 도중에는 전송하지 않으며 최초 추출 완료 시와 명시적인 서버 저장 시 전송한다.

## 안전 경계와 저장 구조

- 기존 `guide_drafts` JSONB와 저장소 트랜잭션을 재사용한다. SQL 마이그레이션, 의존성/잠금 파일, Nix 변경은 없다.
- `GET/PUT /api/guides/:guideId/draft`는 해당 작업의 편집 키가 필요하다. GET은 초안을 생성하지 않는 읽기 전용이다. PUT은 JSON 64 KiB 제한, 엄격한 필드/문자수/좌표/소유 프레임 검증을 거친다.
- 저장은 부모 작업 잠금 아래 영상 식별값과 초안 버전을 확인한다. 삭제·실패·재처리 중 작업에는 편집을 저장할 수 없다.
- 원본 영상과 추출 프레임은 바꾸지 않는다. **이 단계 삭제**는 편집 목록에서만 제거하며, 원본/추출 객체 삭제는 기존 **전체 삭제** 흐름으로 한다. 전체 작업 삭제 시 서버 초안도 제거된다.
- 기존 비공개 작업 보관 기한과 접근 키 정책을 그대로 따른다. 서버 저장은 영구 보관이나 다른 기기 로그인 복구 기능이 아니다. 현재는 이 브라우저의 복구 키를 잃으면 편집 접근도 잃을 수 있다.
- 이미지 읽기, AI 실행/예약/과금은 이 저장 API에서 수행하지 않는다. 개인정보 검토 상태도 `pending`이며 실제 영상의 가림·공개 공유는 계속 비활성 상태다.
- `main` 병합, Publish, 실제 Gemini 전송 및 운영 DB 직접 변경은 하지 않았다.

## 검증 결과와 한계

로컬 Windows / Node 24.15.0에서:

- 이관 안전 61개 + 서버 493개 + 클라이언트 31개 = **585개 통과, 실패·생략 0**.
- 라이브러리, API/ShowMe 앱 및 테스트, mockup, scripts 타입 검사 통과. API와 ShowMe production 빌드 통과.
- 기존 UI 세 파일의 소스맵 경고는 남아 있다. ShowMe JS 번들은 약 527 kB(압축 약 163 kB)이며 500 kB 경고가 새로 발생한다. 경고 임계값을 올려 숨기지 않았다.
- 격리 Chrome + 실제 로컬 HTTP API + 실제 JSON 저장소 + 실제 FFmpeg로 개인정보/음성 없는 3장면 영상을 업로드했다. 최초 의도 저장, 제목/설명/좌표 저장과 새로고침, 의도 수정, 503 실패, 커밋 후 응답 손실/재시도, 두 탭 충돌과 명시적 재읽기, 합치기/단계 제거, 전체 삭제를 확인했다. 페이지 오류 0, AI 호출 0.
- 320/390/640/768px 가로 넘침 검사 및 모바일 제목 저장/재열기 통과. 390px와 데스크톱 화면을 별도 이미지로 확인했다.
- PostgreSQL 경로는 트랜잭션 대역으로 부모 잠금과 실패 롤백을 검사했다. 실제 PostgreSQL 엔진/실제 Replit DB에 연결한 검사는 아니다. 이 환경에는 격리 PostgreSQL 실행 도구가 없어 아래 실환경 확인이 남는다.
- 첫 회귀 검사에서 기존 `save-draft`의 문서 누락 거부가 약해진 오류를 발견해 구현을 수정했고 기존 테스트는 유지했다. 새 명령의 누락 필드 검사도 추가했다. 첫 브라우저 검사의 모바일 넘침도 구현을 고친 뒤 재검증했다. 검사를 생략하거나 성공 조건을 낮추지 않았다.

## Replit에서 다음 확인

[안전 반영 순서](REPLIT_UPDATE.md)에 따라 변경 없는 브랜치만 fast-forward로 갱신한다. `.env`/키를 출력하거나 DB를 초기화하지 않는다.

```sh
git status --short --branch
git log -1 --oneline
```

변경이 없고 예상한 브랜치인 경우에만 기존 Workflows를 중지한 뒤:

```sh
git pull --ff-only &&
node scripts/run-tests.mjs &&
PORT=20116 BASE_PATH=/ pnpm run build
```

성공 뒤 기존 Workflows만 재시작한다. 같은 포트의 서버를 Shell에서 중복 실행하지 않는다.

1. 개인정보 없는 합성 영상을 선택하고 목적을 입력해 추출한다. **현재 편집 내용이 서버에 저장되어 있어요**가 나타나는지 확인한다.
2. 제목과 1단계 설명을 바꾸고 화면을 눌러 위치를 지정한다. **서버 저장** 완료 뒤 새로고침하여 세 값이 그대로인지 확인한다.
3. 제작 의도를 수정·저장하고 다시 열어 확인한다. 기존 설명과 직접 수정한 제목이 유지되어야 한다.
4. 필요하면 두 탭에서 같은 작업을 열어 한쪽 저장 후 다른 쪽의 오래된 저장이 충돌로 거부되는지 확인한다. 입력을 버려도 될 때만 최신 저장본을 불러온다.
5. 검증용 영상의 **전체 삭제**를 명시적으로 실행하면 삭제 전용 화면을 거쳐 완료 응답 뒤 홈으로 돌아가야 한다. 오류/404를 삭제 성공으로 간주하지 않는다.

이 과정을 통과하기 전에는 실제 Replit 서버 저장까지 확인됐다고 보고하지 않는다. AI 설명 생성·개인정보 영구 가림·공개 공유는 다음 개발 범위다.
