# B5 후속: 운영 확인 기록의 영속 저장과 철회

2026-09-19. [운영 확인 분리 결정](ANALYSIS_OPERATIONS_SEPARATION.md)의 후속 구현이다. 원본 개발 계획과 기존 요구 문서는 수정하지 않았다. 이 단계는 **내부 저장 기능과 임시 PostgreSQL 검증**이며 실제 운영 승인을 발급하거나 AI를 활성화한 작업이 아니다.

## 구현 범위

- `analysis-operations-store.ts`의 `PostgresAnalysisOperationsStore`가 운영 기록 작성/갱신(`put`), 철회(`revoke`), 최신 기록 조회(`readLatest`)를 제공한다.
- 새 마이그레이션 `0011_analysis_operations_reviews`는 빈 이력 테이블과 제약만 추가한다. 기존 0000–0010은 변경하지 않고, 승인 기록·권한·자동 활성화를 추가하지 않는다.
- 배포별 증가 버전과 예상 버전 비교로 오래된 화면/프로세스의 덮어쓰기를 거절한다. 같은 명령 ID와 내용의 재시도는 기존 영수증을 반환하며 중복 저장하지 않는다. 같은 ID의 다른 내용/작성자는 충돌이다.
- 저장 API는 과거 행을 수정/삭제하지 않고 새 행을 추가한다. 철회 시 원래 관측·작성·만료 시각을 보존한다. 가이드 삭제에 기록이 연쇄 삭제되지 않는다.
- `pending`은 미확인을 보존할 수 있지만 승인이 아니다. `approved`는 기존 다섯 확인 항목·대상·정책·시각 조건을 모두 통과해야 한다. 현재 시각은 DB에서 읽는다. 오래된 관측의 유효기간을 새 저장으로 연장할 수 없다.

## 권한과 신뢰 경계

쓰기 허용 역할의 기본값은 빈 목록이다. 허용 목록은 신뢰하는 서버 구성에서만 주입하며 요청 본문이나 환경 JSON으로 받지 않는다. PostgreSQL이 인증한 `session_user`와 `current_user`가 같고 허용 목록에 있어야 한다. `SET ROLE`로 운영자 행세를 하는 요청은 거절한다. 작성자의 `reviewerRef`도 실제 DB 역할에서 만든 참조와 일치해야 한다.

이것은 **DB 주체 인증**이다. 공유 DB 로그인만으로 개별 사람의 신원을 증명하지 않는다. 역할 해시는 익명성 보장이 아니며, 실제 운영에는 분리된 로그인/최소 권한과 운영자 인터페이스의 인증 경계가 필요하다. 이번에는 운영 DB 역할 생성·권한 부여·키 변경을 하지 않았다. 검사 속 `postgres` 허용은 폐기되는 로컬 DB 전용이다.

DB 관리자에게도 변조 불가능한 원장은 아니다. 특권 DB 사용자는 직접 SQL로 행을 바꿀 수 있다. 조회 시 형식·행과 payload의 대응을 검사하지만 클라우드 근거의 진실성을 자동 증명하지 않는다. 기존 DB 런타임 probe의 검사 통과도 새 운영 이력의 운영자 권한 분리 전체를 증명하지 않는다.

## 철회와 실행 차단

실제 기록 변경은 기존 접수·계수·생성 전송 경로와 같은 **전역 제어 행 잠금**을 먼저 획득한다. 기록 추가와 `halted:true` 저장은 한 트랜잭션이다. 어느 쪽이 실패하거나 DB 정책/트리거가 중지 상태 갱신을 조용히 생략해도 모두 롤백한다. 중지 제어 행이 없거나 잘못되면 자동 복구하지 않고 거절한다.

- 철회뿐 아니라 대기/승인 기록의 신규 저장·갱신도 해당 DB의 분석 실행을 전역 중지한다. 배포별 기록 저장이지만 중지는 해당 DB를 공유하는 전체 분석에 적용된다.
- 변경이 먼저 커밋되면 다른 프로세스의 새 접수와 아직 시작하지 않은 계수·생성 전송은 기존 공통 중지 검사에서 차단된다. 이미 확보한 계수 실행 표도 예외가 아니다.
- 먼저 시작된 외부 요청의 전송을 되돌리는 기능은 아니다. 클라우드 설정 변경 자체를 즉시 발견하는 감시 기능도 아니다.
- 기록 작성 결과는 항상 `authorizesAnalysis:false`다. 승인 기록을 저장해도 자동으로 중지를 해제하지 않으며, 이 저장소에 재개/활성화 API는 없다.
- 같은 명령을 재시도하여 받는 과거 영수증은 **현재 승인 상태가 아니다**. 이후 철회·갱신된 상태는 `readLatest`에서 조회해야 한다. 이 조회 자체도 실행 허가를 발급하지 않는다.

## 실패·취소 처리

작업 기한은 최대 5초이며 DB 문장/잠금 대기에도 별도 제한이 있다. 취소 후 늦게 연결되면 SQL 없이 반환한다. 미완료 작업이 실제로 끝날 때까지 동일 저장소 인스턴스의 새 작업을 받지 않는다. 트랜잭션 오류는 롤백하며, 롤백 실패 시 자신이 확보한 연결만 폐기한다. 원본 DB 오류·SQL·기록 내용은 외부 오류로 노출하지 않는다.

커밋 응답을 잃거나 커밋 직후 취소되면 호출자는 오류를 받더라도 DB에 저장됐을 수 있다. 자동 재시도하지 않으며 **같은 명령 ID와 내용**으로 재확인한다. 다른 ID로 다시 쓰면 새 작업이므로 이를 복구 수단으로 사용하지 않는다.

## 검증 기록

- 새 단위 검사 10개: 기본 권한 거절, DB 주체 결합, 잘못된 승인 거절, 중복/CAS, 커밋 응답 유실, 원자적 중지, 취소/지연 연결, 비공개 오류, 시작 경로 미연결을 검사한다.
- 실제 PostgreSQL 16.15 최종 검사 **80개 통과, 실패·취소·생략 0**. 이 중 새 운영 저장 관련 검사는 10개다. 독립 연결의 재조회, 12개 중복 요청/8개 갱신 경쟁, 역할 변경 차단, 철회 이력, 부분 실패 및 조용히 생략된 중지 갱신의 롤백, 프로세스 간 전송 차단과 잠금 순서를 확인했다.
- 새 마이그레이션으로 총 12개가 되었는데 기존 검사의 기대값이 11이어서 최초 DB 실행은 79/80이었다. 기대값과 범위 설명을 0000–0011로 맞춘 뒤 전체 재실행을 통과했다. 안전 검사 제외나 제한 완화는 하지 않았다.
- API 제품/테스트 TypeScript 검사와 서버 빌드 통과. 프런트엔드 코드는 변경하지 않았고 프런트엔드 빌드는 다시 실행하지 않았다.
- 최종 일반 전체 회귀 **792개(이관 91 + 서버 615 + 클라이언트 86)** 통과, 실패·취소·생략 0, 종료 코드 0. 기존 격리 실행기로 앱 환경/비밀값을 제외했으며 기존 테스트용 FFmpeg/ffprobe만 사용했다. 위 실제 PostgreSQL 80개는 별도 실행 결과다.
- 사용자가 Docker 실행을 확인한 뒤 기존 로컬 이미지만 사용했다. 루프백 포트·임시 메모리 저장소·일회용 자격증명의 독립 컨테이너에서 검사했으며 실행별 컨테이너/DB 자동 정리를 확인했다. 개인 영상, Replit DB/Storage, 앱 비밀값, 실제 AI 호출을 사용하지 않았다.

## 남은 연결과 배포 상태

1. 실제 운영자 로그인/최소 권한 구성, 인증된 작성·철회 진입점, 최신 DB 기록과 준비 상태 소스의 안전한 연결은 아직 없다. 운영 확인 내용도 실제 근거로 채워야 한다. 미확인을 승인으로 채우지 않는다.
2. 전체 요청의 검토된 입력 토큰 상한은 여전히 미확정이다. 과거 측정치를 다른 입력에 일반화하지 않는다.
3. 위 조건을 해결한 뒤 승인된 합성 자료에 한해 실행 연결을 검증한다. 활성화·개인 영상 외부 전송은 별도 문제이며 이번 작업으로 허용되지 않는다.

변경은 로컬 작업본에만 있다. 운영 DB 마이그레이션, 커밋/푸시, Replit 재시작/배포, 사용자 capabilities 활성화는 하지 않았다. 서버 시작 경로와 HTTP 라우터에는 운영 저장소를 연결하지 않았으며 기존 AI 기본 차단을 유지한다.
