# 저장소 접근·장애 정리 점검 — 2026-09-23

## 판정

정상 게시/철회 통합 검사는 앞선 단계에서 통과했다. 읽기 전용 점검에서는 익명 목록 접근 차단과 현재 프로젝트 접근자 표시를 확인했다. **전체 bucket IAM/객체 ACL 감사 완료는 아니다.** SDK 실패 응답 이후 늦은 저장의 정리 기록 소실을 로컬 모형으로 재현했고, 후속 승인으로 해당 기록 보존을 보완하여 **Replit 개발 API에 `135a61c`를 반영·재시작·검증했다.** 원격 업로드 종료 자체를 확인/취소하는 기능을 완성한 것은 아니다. 공개 실행기 OFF를 유지하며 운영 해소 조건은 별도로 남는다.

감사 기준 소스는 `18c9533`이다. 최초 접근 감사에서는 제품 코드·환경·권한·DB·저장소 객체를 변경하지 않았다. 그 뒤 로컬 제품 코드·합성 테스트·진행 기록을 보완했고, 다음 승인 단계에서 개발 API만 갱신·재시작했다. 개인 영상·외부 AI·운영 Publish·SDK 교체는 하지 않았다. 원래 개발 MD 목표/완료 조건은 유지한다.

## 후속 보완 — 실패 응답과 원격 쓰기 종료를 분리

- `StorageWriteSettledError`는 신뢰된 어댑터가 ‘이 호출로 더는 쓰기가 발생하지 않는다’고 보장할 때만 사용한다. LocalStorage의 전부 await된 파일 작업 실패, Replit SDK를 호출하기 전 파일/키 검증 실패가 해당한다. 부분 파일은 남을 수 있으므로 기존 삭제 절차는 그대로 필요하다.
- Replit SDK 호출 이후의 오류 결과/예외는 종료 불명으로 취급한다. HTTP 상태 코드·현재 파일 부재·delete 성공·경과 시간으로 확정 종료를 추론하지 않는다. 성공 응답은 기존처럼 완료로 처리한다.
- renderer 밖의 호출별 상태에 미확정 쓰기를 기록한다. 독립 E2와 게시 준비 모두 그 상태가 남으면 `settle`을 실행하지 않는다. 뒤이은 임시 파일 정리나 조회 오류가 원래 오류를 가려도 이 상태는 유지된다.
- 실패한 게시 작업을 닫고 예약된 정확한 key를 삭제하되, `writerSettled=false`인 원장은 남긴다. 이후 정리/복구가 같은 key의 늦은 객체를 다시 삭제할 수 있으며, guide 최종 삭제는 완료로 보고하지 않는다. put 자동 재시도·타이머 기반 강제 settle·권한 우회는 추가하지 않았다.
- 기존 정상 저장, 확정된 로컬 실패, read-back 오류, 아직 진행 중인 put의 늦은 성공과 취소 정리 동작은 유지한다. DB schema/migration 변경은 없다.

- LocalStorage/SDK 사전 검증과 SDK 오류 코드별 분류 검사를 추가했다. 확정된 부분 쓰기 기존 테스트는 실제 로컬 쓰기 종료를 보장하는 대역임을 명시했다.

## 접근 점검 증거와 한계

| 항목 | 관측 | 해석 범위 |
| --- | --- | --- |
| 프로젝트 접근자 | SHOW-ME 초대창의 접근 목록에 현재 소유자 한 명만 표시 | 표시된 협업자 목록 확인. 조직 관리자·사업자 권한 전체 감사는 아님 |
| 초대 링크 | 복사를 눌러 생성하라는 비활성 입력만 표시 | 생성·복사·초대·권한 변경은 하지 않음. 과거 모든 링크 부재의 증명은 아님 |
| App Storage 설정 | 선택된 프로젝트 bucket의 ID와 삭제 버튼만 표시 | IAM/객체 ACL/보존 정책을 열람하는 항목은 확인되지 않음. 삭제 버튼 미사용 |
| 앱 대상 일치 | 셸의 명시적 bucket ID가 UI 선택 bucket과 일치 | 값은 이 기록에 보관하지 않음 |
| 익명 목록 접근 | 인증·쿠키 없는 GCS JSON objects.list가 HTTP **401**, `DENIED` | 목록 권한 차단만 확인. 개별 객체 직접 읽기/전체 ACL은 미검증 |

익명 요청은 해당 bucket 하나의 `objects.list`에 `maxResults=1&fields=kind`를 지정했다. 파일명/객체 본문은 요청하지 않았고 응답 본문을 출력하지 않았다. 자동 인증 SDK나 sidecar 토큰을 이 요청에 사용하지 않았다. 프로젝트 ID와 bucket ID가 관측값과 다르면 요청하지 않도록 했다. 재시도·다른 bucket 탐색은 없었다.

공식 영문 [App Storage 문서](https://docs.replit.com/features/data-and-storage/object-storage)는 현재 bucket이 생성 프로젝트 전용이며 다른 프로젝트에 연결할 수 없다고 설명한다. 일부 번역본에는 과거 앱 간 공유 설명이 남아 있어 현재 영문 설명과 실제 UI를 우선했다. 이 문서의 일반 설명은 특정 bucket의 IAM 검증을 대체하지 않는다. [GCS objects.list](https://docs.cloud.google.com/storage/docs/json_api/v1/objects/list)는 목록 조회와 객체 ACL 조회 권한을 구분한다.

설치된 `@replit/object-storage` **1.0.0** 공개 타입은 객체 작업을 제공하지만 IAM/업로드 세션 취소·조회 메서드는 제공하지 않는다. 웹 SDK 문서에 나오는 `getBucket`은 설치된 타입에서 private다. 숨은 메서드를 호출하거나 인증 토큰을 추출해 우회하지 않았다.

## 장애 경로 재검증

기존 `privacy-assets`, `publication-preparation`, `publication-recovery` 집중 검사 **42개 전부 통과**, 실패·취소·생략 0, 종료 코드 0, 약 18.7초다. 앱 환경변수는 기존 allowlist 시험 환경으로 제외하고 .env를 읽지 않았다. 합성 자료와 일회용 로컬 JSON/LocalStorage만 사용했다. 실제 Replit에 장애를 주입하거나 연결을 끊지 않았다.

기존 검사가 확인하는 보호:

- 아직 끝나지 않은 put을 timeout만으로 끝났다고 판단하지 않음.
- 실제 진행 중인 put이 늦게 완료되면 그 뒤 출력을 정리함.
- 프로세스 재시작으로 `writerSettled=false`가 남으면 기록과 삭제 차단을 유지함.
- 삭제 실패/지연에서 정리 기록을 남기며 다른 batch·원본·초안을 보존함.

그러나 이는 **put Promise가 거절된 뒤 저장소 측 쓰기가 늦게 완료되는 경우**와 다르다.

## 발견 사항: 실패 응답 뒤 늦은 저장의 정리 기록 소실

수정 전 `storage.ts`는 Replit SDK의 `uploadFromFilename` 실패를 예외로 변환했다. `publication-preparation.ts`의 catch는 해당 예외 후 `settle(...receipts:null)`을 실행하며, `privacy-asset-cleanup.ts`는 삭제 응답과 이 settled 상태를 근거로 기록을 없앴다. 독립 E2의 `privacy-asset-writer.ts` catch에도 같은 settled 처리 형태가 있었다.

별도 로컬 진단에서 합성 fixture와 메모리 저장소로 다음 순서를 제어했다:

1. 모의 저장소가 PNG 바이트를 받지만 클라이언트에 실패 응답을 반환한다.
2. 기존 준비 함수가 실패 처리/삭제를 수행하고 자산 정리 기록을 제거한다.
3. 모의 저장소가 그 뒤 같은 key에 바이트를 확정한다.
4. 기존 정리 함수를 다시 호출한다.

관측 결과:

```json
{"event":"SIMULATED_LATE_COMMIT_AFTER_REJECTION","realRemoteUsed":false,"ledgerAfterError":0,"ledgerAfterCleanup":0,"cleanupReportedComplete":true,"lateObjectRemains":true}
```

진단 종료 시 메모리 객체를 비우고 `SYNTHETIC_PROBE_LOCAL_FIXTURE_REMOVED`를 확인했다. 제품 코드/상시 테스트 파일은 수정하지 않았다. 진단 exit 0은 위 조건의 관측과 자체 정리 완료를 뜻하며 제품 안전성 PASS가 아니다.

**실제 Replit에서 늦은 commit이나 유출을 관측한 결과는 아니다.** 이것은 저장소 실패 응답이 원격 작업 종료를 보장하지 않을 때 현재 코드에 생기는 공백이다. 정상 통합 검사의 시험 객체 네 개 삭제 확인을 취소하는 결과도 아니다. 모의 실패 경계에 대한 보강이 필요하다는 별도 근거다.

설치 SDK의 파일 업로드는 내부 GCS `bucket.upload`에 전달되며 외부에 업로드 세션 식별자/취소 확인을 반환하지 않는다. GCS의 [resumable uploads](https://docs.cloud.google.com/storage/docs/resumable-uploads) 및 [세션 취소](https://docs.cloud.google.com/storage/docs/performing-resumable-uploads) 문서는 업로드 세션과 완료된 객체를 구분한다. 일반 delete 성공/객체 부재/프로세스 종료만으로 세션 취소를 증명할 수 있다고 해석하지 않는다. 세션의 최대 기간을 임의의 안전 대기시간으로 제품에 적용하지 않는다.

## 운영 대응 절차 — 현재 가능한 범위

| 상태 | 대응 | 완료로 표시하면 안 되는 조건 |
| --- | --- | --- |
| 새 게시 준비 장애 | 새 게시 접수를 닫고 해당 guide/job/batch와 시각을 보존 | 단순 재시작·lease 만료·실패 응답만으로 writer 종료 처리 |
| 이미 공유 중인 자료 중지 | 기존 소유자 인증과 관측한 version으로 철회, 이전 URL 차단 확인 | 버전 충돌을 무시한 강제 중지나 자동 재게시 |
| writer 정상 종료가 확인된 삭제 실패 | 정확한 batch의 기존 정리 경로를 재시도하고 결과 확인 | 원장보다 넓은 prefix/버킷 전체 삭제 |
| writer 종료 불명·응답 유실 | 정리 대기로 유지, 자동 put 재시도 금지, 사업자 확인 또는 지원되는 세션 취소 증거 확보 | 일시적인 404/exists:false/타이머만으로 원장 제거 |
| 삭제 확인 | 정확한 key 부재와 관련 원장 완료를 확인 | 사업자 백업·soft delete·과거 generation까지 즉시 제거됐다고 단정 |

위 절차는 강제 삭제/settle용 새 운영 도구가 아니다. **원장 보존 보완은 개발 API까지 반영됐지만, 불명 업로드의 종료 확인까지 해결한 것은 아니다.** 현 앱 공개 실행기는 꺼진 상태이며, 이번에는 실행기/권한 설정을 변경하지 않았다.

2. 원장 보존/재삭제 보완을 불명 업로드의 영구 종료로 해석하지 않는다. 단순히 모든 실패 기록을 영원히 남기는 것으로 운영 완료를 주장하지 않는다.
3. 지원되는 업로드 세션 추적/취소 또는 사업자 확인으로 불명 기록을 해소하는 방식을 정한다. SDK 교체·새 자격증명/권한·실환경 장애 주입은 별도 범위로 승인받는다.
4. Replit에 특정 bucket의 익명 객체 읽기 차단/IAM 확인 방법, 불명 업로드 종료 확인 방법, soft-delete·versioning·백업 보존 범위를 확인한다. 현재 UI/공개 SDK만으로 확인하지 못한 항목을 통과로 바꾸지 않는다.
5. 보완·검증 후 별도 승인으로 공개 실행기를 활성화하고 실제 수신자/모바일 검사를 진행한다.

필요시 사업자 문의 초안(아직 발송하지 않음): “App Storage의 프로젝트 전용 bucket에 대해 익명 객체 읽기와 상속 권한을 확인할 수 있는 공식 방법, 업로드 응답 유실/앱 종료 후 잔여 세션을 확인·취소하는 지원 방법, 객체 삭제 뒤 soft-delete·versioning·백업 보존 정책을 안내해 주세요.” 키·세션 URI·영상·객체 내용을 보내지 않는다.
