# 게시 준비와 가림 이미지 저장 연결 — 2026-09-21

기존 계획 E3의 다음 내부 단계다. 게시 요청이 예약한 자산 묶음을 실제 E2 이미지 생성·저장에 연결했다. **이미지 준비 완료는 게시 완료가 아니다.** 공개 링크·불변 게시본 확정·HTTP·화면 버튼·자동 작업 루프는 아직 연결하지 않았다. 원래 개발 계획의 목표·완료 조건은 변경하지 않았다.

후속 `PUBLICATION_COMMIT.md`에서 별도 내부 확정을 구현했다. 준비 함수가 자동 게시하지는 않는다. `cleanupPublicationPreparation`은 이후 성공 작업이라도 자산이 이미 cleanup으로 전환된 이전 게시 묶음은 정리하며, 현재 활성 ready 묶음은 보존한다. 아래 확정 미구현·JSON v7·검증 개수는 준비 단계 당시 기록이며 최신 상태는 후속 문서를 따른다.

## 연결 계약

- `preparePublicationAssets`는 대기 작업 ID와 version만 받아 직접 새 writer lease를 한 번 claim한다. 이전 실행의 running 작업/lease를 재구성해 원격 쓰기를 반복하지 않는다. 이미 예약한 `job.batchId`만 쓰며 새 자산 묶음을 만들지 않는다.
- 공통 `privacy-asset-session`으로 기존 단독 E2 저장 함수와 같은 프로세스당 1개 작업 제한을 사용한다. 제한시간은 최대 120초다. 호출자가 취소/시간 초과를 받더라도 실제 저장·정리가 끝날 때까지 슬롯을 반환하지 않는다.
- 원본 합성 JPEG를 읽는 것부터 가림 PNG/썸네일 생성, 비공개 저장, 길이/SHA-256 재확인까지 기존 엔진을 재사용한다. 가림 실패 시 원본이나 미가림 썸네일로 대체하지 않는다. 신뢰한 work 디렉터리 아래 임시 파일은 실제 작업 종료 후 정리한다.
- 이미지 처리 경계마다 소유권·현재 초안/확인 지문을 검사한다. 처리 도중에도 250ms 간격으로 검사하며 한 번에 하나의 DB 검사만 수행한다. 편집·취소·삭제·lease 만료가 확인되면 호출자와 변환 중단 신호에 전달한다. DB/저장소가 응답하지 않으면 정상 종료를 추정하지 않고 전체 제한시간/소유권 기록을 유지한다.
- 마지막 `complete-assets` 명령은 부모 가이드 잠금 안에서 현재 입력을 다시 확인하고 **자산 ready/receipt와 작업 assets-ready를 한 트랜잭션에 기록**한다. JSON도 단일 원자적 파일 교체다. DB 오류나 조용히 무시된 쓰기에서 한쪽만 준비 완료로 남기지 않는다.
- 최종 저장 응답을 잃었을 때는 이 호출이 만든 lease와 저장된 준비 상태를 다시 확인할 뿐 이미지 변환/업로드를 반복하지 않는다. claim 응답을 잃었을 때는 이미지 I/O를 시작하지 않으며 자기 lease가 확인될 때만 취소·정리한다.
- 실패 시 내부 `abandon`은 정확히 같은 lease만 작업을 멈출 수 있다. 실제 이미지 I/O가 끝난 뒤에만 writer 종료를 기록한다. `cleanupPublicationPreparation`은 실패/취소된 작업의 정확한 자산 묶음만 재정리하며, 다른 묶음·원본·초안은 건드리지 않는다.

## 중단 복구의 남은 범위

살아 있는 프로세스에서 취소를 무시한 저장이 늦게 끝나는 경우, 실제 종료를 기다렸다가 출력 키를 다시 지우는 경로를 검사했다. 정리 실패는 원장을 보존하며 재접속 후 해당 작업 정리만 재시도할 수 있다.

**원격 저장 도중 프로세스 자체가 죽은 경우는 아직 자동 해결하지 않는다.** lease 만료만으로 원격 쓰기가 끝났다고 볼 수 없다. 그 기록은 계속 삭제 완료를 막는다. 전역 정리 발견/자동 실행 루프와 불확실 원격 쓰기 해소 절차, 실제 Replit Storage의 늦은 commit 검증은 남아 있다. 현재 내부 함수를 일반 사용자 기능으로 노출하지 않은 상태다.

후속 구현: `PUBLICATION_RECOVERY.md`의 내부 루프가 만료 job과 terminal job의 남은 자산을 순환 조회·정리한다. 제품 시작 연결과 불확실 원격 쓰기 해소는 여전히 미완료다. 위의 자동 루프 미구현 설명은 이 연결 단계 당시의 기록이며 후속 구현 범위와 구분한다.

## 배포 경계

이 연결 자체는 추가 DB migration이 없다. 앞선 E2/E3의 0013/0014 및 JSON v7을 사용한다. Replit migration·기존 실행 역할 권한 변경·pull·재시작·배포는 수행하지 않았다. .env·키·개인 영상·실제 외부 AI도 사용하지 않았다. 기존 원본 공유 기본 차단과 일반 AI off를 유지한다.

## 검증 기록

- 새 일반 검사 16개: 실제 합성 JPEG → 가림 PNG/썸네일 → 기존 단일 묶음 저장/재읽기, 재접속, 12개 동시 실행, 기존 running lease 재사용 거절, 편집/전체 삭제/취소 경합, 비협조적 변환·늦은 저장, 부분 put·손상 readback·변환 실패, claim/최종 저장 응답 유실, 최종 DB 쓰기 실패, 재시작 후 정확한 묶음만 정리, lease 만료 중 불확실 writer 보존, 제품 시작 경로 미연결을 확인했다. 기존 E2/원장 포함 집중 검사 42개 통과.
- 최종 일반 전체 **940개 통과**(이관 99 / 서버 742 / 클라이언트 99), 실패·취소·생략 0, 종료 코드 0.
- 실제 PostgreSQL 16.15 **115개 통과**, 실패·취소·생략 0, 종료 코드 0. 새 4개는 실제 PNG 생성과 DB receipt/작업 동시 저장·독립 연결 복원, 마지막 DB 쓰기 예외 및 조용히 무시된 쓰기의 양쪽 롤백/이미지 정리, 다른 연결의 취소와 진행 중 put/삭제 경합을 검사한다. 0000–0014 migration 적용/재실행도 포함한다.
- 일회용 컨테이너 `showme-b5-826b5e03897d440a8c54a4af84d5a1f9`은 `postgres_fixture_removed`로 정리했다. 이미지 검사는 합성 JPEG와 LocalStorage를 사용했으며 실제 Replit Storage 검증을 뜻하지 않는다.
- 서버 제품/테스트 타입 검사와 서버 빌드 통과. 빌드는 샌드박스 상위 경로 접근 제한 때문에 실패한 뒤, 같은 코드를 권한 환경에서 재검사해 통과했다. 제품 코드 우회나 설정 완화는 없다. 화면 코드 변경/새 브라우저 UI 검사는 없다.
- 현재 변경은 로컬 작업본이며 앞선 원장 변경과 함께 **미커밋·미푸시** 상태다. Replit 반영 완료로 해석하면 안 된다.

## 다음 순서

3. 이후 소유자 인증 게시 API/버튼, 공개 API/뷰어, 원본 공유 명시 선택 및 Replit 실환경 검증을 연결한다.

현재 반환하는 `running / assets-ready`만으로 공유 URL을 만들거나 게시 성공으로 표시하면 안 된다.
