# Replit 이관 안전장치·테스트 복구 — 1–2단계

기준: `f8844eb` / `codex/replit-migration-checkpoint`, 작업일: 2026-09-16.

## 변경 범위

- `scripts/post-merge.sh`에서 scaffold DB의 `push` 호출을 제거했다. 기존 잠금 파일 기반 의존성 설치는 유지한다. 실제 ShowMe SQL migration이나 서버 시작 코드는 바꾸지 않는다.
- `.gitignore`에서 실제 환경 파일·인증 키·로컬 영상/프레임 데이터·도구 상태 제외를 복구했다. `.env.example`은 추적 가능하게 유지한다. 이미 추적 중인 파일은 삭제하거나 추적 해제하지 않는다.
- `.gitattributes`에서 셸 스크립트를 LF로 고정했다. Windows에서 편집 후 Linux의 후처리 실행이 깨지는 것을 방지한다.
- `test:migration`을 추가했다. Node와 Git만 사용하는 읽기 전용 회귀 검사다. 서버 import, `.env` 로딩, 의존성 설치, 후처리 실행, DB/Storage/Gemini 접속은 하지 않는다.

## 1단계 검증 기록

1단계 당시에는 저장소 루트에서 `node --test scripts/tests/migration-safety.test.mjs`를 실행했다. 현재 전체 안전 검사는 `node scripts/run-tests.mjs migration` 또는 `pnpm run test:migration`으로 실행한다. 당시 이 PC의 번들 pnpm 실행기는 설치를 자동 시도했으나 네트워크 권한 오류로 진행되지 않아 중단했고 직접 Node 실행으로 검증했다. 후속 Linux 검증은 아래 2단계 기록을 따른다.

검사 범위: 후처리 명령 제한, 위험 명령 삽입 시 검사 실패, 셸 줄바꿈, 테스트 명령 연결, 가상 비밀/출력 경로의 추적 제외, 예시/소스/SQL 경로의 추적 허용, 기존 미디어 보안 검사 유지, 실제 실행 위치의 과거 SQL/메타데이터 보존. 새 migration 추가는 허용하되 과거 journal 항목의 변경/삭제는 허용하지 않는다.

기존 의존성 설치나 서버 시작을 실행한 검증은 아니다. 이미 추적된 비밀정보를 지우는 기능도 아니며, 비밀정보 전체 감사와 구별한다.

검증 기록: Node 24.15.0 / Windows에서 변경 전 검사 실패로 누락을 재현했고, 보완 후 **42개 통과 / 실패 0 / 생략 0**을 확인했다. 셸 스크립트의 `bash -n` 구문 검사와 `git diff --check`도 통과했다. Replit/Linux에서의 후처리 실제 실행이나 전체 제품 빌드는 이번 범위가 아니다.

## 1단계 당시 다음 순서

1. 보존된 서버 단위 테스트 36개 파일·보조 자료와 클라이언트 테스트를 현재 `artifacts/` 소스를 대상으로 복구한다. 백업 소스에 대한 검사로 대체하지 않는다.
2. 테스트 경로·스크립트·개발 의존성과 별도 PostgreSQL 시험 경계를 복구하고 타입/빌드/기능 회귀 검사를 수행한다.
3. 현 잠금 파일에는 Linux 전용 네이티브 의존성 제외 설정이 있다. Windows 기존 프로젝트에 무작정 설치하지 말고 독립 환경에서 검증한다.

이번 단계에는 Replit 파일 직접 변경, main 병합, Publish, 실제 DB 변경, 저장소/Gemini 호출 또는 자동 분석 활성화가 포함되지 않는다. 로컬 보완본은 Replit에 별도로 반영해야 한다.

- Replit의 사용자 변경부터 확인하고 가져오기·재검증을 진행한다. [반영 순서](REPLIT_UPDATE.md)를 따르며, 원격 업로드 성공 여부는 실제 원격 커밋 확인으로 판정한다.

## 4단계 Replit 재검증 중 테스트 경로 보완 — 2026-09-16

- 사용자가 Replit에서 `11589a0`으로 전환하고 `pnpm install --frozen-lockfile --ignore-scripts`를 완료했다. 이후 `analysis-images.test.ts`의 재확인 횟수 검사에서 `actual: 1 / expected: 2`가 발생했고, 번들 FFmpeg 파일은 없음을 확인했다.
- 원인: 이 파일만 공통 `testMediaPaths()`를 사용하지 않고 `ffmpeg-static` 경로를 직접 참조했다. 이미지 디코딩에서 실패해 두 번째 가이드 조회까지 도달하지 못했다. 이전 Linux 검증은 번들 실행 파일을 별도로 설치해 이 누락을 발견하지 못했다.
- 해당 테스트도 공통 경로 선택기로 통일했다. 모든 미디어 테스트가 같은 선택기를 사용하고 플랫폼 보조 코드 밖에서 번들 경로를 직접 가져오지 못하도록 회귀 검사를 추가했다. 기대값·운영 코드·보안 검사·잠금 파일·설치 스크립트 정책은 바꾸지 않았다.
- 번들 모듈이 존재하지 않는 실행 경로를 반환하도록 시험 프로세스에서만 바꾸고 별도 테스트 도구 경로를 제공했다. 수정 전 같은 `1 !== 2` 오류를 재현했으며, 수정 후 해당 이미지 검사 **20개 통과 / 실패·생략 0**을 확인했다. 실제 설치 파일은 삭제하거나 수정하지 않았다.
- Windows / Node 24.15.0의 기존 로컬 의존성으로 기본 검사 **537개(안전 50 + 서버 483 + 클라이언트 4), 실패·생략 0**과 서버 테스트의 엄격한 타입 검사를 통과했다. 이는 Replit 잠금 의존성·호스트 FFmpeg 8.1.2의 재검증을 대신하지 않는다. 이번에는 전체 제품 빌드를 재실행하지 않았다.
- 앱 환경변수와 `.env`를 사용하지 않고 합성 자료·로컬 파일/HTTP·모의 공급자로 검사했다. 실제 DB/Storage/Gemini 호출, main 병합, 배포는 하지 않았다. Replit에서는 수정본을 받은 뒤 전체 테스트를 다시 확인하고, 통과해야 빌드 단계로 넘어간다.

## 5단계 Replit 이미지 읽기 지연 — 원인 분리 진행 중

- 경로 보완 후 Replit에서는 정상 이미지 읽기가 약 4.5초 제한에서 실패했다. 첫 합성 이미지만 직접 디코딩한 검사는 171ms/156ms였지만, 전체 검사 재실행과 이미지 파일 단독 검사에서도 첫 정상 읽기 검사가 실패했다. 병렬 부하만으로 설명할 수 없으며, 직접 검사에는 두 번째 이미지와 비동기 파일/프로세스 경로가 빠져 있었다. 첫 실행 지연이라는 이전 추정은 확정 원인이 아니다.
- 운영 코드는 변경하지 않고 첫 정상 읽기 테스트에 제한된 이벤트 관찰을 추가했다. 이미지 번호와 호출 순서, 파일 읽기, 디코더 입력·출력·종료 상태를 실패 시 기록한다. 기존 4.5초 제한·기대값·실패 판정은 유지하며, 테스트 후 원래 프로세스 실행 함수를 복원한다.
- `images` 선택지를 추가해 한 명령으로 관련 파일만 실행할 수 있다. 기본 전체 검사 범위는 그대로이며 임의 파일/Node 옵션이나 실제 DB 검사는 허용하지 않는다.
- 로컬에서 지연 프로세스를 주입해 원래 실패가 그대로 유지되고 `IMAGE_LOAD_TRACE`가 파일 읽기 완료·디코더 시작·입력 완료·출력 없음까지 구분하는 것을 확인했다. 실제 바이너리를 교체하거나 운영에 모의 프로세스를 연결한 것이 아니다. Replit의 해당 추적 결과를 받아야 실제 정체 위치를 확정할 수 있다.
- 전체 로컬 재검증 중 정산 종료 검사 3개가 별도로 실패했다. `cancel`은 실제 현재 날짜를 기록하는데 후속 종료 검사는 고정 `2026-09-16T12:00:00Z`를 사용해, 실제 시각이 이를 지나면 정상적인 역행 방어에 걸렸다. 해당 테스트 파일의 Date만 시나리오 시작 시각에 고정했다. 실제 타이머·정산 로직·역행 거부 조건은 그대로다. 이미지 지연의 원인이나 해결로 취급하지 않는다.
- 보완 후 Windows / Node 24.15.0의 기존 로컬 의존성에서 기본 **538개(안전 51 + 서버 483 + 클라이언트 4), 실패·생략 0**, 이미지 단독 20개 및 서버 테스트 타입/실행기 구문/공백 검사를 통과했다. 운영 소스·SQL·잠금 파일·Replit 설정에는 차이가 없다. 전체 제품 빌드·Replit 실환경 성공으로 확대 해석하지 않는다.

## 6단계 Replit 빌드 통과·관찰 없는 이미지 검사 분리

- 사용자가 진단본에서 이미지 단독 20개, 이후 서버 483개와 클라이언트 4개의 실패·생략 0 결과를 제공했다. 이어 전체 타입 검사와 API·ShowMe·mockup 빌드 성공 출력을 확인했다. ShowMe의 기존 세 UI 파일 소스맵 위치 경고는 남아 있다. 이 기록은 사용자가 실행한 Replit 결과이며 이 PC의 실행 결과와 구분한다.
- 관찰 추가 후 통과했다는 사실만으로 지연 원인을 해결했다고 판정하지 않는다. 관찰에 따른 실행 타이밍 변화 가능성을 분리하기 위해 원래 정상 읽기 검사 본문을 첫 검사 `(without tracing)`로 복구하고 관찰 포함 검사는 두 번째 독립 검사로 유지했다. 첫 본문이 `86473c7`의 원래 본문과 같음을 TypeScript 구문 트리에서 추출해 비교했다. 저장소/조회 래퍼나 프로세스 관찰은 첫 검사에 설치되지 않는다.
