# B5-B3b5 — 입력량 계산 실행·실측 보관·생성 연결

갱신일: 2026-09-15 · 내부 연결·로컬 검증 완료. 운영 자동 분석은 계속 꺼짐.

## 이번 단계의 범위

`AccountedGeminiInputCounter`와 `AccountedGeminiMeasurements`를 추가해 기존 계산 원장과 입력 실측 검사를 실제 실행 코드로 연결했다. 내부 dispatcher가 명시적으로 주입받은 계산 단계를 호출하고, 저장이 확인된 최신 실측 결과만 이후 생성 요청에서 사용한다. 기본 서버/HTTP에는 등록하지 않았다.

```text
현재 동의·입력·무료 조건·검토된 상한 확인
  → 계산 최대분 예약
  → sending + 공유 공급자 한도 차감 확정
  → launch_claimed 확정 + 일회용 메모리 티켓
  → 현재 DB 상태와 승인/입력 재확인 → 계산 전송 시작 1회
  → 응답 수치 정산 확정 → 단기 실측 등록
  → 생성 전 기존 동의·입력·한도·실측 검사 → 생성 및 초안 저장
```

계산 실패를 생성 재시도 사유로 바꾸지 않는다. 토큰 계산만 승인된 개발용 probe의 동의/과거 결과를 이 흐름의 생성 허가로 사용하지 않는다. 운영 준비 검증기는 현재 입력에 대한 전송 범위와 무료 조건을 독립적으로 확인해야 한다.

## 중복 전송과 DB 경계

- migration `0010`은 계산 상태에 `launch_claimed`를 추가한다. 기존 자료를 삭제하거나 초기화하지 않는다.
- `claimAnalysisCountLaunch`는 기존 `sending`을 한 번만 확정하고, 성공 응답을 받은 저장소 객체 안에서만 사용할 수 있는 티켓을 발급한다. 티켓 복사·재접속·다른 저장소 인스턴스·중복 claim은 새 전송 권한이 아니다.
- `launchAnalysisCount`는 첫 await 전에 티켓을 소모한다. 최종 트랜잭션은 쓰기 없이 `global control → guide` 잠금을 잡고 현재 실행/소유권·취소·삭제·manifest·묶음·예산·공급자 허가를 재확인한다. 승인·전체 요청 해시·상한·기한 검사는 실제 fetch 직전에도 수행한다.
- 전송 시작만 잠금 안에서 동기적으로 수행하고 응답 대기는 밖에서 한다. 외부 전송 후 DB 롤백으로 티켓을 재발급하는 구조가 아니다. 최종 트랜잭션의 응답을 잃으면 최대 사용량을 보존하며 다시 보내지 않는다.
- 계산 기록의 프로젝트/모델 범위 해시도 현재 binding과 일치해야 한다. 손상된 범위로 기존 사용량 조회를 건너뛰고 공급자 한도를 더 쓰는 경로를 거절한다.
- `sending`/`launch_claimed`의 취소·만료·소유권 변경 후 복구는 `uncertain`이다. 티켓을 잃어 실제 전송이 없었더라도 전송을 증명할 수 없으므로 최대분을 유지한다. 안전한 미전송 반환은 `reserved`에서만 가능하다.

## 응답과 실측의 수명

- 모델은 기존 `gemini-3.5-flash-lite`로 고정한다. 전체 생성 요청을 `generateContentRequest`로 감싼 계산 본문을 사용한다. 개발용 probe와 실행기는 동일한 본문 생성/제한된 응답 해석 함수를 공유한다. [Google countTokens 계약](https://ai.google.dev/api/tokens)
- 명시적 활성화와 키, `postgres-count-0010` 저장소 계약, 신뢰할 수 있는 현재 준비 보고서의 `count-accounted-0010-v1`이 모두 필요하다. 이 문자열이나 환경변수만으로 운영 준비를 증명하지 않는다.
- 계산 준비·DB 작업·전송·응답까지 최대 20초다. 리다이렉트/자동 재시도/모델 대체 없음. 응답은 최대 64 KiB·4096개 조각·양의 안전 정수 `totalTokens`로 제한한다. 취소 뒤 늦은 응답은 폐기한다.
- 중단을 무시하는 실행이 실제로 끝나기 전에는 같은 실행기의 다음 계산을 막는다. 불확실 정산/미전송 반환은 각각 최대 2초의 숫자 정리만 시도하며, 실패해도 새 외부 호출은 하지 않는다.
- 수치 정산은 전송 후 동의가 철회돼도 가능하다. 대신 철회된 결과는 실측 증거나 생성 허가가 되지 않는다. 정산 확인 유실, 상한 초과, 만료 시에도 실측을 발급하지 않는다.
- 실측은 시작부터 최대 30초·현재 프로젝트/승인/manifest/전체 요청/모델/프롬프트에만 유효하다. 재시작 시 비어 있고, 조회는 외부 통신을 하지 않는다. 별도 검토 상한을 대체하지 않으며 생성의 실제 입력량과 계산 수치가 약간 달라도 각각 기록한다.
- 명시적으로 실행한 dispatcher의 제한된 조회 회차에서 계산 복구도 수행한다. 커서 20건, 회차 복구 최대 5초이며 오래 걸리면 중단하고 다음 회차에 이어간다. 기본 서버의 자동 복구를 켠 것은 아니다.

## 검증

- 기본 **469 processor + 4 client = 473개**, 실제 PostgreSQL **43개**, 총 **516개** 통과. 타입 검사·processor 빌드·린트·Site 빌드도 통과했다. 새 린트 경고는 없으며 기존 Vite 설정의 향후 호환성 안내만 남아 있다.
- 신규 기본 시험 10개(계산 실행기 7개·상태 전환 1개·dispatcher 연결 2개), 실제 DB 시험 8개를 추가했다. 반복 실행은 중복 합산하지 않는다.
- PostgreSQL **16.15**, migration `0000–0010` 적용/재적용 통과. 마지막 시험은 약 43초이며 해당 작업의 `showme-b5-5bb9047f455a477a837db4864fcae881` 컨테이너와 폐기용 tmpfs를 정리했다. 원래 사용자 DB·파일은 유지했다.
- 모든 새 API 응답은 주입한 모의 응답이며 Google 전송은 0회다. 성공 통합 시험은 계산 321·생성 입력 322/출력 20의 서로 다른 수치를 각각 저장했다. 계산 503 시험은 생성 0회·초안 미변경·계산 최대분 보존을 확인했다.

검증 범위: 20개 동시 claim/티켓 사용, 티켓 복사·재접속·응답 확인 유실 모사, 취소·삭제·기한 만료·잠금 대기 후 철회, 최종 전송의 쓰기 없음, claim 롤백, 손상된 프로젝트 범위 차단, 계산→생성의 동일 본문·독립 정산·초안 반영, 계산 실패 시 생성 0회, 취소 뒤 늦은 숫자 정산.

실제 TCP/COMMIT 단절이나 프로세스 강제 종료 시험은 아니다. 모의 이미지/상한/가격/프로젝트 보고서를 실제 Google·비공개 저장소·요금 검증으로 표시하지 않는다. 단순 계산→생성 연결 시험은 전체 영상 업로드→게시/모바일 흐름 시험도 아니다.

## 다음 단계와 유지할 제한

1. 운영 DB/비공개 Storage·같은 승인 입력·무료 프로젝트·모든 호출자를 포함하는 한도 범위·전체 입력 상한의 신뢰할 근거를 묶는 준비 검증기를 구현/검증한다. 모의 보고서와 과거 7,199토큰을 운영 근거로 승격하지 않는다.
2. 위 조건과 별도 전송 범위가 확인된 뒤 승인된 합성 자료로 제한된 실제 연결을 검증한다. 무료 조건이나 권한이 미확인인 부분은 켜지 않는다.
3. 이후 동의/진행/검토 화면, 편집·가림·게시·모바일 검증을 기존 전체 계획 순서로 진행한다.

이번 외부 API 호출 0회. 운영 DB/Storage, `.env`/키/과금, 화면/호스팅, 푸시/배포 변경 없음. 임시 DB만 정리하고 사용자 자료는 유지한다. 운영에서 `0010` 계산 기록을 만든 뒤 이전 코드와 혼용하거나 상태/사용량을 수동 삭제해서 재시도하면 안 된다.
